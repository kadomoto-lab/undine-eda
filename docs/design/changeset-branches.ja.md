# git ブランチ上の changeset(設計)

状態: 採用済みの設計。実装済み(`server/undine/vcs/branches.py`、`server/undine/store/changeset.py`、レビューは
`web/src/panels/ChangesPanel.tsx`。以下の本文で決めていない点は[実装での決定](#as-built)にあります)。ユーザーガイドは
[変更セット (changeset)](../guide/changesets.md) です。

## 目的

changeset は、人とエージェントから見えるものとしては変わりません。タイトルと理由を持つ提案で、専用の作業コピーで同時に 1 人の書き込み者が編集し、
その場で見られ、前後でチェックし、レビューし、採用、破棄、取り消しをします。変わるのは中身です。これまでは `<root>/.changesets/<project>/<id>/
{work,base}` にプロジェクトのライブラリをコピーし、記録した効果を再生して採用していました。これからは git です:

| | これまで | これから |
|---|---|---|
| 提案 | ライブラリのコピー | ブランチ `undine/<project>/<id>` |
| 作業コピー | `.changesets/<project>/<id>/work` | そのブランチの git worktree(同じ場所) |
| 起点 | 2 つ目のコピー(`base`) | 開いたときのプロジェクトのファイルから作る起点のコミット |
| 元の設計のチェック | `base` のコピー | 起点のコミットの、HEAD を切り離した worktree(`.../<id>/base`)。読み取り専用 |
| レビュー | 記録した操作 | 記録した操作と、起点から作業コピーまでの意味的な差分 |
| 採用 | オブジェクト ID で効果を再生 | 起点、今のプロジェクト、ブランチの[意味的な 3 方向マージ](merge.md) |
| 取り消し | 逆の効果 | 同じマージを逆向きに |
| その後 | 記録と証拠 | それに加えて、`refs/undine/changesets/<project>/<id>` に残すブランチのコミット |

変わらないもの: プロジェクト名 `<project>~<id>`(作業コピー)と `<project>~<id>~base`、作業コピーの操作ログ(誰が、なぜ、ターン、タイムライン、
チェックポイントの復元、batch)、書き込みのリース、変更前後のチェックとその鮮度、採用・破棄時に保存する証拠、記録 `<project>/changesets/<id>.json`、
ルート、エージェントのツール。

理由: 履歴、ブランチ、マージを 1 つの仕組みで扱えます。ブランチである提案は、Undine だけでなく git でも push、共有、マージできます。
そして、オブジェクト単位でまとめる処理(マージドライバ)が、採用とブランチのマージで同じコードになります。

## リポジトリ

changeset には、プロジェクトが git のリポジトリにあることが必要です:

- どのリポジトリにも入っていない: 最初の changeset を開くときに `git-setup` を実行し(git init、`.gitattributes`、`.gitignore`、
  ドライバ、フック)、続けてユーザーのブランチにプロジェクトの最初のコミットを作ります(`branches.first_commit`): プロジェクトのファイルを
  そのまま、起点と同じ作り方のツリーで(除くパスもライブラリの検査も同じ)、ユーザーのインデックスにあるプロジェクトの項目から
  (`.gitignore` が無視するファイルでもユーザーが `-f` で追加したものは含めます)、親なし、author は開いた主体、メッセージは
  `Project <project>: its files when Undine set up its repository` です。ブランチはまだ生まれていない(unborn)ときだけそこに作り
  (その間にユーザーがコミットした場合はそちらが優先で、起点はそこから始まり、`"first_commit": null`)、プロジェクトのディレクトリの
  インデックスの項目はすべてそれに合わせ、stat 情報も更新します(ユーザーがステージしていた Undine の出力は追跡しない状態に戻ります)。
  そのため `git status` に出るのはツリーが除いたものだけです。別の git が Undine の待つ時間(2 秒)より長くインデックスを使っているときは、
  コミットはそのままで、`git reset` を実行するよう答えに書きます(`"first_commit_note"`)。これがないとブランチは生まれないままで、
  生まれていないブランチには採用でマージコミットを作らないため、どの採用も未コミットのまま残ってしまいます。結果にそう書きます
  (`"git_setup": true`、`"first_commit": <sha>`)。最初のコミットは起点より先に作り、起点はそれを親にします。そこでライブラリを
  拒否した場合(下記)は、開くのを拒否したほかの場合と同じくリポジトリを取り消します。保存していないレイアウトの編集を持つログは、起点と
  同じくジャーナルのままこのコミットに入ります: 保存する人がその場におらず、開くときに人のレイアウトを保存することはしないためです。
- まだコミットのないリポジトリで、Undine がその場で作ったものではない(手で git init と `git-setup` をした、またはこれより前の Undine が
  設定した): そのためのコミットはせず、採用は理由を付けて未コミットのまま残します(`"why": "no_commit"`)。履歴パネルは
  **最初のコミットを作成** を示します(`POST /api/p/{project}/git/first-commit`。人が行うもので、エージェントのツールはありません。
  Undine 用に設定したリポジトリでだけ示します)。上と同じくプロジェクトのファイルをコミットします。プロジェクトがリポジトリの
  サブディレクトリなら、プロジェクトのディレクトリだけをコミットします(作業ツリーとインデックスのほかの部分はそのままです)。履歴パネルの
  **セットアップ** も、git init を実行したときは最初のコミットを作ります。`undine git-setup` 自体は何もコミットしません(リポジトリに
  まだコミットがないときはそう表示します)。どちらも、セルファイルに保存されていないレイアウトの編集をログが持つあいだは、pre-commit
  フックがそのようなコミットを拒否するのと同じく拒否します(409 `unsaved` でレイアウトを示します。セットアップの答えでは
  `"commit_refused"`)。パネルのボタンは保存されるまで待ちます。
- Undine のマージドライバが登録されていないリポジトリにある(`merge.undine.driver` が未設定。例: git で管理しているホームディレクトリ):
  開くのを拒否し、`undine git-setup <project>`(コマンドの既定とは別のストアでは `undine --root <root> git-setup <project>`。
  履歴パネルでのボタンの表示どおり **セットアップ** でも同じ)を実行するか、プロジェクトを移すよう伝えます。答えはコード `not_set_up`、
  リポジトリの最上位(`"top"`)、プロジェクト(`"project"`)、セットアップするコマンド行(`"command"`)を持つ 400 で、UI は自分の言語で文を作ります。誰も Undine 用に設定していない
  リポジトリに、Undine がブランチや設定を書き込むことはありません。

worktree が持てるのは git が保存するものだけです。また git はシンボリックリンクを、その文字列のとおりにチェックアウトし、worktree のフォルダ
から解決させます。そのため、プロジェクト自身のライブラリ(`project.json` でプロジェクトの中のパスにあるもの。`"git"` の依存関係は含みません)を
worktree がプロジェクトと同じ形で持てない場合も、開くのを拒否します。リンクはどれも、worktree のコピーが解決するのと同じ方法で判断します:
ライブラリのパスを名前 1 つずつたどり、リンクの文字列はそのリンクのフォルダから読みます。ライブラリのフォルダ、その上、その中、さらにリンクの
先をたどった先も対象です。拒否するもの:

- プロジェクトの外か、存在しない場所を指すシンボリックリンク(ループも): 提案の編集はリンクを通って実際のファイルに書き込まれるか、何も
  見つかりません。
- 文字列が絶対パスのシンボリックリンク(プロジェクトの中を指していても): worktree からは、worktree のコピーではなく、プロジェクトの
  ファイルを指します。
- 文字列がプロジェクトの外へ上がる相対リンク(`../../...`。また中に戻ってきても): worktree からは別のファイルを指すか、何も指しません。
- プロジェクトのリポジトリが保存しないリンク、またはリンク先のフォルダ(`.gitignore` が外している、または `llm/` のような Undine 自身の
  出力): worktree にはそれがありません。
- それ自身が git リポジトリであるフォルダ(クローン、またはサブモジュールの `.git` ファイル): git は gitlink として保存し、新しい worktree
  では空になります。

フォルダを見れば分かること(リポジトリが保存するかどうか以外のすべて)にはリポジトリが要らないので、何かを設定する前に最初に確かめます。
拒否された場合は `git init` も `git-setup` も実行しません(`branches.check_libraries`)。リポジトリが保存するかどうかは、起点のツリーを作った
後、起点のコミットを作る前に確かめます。この確認で拒否したのが、プロジェクトをリポジトリにしたばかりの開き方であれば、そのリポジトリを元に
戻します(`.git` を削除し、`.gitignore` と `.gitattributes` を元の状態に戻す)。拒否された開き方がリポジトリを残すことはありません。答えはコード `unsupported_library` の 400 で、ライブラリ(`"library"`)、リンクまたはリポジトリ
(`"path"`。プロジェクトのディレクトリから)、種類(`"kind"`: `link_out` はプロジェクトの外を指す、絶対パス、または外へ上がるもの、
`link_nowhere` は何もない場所かリポジトリが保存しないものを指すもの、`own_repository`)、リンクの文字列(`"target"`。リポジトリでは null)を
持ちます。UI は自分の言語で文を作ります。

代わりにファイルを worktree にコピーしても、ブランチのファイルにはなりません: 採用でマージされないか、コピーでユーザーのリンクを上書きして
しまいます。どうすればよいか: リンクをプロジェクトの中を指す相対リンクにする(`ln -sr`)、リンク先をリポジトリに保存させる、リンクの代わりに
ファイルそのものをプロジェクトに置く、またはライブラリを依存関係(`project.json` の `"git"` のライブラリ)にします。それ自身がリポジトリである
ライブラリは、依存関係にするか、その `.git` をプロジェクトの外に移します(ファイルはプロジェクトのリポジトリのものになります)。プロジェクトの
中の、リポジトリが保存するものを指す相対リンクはそのまま使えます(worktree 自身のコピーを指します)。プロジェクトのほかの場所にあるリンクや
リポジトリは、git の保存するとおりに保存します。

`project.json` で絶対パス(または `~/...`、プロジェクトの外へ上がるパス)で指定したライブラリは、プロジェクトのフォルダではないので、worktree の
フォルダでもありません。作業コピーはそれを元の場所、つまり実際のファイルとして見つけます。そのため作業コピーでは依存関係と同じく読み取り専用に
します(`changeset.Working`)。提案がそこに書き込むことはありません。プロジェクト自身からは、これまでどおり編集できます。

プロジェクトの git の作業はすべて、リポジトリごとに 1 つのロックを通ります(一時的なインデックス、`commit-tree`、`update-ref`、worktree)。
コミットは `commit-tree` で作ります(フックなし、署名なし、author は明示した主体、committer は Undine)。Undine 自身の出力と changeset の記録は、
changeset のコミットには決して入りません: `runs/`、`tapeout/`、`llm/`、`.undine/`、`*.pre-split`、`changesets/` は、Undine が作るどのツリーからも除きます。

## 開く

1. **起点のコミット。** プロジェクトの作業ツリーをそのまま(未コミットの編集と未追跡のファイルを含み、上のパスを除いて)コミットにします:
   一時的なインデックス、`write-tree`、HEAD を親にした `commit-tree`(HEAD がまだなければ親なし)。ユーザーのブランチ、インデックス、
   作業ツリーには触れません。
2. **ブランチと worktree。** `git worktree add -b undine/<project>/<id> .../<id>/work <base>` と
   `git worktree add --detach .../<id>/base <base>`。プレビューのプロジェクトは `<worktree>/<prefix>`(リポジトリの中でのプロジェクトの
   ディレクトリ)です。インストール済みの依存関係(`.undine/deps`。無視されている)は両方にハードリンクします(そのファイルは読み取り
   専用で、その場では書き換えず置き換えるだけなので、ディスクを使いません)。リンクできないとき(別のファイルシステム、
   `UNDINE_STORE_LINK=copy`)は読み取り専用でコピーし、インストールの印のファイルはコピーします。git が追跡しないライブラリのフォルダ
   (空のもの)は作ります。
3. **ログ。** worktree の `history/<lib>.jsonl` は、そのときのプロジェクトのログです。changeset 自身の記録はその後のもの(ライブラリごとの
   `base_seq`。記録に入れます)です。番号付け(gseq)、タイムライン、復元、レビューの操作、Undo と Redo はそれだけを見ます。起点にある
   レイアウトのジャーナル(プロジェクトの保存していないレイアウトの編集)は作業コピーでは再生せず、コピーのときと同じく、作業コピーは
   ファイルから始まります。batch の gseq の床は worktree の隣(`.../<id>/gseq.floor`)に置き、中には置きません。
4. 元の設計のライブラリは読み取り専用です(ジャーナルの再生、保存、レイアウトのセルの追加、どのルートからの編集もしません。Undo と
   Redo は何もしません)。
5. 記録には `"libs": [...]` と `"git": {"branch", "base", "head"(開いたときのユーザーの HEAD), "prefix", "base_seq": {lib: seq},
   "tip": null, "ref": null, "commits": 0}` を入れます。`"base": {lib: {}}`(ライブラリだけで、ファイルごとのダイジェストはもうありません。
   読むものがなく、すべてのファイルのハッシュを取ると開くのが遅くなるため)は古い読み手のために残します。

## 開いている間

コピーのときと同じく、すべて worktree の上で動きます。書き込みのリースが終わったとき、チェックを実行する前、採用・破棄の前に、作業コピーの
開いているレイアウトを保存してから、作業コピーのコミットをブランチに加えます(メッセージ: タイトル、主体、ターン、前のコミット以降の操作)。
コミットは同じものを除いた worktree のファイルから作るので、Undine がそこに自分で書くもの(runs、床)はコミットされません。

## レビュー

レビューは、これまでどおりセルごとの操作と、起点から作業コピーまでの意味的な差分(履歴パネルと同じ表示)を見せます。差分には、操作として
記録されていないもの(作ったライブラリ、取り込んだレイアウト)も出ます。それが採用でマージされる内容です。元の設計のチェックは、起点の
worktree で実行します。

## 採用

1. 作業コピーをコミットします(先端、tip)。
2. **計画。** 起点と先端で違うパスごとに、起点のファイル、今のプロジェクトのファイル、先端のファイルを、ビューのマージ(回路図、シンボル、
   レイアウト、netlist、設計の意図。それ以外は行単位。操作ログはファイルとしてはマージしません。5 を参照)でまとめます。保存していない
   編集のあるプロジェクトの開いたレイアウトは、保存したものとして加わります: 以前の採用と同じく、先に保存します(記録します)。
3. **ファイルをまたぐ検査。** changeset のシンボルのトランザクション(シンボルと、それに合わせて配線を付け替えた利用側)では、各メンバーの
   ビューがプロジェクトで起点のときのままであること、その後に配置された、トランザクションに含まれない利用側がないことが必要です。
   そうでなければ、以前と同じく衝突です。マージで changeset の先端からそのまま取り、起点ではそのシンボルを置いていなかった回路図
   (シンボルを変えた後に changeset が描いたもの。新しいテストベンチなど)には、新しいピンに合わせて置いたインスタンスしかないので、
   追従させる利用側ではありません。取り消しでは、起点からそのまま取り、先端ではそのシンボルを置いていなかった回路図が同じ扱いです。
   前からあったインスタンスは引き続き検査します。元に戻す操作で、古い配線のまま戻ることがあるからです。
4. **全か無か。** 衝突が 1 つでもあれば何も書き込みません。答えはコード `merge_conflict` の 409 で、ファイルごとに
   `{path, kind, conflicts: [{id, what, base, ours, theirs}]}` を返します(パスはプロジェクトのディレクトリから)。そうでなければ、まとめた
   ファイルをすべて書きます(一時ファイルに書き、最後に名前を変え、失敗したら元に戻します)。書き込みは compare-and-swap です: 計画が読んだ後に
   プロジェクトで変わったファイルがあれば衝突 `changed` で、何も書き込みません。
5. **ログ。** プロジェクトのログには、changeset の記録(`"changeset": <id>` 付き)と、changeset を示す `merge` の記録が入ります。Undo は
   そこから始まり直します。採用した changeset は Undo ではなく **Revert** で戻します。
6. **コミット。** ユーザーのブランチにコミットがあり、インデックスに何もステージされておらず(Undine 自身の出力と changeset の記録は
   除きます)、プロジェクトの作業ツリーが採用の前にきれいだった(HEAD との違いがマージで書いたものだけ)なら、ユーザーのブランチに
   マージコミットを作ります: 親は HEAD と先端、メッセージは
   `Apply <id>: <changeset title>` で、理由、主体、チェックの結果を入れ、インデックスもそれに合わせます。そうでなければマージは作業ツリーに未コミットの
   まま残り、答えにそのことと理由を書きます(`"commit": null`、`"uncommitted": true`、`"why"`: `"no_commit"` はブランチにまだコミットが
   ない、`"changes"` はプロジェクトにほかの未コミットの変更があった、`"failed"` はコミットに失敗した、またはその前に Undine が止まった。
   コミットしたマージの `"why"` は null で、以前の記録にはありません)。レビューは理由ごとに文を変え、`no_commit` では履歴パネルの最初の
   コミットへ案内します。
7. 証拠はこれまでどおり保存し(起点と先端のコミット付き。実行結果はハードリンク、「実装での決定」の「証拠」を参照)、1 と 2 の間に保存するので、マージするのは保存した先端です。ブランチは
   `refs/undine/changesets/<project>/<id>` に移し、worktree は削除します(`--force`、続けて `git worktree prune`)。プロジェクトの開いている
   エディタとレイアウトは、ファイルを読み直します。

## 取り消し

先端を起点に、起点のコミットをもう一方にした同じマージを、changeset が変えたパスについて行います。同じオブジェクトへの後からの編集は
衝突です(何も書き込みません)。changeset が追加したファイルは残します(作ったセルがその後ほかに配置されているかもしれないため)。以前の
取り消しが作ったセルを残していたのと同じです。changeset が作ったライブラリの `project.json` の項目も、そのフォルダにファイルが残っている間は
残します。ログはマージしません: プロジェクトのログには、取り消しを示す `merge` の記録が入ります。
コミットするかどうかは採用と同じです。

## 破棄

証拠を保存し、ブランチを残す参照に移し、worktree を削除します。

## 以前の changeset

以前に採用・破棄した changeset の記録は証拠を残し、これまでどおり表示します。その取り消し(逆の効果による)はもう提供しません。
以前の形(コピー。記録に `"git"` がない)でまだ開いている changeset は、確認と破棄ができます(レビューに **Request changes** は
出しません)。採用しようとすると、新しい changeset として提案を作り直すよう伝えます。

## (まだ)扱わないこと

- 採用が衝突した changeset を Undine の中でリベースすることはできません。マージの基準は起点のコミットのままなので、そのブランチ上で git で
  解決しても(ユーザーのブランチをマージしても)採用の助けにはなりません。解決した値が 3 つ目の値になるためです。うまくいく方法: 衝突した
  オブジェクトを両側で一致させてからもう一度採用する(設計側で起点の値に戻すと提案の値が入る。または作業コピー側で変える)、破棄する、
  または Undine の外で git でブランチをマージしてから破棄する。
- 大きなリポジトリのサブディレクトリにあるプロジェクトでは、worktree ごとにリポジトリ全体をチェックアウトします(スパースチェックアウトは
  まだありません)。
- changeset のブランチの push と pull は普通の git です。Undine はリモートのブランチを一覧にしません。

<a id="as-built"></a>
## 実装での決定

上の本文に幅がある点について、実装で決めたこと:

- **開いている間の先端。** ブランチの最後のコミット、コミット数、最後にコミットした `gseq` は、changeset が開いている間は
  `.../<id>/tip.json` に置きます(記録はほかの書き手が古いコピーから書き直すことがあるため: チェックの行、退避したものを書き戻す batch)。
  閉じるときに記録に `tip`、`ref`、`commits` を入れます。
- **作業コピーをコミットするとき。** チェック、採用、破棄の前に加えて、アシスタントのターンの終わり、MCP セッションの終わり(DELETE /mcp)、
  停止の後、画面の `/live` のポーリング(期限切れの MCP のリースはここで分かります)。現在の書き込み者以外がリースを持っている間は
  コミットしません。そのため、UI から始めたチェックが、エージェントの操作の途中でコミットすることはありません。そのリースの終わりで
  コミットします。
- **ログ。** 行単位のマージも logmerge も使いません。マージが触るライブラリごとに、プロジェクトのログをそのまま置き、(採用では)
  `base_seq` より後の changeset の記録を、その印を付けて番号を付け直して(`merged_seq`。`of` と `replay` も追従)続け、最後に `merge` の記録
  `{"changeset", "action": apply | revert}` を書きます。これで、どの場合も changeset を示す区切りが入ります(logmerge の早送りでは
  入りません)。マージがファイルを書くが changeset がログを変えていないライブラリにも入ります。changeset の記録は先端のログから読みます。
  先端にログがない(プロジェクトの `.gitignore` が `history/` を git から外している)ときは、採用では作業コピーのログから、先端をコミットした
  ときの `gseq` まで(新しくコミットするものがなかったときも `tip.json` に残します)を読み、取り消しでは採用がプロジェクトのログに入れた記録
  (`merged_seq`)を読みます。シンボルの検査、レイアウトのジャーナルの検査、ログのマージはどれもその記録から行うので、`history/` を無視していても
  どれも飛ばしません。
- **記録の読み込み。** worktree のログはプロジェクトの履歴全体から始まるので、床より後の記録をログのファイルごとにキャッシュします(デバイス、
  inode、サイズ、時刻で識別)。次に読むときは、その後に追加された行だけを解析し(最後に読んだバイトと照合します)、最初に読むときは行を二分探索して
  床を見つけます。activity のポーリング、レビュー、タイムライン、復元は、呼ばれるたびに履歴全体を解析することはなくなりました。
- **stat のキャッシュ。** 起点のコミットや worktree のコミットに使う一時的なインデックスは、同じ作業ツリーのインデックスのコピー(起点のコミットでは
  ユーザーのもの、worktree のコミットでは worktree のもの。git の racy なファイルの検査のため、時刻ごとコピーします)から始め、親への
  `read-tree -m` で変わっていないエントリの stat の情報を残します。git はすべてのファイルではなく、その後に変わったファイルだけを読みます
  (以前は `core.bigFileThreshold` を超えるファイルをコミットのたびに圧縮し直していました)。ユーザーが assume-unchanged や skip-worktree を
  付けたエントリは、それでも読みます。使えるインデックスがない(まだない、または衝突がある)ときは、すべてのファイルを読みます。コミットのたびに
  (コミットするものがなかったときも)、更新した一時的なインデックスを worktree 自身のインデックスにします(`index.lock` の下で、できる範囲で)。
  開いた後の最初のコミットは、チェックアウトが最後の 1 秒に書いたファイルを一度読み、その後のコミットは変わったものだけを読みます。
- **リポジトリの中の worktree。** ストアの `.changesets/` フォルダは、`.pytest_cache` や仮想環境と同じく自分自身を無視させます: worktree を
  加える前に、そのパスの上で最も近い `.changesets` という名前のフォルダに、`*` だけの `.gitignore` がなければ書きます(既にあればそのままで、
  消すこともありません)。こうして、ストアのルートを含むリポジトリはどれも、フォルダ全体を無視します。プロジェクト自身のリポジトリでも、
  プロジェクトがそれ自身のリポジトリ(ストアの中のクローン)でありながらストアのルートを管理しているリポジトリでも同じで、最後の worktree が
  なくなった後(閉じる処理が残した `tip.json`)も同じです。worktree、`tip.json`、`gseq.floor`、batch や復元の退避は、ユーザーの
  `git status` や `git add -A` に出ません。さらに念のため、ストアのルートがプロジェクトのリポジトリの中にあるときは、その `info/exclude` の
  1 行(`/<path>/.changesets/`)でもフォルダを除外します。`git worktree add` の前に加え、そこにリポジトリの worktree がなくなったとき
  (prune の後)に消します。リポジトリのほかの場所にある worktree は、そこでは自分だけを除外します。
- **リンクやファイルになったフォルダ。** 起点のコミット(と worktree のコミット)は、追跡しているフォルダが今はシンボリックリンクやファイルに
  なっていれば、今の形で取り込みます: 一時的なインデックスから、もう実際のディレクトリではないフォルダの下のエントリを先に取り除いてから、
  そこにあるものを加えます(そうしないと `git update-index` が断ります)。ユーザーのインデックスには触れません。
- **提案の保存していないレイアウトの編集** は、コミットのたびに先に保存します。レイアウトを開かないまま再起動前に行ったレイアウトの編集の
  ジャーナルも、開いて(再生して)保存します。それでもログにジャーナルが残る先端は、衝突 `layout-journal` です。
- **プロジェクトの保存していないレイアウトの編集** は、マージが触るライブラリについて、すべての検査を通った後に保存し(`system` として、
  changeset 付きで記録します)、保存したファイルで計画を作り直します。その後にマージを拒否したか、マージの書き込みが失敗したら、保存が
  残したままである範囲で元に戻します(ファイル、ログ、レイアウトのメモリ。下記)。
- **ロック。** `changeset_lock`(採用と取り消しは順番に行う)、プロジェクトのエディタ(ライブラリのすべての回路図とシンボル、その中の
  すべての設計の意図と RTL のファイル、およびマージが追加するそれらのファイル(エディタが開いていなければ作ります)、開いているエディタ)、
  レイアウト、`netlist._LOCK`、ログ、最後にリポジトリの git のロック。その間に Undine を通して届いた編集(設計の意図や RTL の編集も)は、マージを待ち、
  失われません。
- **compare-and-swap。** 計画が書く各ファイルは、計画が読んだときのダイジェストのままでなければなりません。これらのロックを取らないもの
  (別のプロセス、スクリプト、`git pull`)が変えたファイルは衝突 `changed` です(409 `merge_conflict`。「changed in the project while the
  merge was being made; nothing was written: apply it again」)。何も書き込まず、マージのために保存したレイアウトは、保存が残したままである
  範囲で元に戻します。保存は、残した各セルのファイルのダイジェスト(`wrote`)と、保存後のログのサイズとダイジェスト(`saved`)を記録します:
  セルのファイルは、まだそのダイジェストのときだけ元に戻し(保存が作ったものは消し)、ログは保存前のバイトに、保存したバイトの後に追加された
  行を続けたものに戻します。書き直されていればそのままにします(そのことを報告します)。その間にほかの書き手が書いたもの(記録、新しいセルの
  ファイル)は残ります。レビューはこの衝突と次にすること(もう一度採用または取り消し)を UI の言語で表示します。
- **中断したマージ。** `write_plan` の前に、`<project>/changesets/<id>/merging.json` に、各ファイルの前後のダイジェスト(ログはサイズも:
  マージしたログの `size` と、それが始まるプロジェクトのログの `ours_size`)、マージのコミットの件名(`subject`)、マージの閉じ方を書きます。
  `write_plan` が戻った直後に `written` の印を付け、netlist の同期の後(`paths`)とコミットの後(`commit`)に更新し、記録を `applied`
  (`reverted`)として保存したら消します。その間にサーバーが止まるとこれが残ります。`undine serve` は、netlist の監視役と API を始める前に、
  そうしたマージを先に終えます(`Changesets.finish_interrupted`。`changesets/cs-*/merging.json` のあるプロジェクトをすべて掃除し、終えたもの
  と元に戻したものを表示します)。そうしないと監視役が、マージがまだ名前を変えて入れていない回路図を、入れ終えた netlist に読み戻し、それを
  マージしたログに記録してしまいます。次にその changeset にアクセスしたとき(読み込み、または掃除)も同じことを行います。マージを終えたと
  みなすのは、`merging.json` に `written` か `paths` があるとき、またはすべてのファイルがマージしたものとちょうど同じとき(ログは、マージした
  バイトで始まっていれば。その後に記録が追加されていてもよい)だけです。そのときは記録を保存し、コミットを見つけるかマージを未コミットとし
  (その `why` は `merging.json` が記録した HEAD ときれいさから: `no_commit`、`changes`、それ以外は `failed`)、閉じる処理を行います。コミットとみなすのは、HEAD の最初の親の列にあり、親が記録した HEAD(採用ではそれと先端)で、committer が
  `Undine <undine@localhost>` で、メッセージの 1 行目が記録した `subject` であるもの(以前の `merging.json` では `Apply <id>: ` または
  `Revert <id>: ` で始まるもの)です。その後に人が作ったコミットを、それと取り違えることはありません。そうでなければマージを元に戻します:
  名前を変えて入れたファイルは `.old` ファイルを戻し、ログはプロジェクトのバイトに、その後に追加された記録を続けたものにします(`.old` から、
  `.old` がなければマージしたログ自身の先頭から)。マージが追加したファイルは消し、2 回の名前の変更の間で止まったファイルは戻します。
  隣に `.new` が残っているファイルは名前を変えて入れる前なので、人のものとしてそのまま残します。その後に書き直された netlist は回路図から
  読み直します。名前を変えて入れた後に変わったファイルはそのままにし、名前を示します。changeset はそのまま(開いたまま。取り消しでは採用済み
  のまま)で、記録の `interrupted` に注記を入れ、レビューに出るよう `cleanup_warning` にも入れます。`merging.json` は消すので、もう一度採用
  してもログをマージするのは一度だけです。その後に採用、取り消し、破棄、または復旧が成功すると、注記を消します。どちらの場合も残った
  `.new` / `.old` ファイルは消します。`merging.json` が終わっていない間(復旧が終えることも元に戻すこともできなかったもの)は、採用、破棄、
  取り消しを拒否します(400)。
- **掃除。** プロジェクトとサーバーごとに一度、最初のアクセス(一覧、開く、読み込み。ほかの操作が `changeset_lock` を持っていれば、その後の
  アクセス)で行います。`undine serve` の起動時にも、中断したマージのあるプロジェクトすべてについて行います: 中断したマージを上のように終え、閉じた記録なのにブランチや worktree が残っているもの(記録を保存した後にサーバーが
  止まった)は今閉じ(後から来た編集をコミットして作業コピーを残すか、worktree を削除してブランチを残す)、記録のないブランチ
  `undine/<project>/<id>` や worktree(開いている途中でサーバーが止まった)は、作業コピーをコミットし、worktree を削除し、ブランチを
  `refs/undine/changesets/<project>/<id>` として残します。削除はしません。`retained` の印のある記録と以前の形のコピーには触れず、最後に
  `git worktree prune` を実行します。開いている途中、閉じている途中のものは使用中の印を付けるので、掃除と復旧はそれを飛ばします。この
  プロセスの中だけでなく、プロセスをまたいでも同じです: 操作のあいだ `<root>/.changesets/<project>/<id>.lock` に排他的な `flock` をかけ、
  プロセスが終わればカーネルが解放します。前のサーバーがまだ採用を終えている途中に起動したサーバー(再起動)はそのマージに手を出しません。
  前のサーバーが先に落ちた場合は、次のアクセスがそのマージを終わらせます。
- **書いた後。** まとめた回路図の netlist を読み直し(`netlist.sync`。監視役は何も記録しません)、開いているレイアウトはファイルを読み直し
  (`check_disk(force=True)`)、エディタのシンボルのキャッシュを消します。マージコミットにはこれらのパスも入るので、きれいな状態からの採用の後は、
  インデックスと作業ツリーがコミットと一致します。git が無視していて追跡していないパス(`.gitignore` が `history/` を外しているときのログ)は
  コミットに入れません。UI では、マージが書いたファイル(答えの `paths`)を表示しているタブだけが読み直します。保存していないテキストを持つタブ
  (RTL のタブ、設計の意図の YAML)はそのテキストを残し、テキストを捨てて読み直すためのバーを出します。その間にきれいな状態に戻ったタブ
  (入力を Undo で戻した)は、マージしたファイルを読み直し、バーを消します。
- **マージコミットは HEAD があるときだけ。** まだコミットのないブランチでは、マージは未コミットのまま残ります(`"why": "no_commit"`)。
  プロジェクトの最初のコミット(Undine が git init したときはその場で、それ以外は履歴パネルから作ります)で、ブランチにコミットができます。
- **取り消し** は、HEAD だけを親にしたコミット `Revert <id>: <changeset title>` です。残したファイルは `"reverted": {"kept"}` に入り、残すシンボルの
  トランザクションのメンバーは先端と比べません。先端から起点への `project.json` のマージは、changeset が追加したライブラリの項目を取り除き、
  そこに残したセルと、その後にそこで行った作業もプロジェクトから外れてしまいます。そのため取り消しは、changeset が追加したライブラリ
  (起点ではなく先端の `project.json` にあるもの)のうち、フォルダにまだファイルがあるものの項目を、プロジェクトにある形のまま残します
  (`_keep_libraries`)。その結果マージした `project.json` がプロジェクトのものと同じになれば、書き込みません。
- **証拠。** マニフェストのバージョン 2: `"commits": {"base", "tip"}`。`history/**` はもうコピーしません(worktree のログはプロジェクト全体の
  もので、それらのコミットに入っています)。実行結果はコピーせず、そのファイルへのハードリンクとして保存します(ファイルシステムをまたぐ場合や
  リンクが拒否された場合はコピー。`project.json`、`undine.lock`、以前のコピーのログはその場で書き換わるのでコピー)。証拠のフォルダ
  (`<project>/changesets/<id>/`)と worktree(`<store>/.changesets/`)は通常同じファイルシステムにあり、終了した実行のファイルはその場で
  書き換えず(`Job.set` とログのモデルの注記は新しいファイルに書いて置き換えます)、worktree は閉じる処理で削除するので、最後には証拠が
  その実行結果の唯一の保存場所になります。ジョブのプロセスは専用のプロセスグループを率い(`sim.Process`、すべての種類のジョブ。再起動したサーバーが
  引き継いだシミュレーション `sim.Foreign` も同じグループです)、キャンセルや制限時間はグループ全体を止め(SIGTERM、その後 SIGKILL)、
  閉じる処理はその一部でも残っている間(ジョブが終わった後はステータスに記録したグループで判断します。`sim.left`。`cancel_job` で止められます)と、
  ルートのいずれかのサーバーがシミュレーションをまだ扱っている間(`Jobs.working`: ここで実行中か
  引き継ぎ済み、別の生きているサーバーが走らせているので保留中、引き渡し済み、待機中)は拒否します(`sim.alive`)。そうしないと、
  キャンセルした Verilator のビルドの make と g++ が verilator より長く生き、実行のログに追記し続けます。それでも書き込まれる可能性のある
  実行結果はリンクせずにコピーします(`_copied_runs`): ジョブがキャンセルされた、制限時間で止められた、または終了しなかった実行と、
  何らかのプロセス(止まったサーバーのもの、グループを離れたものも)がその中で作業しているか、そのファイルを書き込み用に開いている実行
  (`sim.writers`、`/proc` から)です。コピーは作りながらハッシュを計算します。各ファイルは数個のスレッドで一度だけハッシュを計算し、
  実行の出力で `[size, mtime_ns, inode]` がステータスがハッシュとともに記録したもの(`provenance.outputs` の `"stamps"`)
  のままのものは読みません。保存中と後片付けのときに提案が変わっていないかは、全ファイルのハッシュの計算し直しではなく、これらの値
  (マニフェストの `"sources"`。再起動後の後片付けのために残します)で判断します。これのない以前のマニフェストはハッシュで比べます。
  マニフェストはバージョン 2 のままです(新しいキーは追加: `"sources"`、
  `"linked"`、`"bytes"`、`"pruned"`)。作業コピーに 3020 ファイル、4.7 GB の実行結果(4 MiB の `out.raw` を持つモンテカルロの実行 600 個と
  512 MiB のもの 4 個。先にページキャッシュから追い出した)を持つ合成した changeset で測ると、以前は採用に 47 秒かかり、4.7 GB を書き、
  18.7 GB を読みました(コピー 1 回とハッシュ 3 回)。今は stamps のない以前の実行で 8.4 秒、書き込み 0.8 MB、読み込みは 4.7 GB を 1 回、
  stamps を記録した実行では 2.2 秒、読み込み 3 MB です。保存中に止められたサーバーが残した途中のもの(`changesets/<id>/.evidence-*`)は
  掃除で削除するので、そのリンクが見えないところで実行結果の容量を持ち続けることはありません。削除は解放する量を示します: 閉じる処理が
  残した作業コピーがまだリンクしているファイル(`st_nlink` > 1)は、その作業コピーとともに解放されます(`"shared"`、`"raw_shared"`、`"freed"`)。
- **閉じる処理の進み具合。** 採用・破棄・取り消しは、changeset のロックを待つ間と処理中に、進み具合を示します(`live.Closings`、メモリ上:
  段階と、保存した証拠のバイト数と全体。バイト数は各ファイルのハッシュを計算したとき、コピーする場合はコピーしながら進みます)。
  `GET .../changesets`、`GET .../changesets/<id>`、画面の `/live` のポーリングに出ます。画面はポーリングで見たものを Changes の一覧と
  レビューに渡すので、すでに開いている一覧やレビューも、別の場所で始まった閉じる処理を表示します。その間に同じ changeset をもう一度
  閉じようとすると、待った後に「open ではない」となるのではなく、409 の `busy` になります。
- **証拠の削除。** 閉じた changeset の保存した実行の波形(`*.raw`、`*.vcd`、`*.fst`)は人が削除できます(エージェントのツールはなく、
  `agent:` のアクターは拒否します)。マニフェストはすべてのハッシュを保ち、削除したことを記録し(`"pruned"`。ファイルを消す前に書きます)、
  記録はその合計を持ちます(`evidence.pruned`)。証拠の検査は、そのファイルを「見つからない」ではなく「削除済み」と報告します。
- **閉じる処理**(採用、破棄)は、まだ開いているうちに、作業コピーが作ったライブラリを記録の `libs` に加えます。そのため閉じる処理はそれらも
  比べ、後から来た編集があったと誤って判断しません。
- **後から来た編集に気づいた閉じる処理** は、それをブランチにコミットし(何も失いません)、いつもの `cleanup_warning` と `"retained": true`
  とともに worktree を残します。掃除はこれに触れません。記録の `retained` が true になる(レビューが **Open retained preview** を出す)のは、
  changeset が閉じていて、そのプレビューが見つかる間だけです。worktree を削除した後にブランチを残せなかったときは、開くものを出しません。
- **採用でマージされる内容。** 開いている changeset に記録した操作もコミットもない間は、レビューはタブを選ばなくても差分を読みます(ポーリングの
  たびに読み直します)。差分にだけ出る変更(セル、またはログ以外のファイル)があれば、**Adopt** と **Run needed checks** を使えます。読むのは
  changeset ごとに一度に 1 つです(大きなレイアウトの差分には数秒かかることがあります): ポーリングが読んでいる途中のものを取り消したり、
  2 つ目を始めたりすることはありません。結果は、レビューがまだその changeset を表示していて、後から読んだものの結果をまだ表示していなければ
  表示します。読んでいる間に作業コピーが進むかボタンを押すと、その後にもう一度読みます。差分に変更が出た後は、ポーリングでは読み直さず、
  作業コピーが進んだときとボタンでだけ読み直します。
- **プレビュー。** `Server.project` は記録からプレビューを見つけます(`changeset.preview`)。`~base` は `Baseline` で、すべてのライブラリが
  読み取り専用です: レイアウトのセルの追加は 403、Undo と Redo は何もせず(記録も書きません)、そのログはどんな書き込みも断ります。
  プレビューの `/git` は `{"repo": false, "preview": true, "changeset", "branch", "base"}` に、プレビュー自身の `unsaved`、`stale`、`reads` を
  付けて答えます。changeset のルートは、プレビューの名前をそのプロジェクトとして受け取ります。

  差分は 400)。まだ開いているものには、レビューは **Request changes** を出しません。

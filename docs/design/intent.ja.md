# 設計の意図(設計)

状態: 採用した設計。手順 1(意図ファイルとエディタ、Intent パネル、エージェントの文脈とツール)は実装済み、手順 2〜4 は未実装。このページでは、設計意図をどこに置くか、ツールが必要とする制約とどう関係するか、人が UI でどう書くか、フローの各段階が必要なものをどう求めるかを決めます。

## 目的

回路図、シンボル、レイアウトは「回路が何であるか」を表します。設計者にはその横に、どのビューにも書かれていない意図があります。
どのポートをどの辺に置くか、どのトランジスタをマッチさせるか、電流の多いネットをどれだけ太くするか、アンプがどれだけのゲインに達するべきか、
なぜ面積よりオフセットが大事か、といったことです。ディジタルのフローでは、その一部をツールのファイル(SDC、ピン順のファイル、マクロの配置)に持ちます。
アナログの設計者は、ほとんどを頭の中かコメントに持っています。

Undine は、この意図を属するセルの横に持つべきです。人、エージェント、ツールのすべてが読める形で、changeset でほかの変更と同じようにレビューでき、
チェックで確かめられるようにします。これはエージェントが作業の拠り所にするものでもあります。人が意図を書き、エージェントがそれを実装し、
人が提案を採用する前に、意図が満たされたかをチェックが示します。

## 決めたこと

| 問い | 決定 |
|---|---|
| 1 層か 2 層か | 2 層。**セルの意図**(要求: セルが満たすべきこと)はセルの上に置くメタな情報で、各ビューは **ビューの意図**(そのビューでどう実現するか)を持つ。ビューの項目は、応えるセルの項目を `serves` で指す。UI では、セルのページの先頭にセルの意図を、各エディタの横にそのビューの意図と、それが応えるセルの意図を表示する |
| 意図はセルのもう 1 つのビューか | いいえ。ビューは 1 つの回路の表現で、互いに比べます(LVS)。意図はそれらに対する要求で、チェックと比べます。セルのビューと並ぶ、もう 1 つの層です |
| 意図か制約か | 設計意図を上位の概念にする。設計者が実現したいこと、守るべきことで、強さの違う種類(目標、選好、制約、仕様、背景)を持つ。ツールが必要とする具体的な制約は、ネットリストが回路図から導出されるのと同じように、フローの段階ごとに意図から導出する(制約生成)。セルのもう 1 つの層にはしない。人が直接決めた制約は、kind が constraint の意図の項目にする |
| どこに置くか | セルに属するもの(ポート、マッチング、仕様、メモ)はセルの意図ファイルに。セルの使い方や作り方で変わるもの(トップでのクロック周期、ダイの大きさ、コーナー、ツールの設定)は、トップのセルを指すプロジェクトのフロー設定に |
| 形式は | 構造化した YAML。回路図の対象(インスタンス、ネット、ポート)を名前で指し、回路図と突き合わせて検証する。ツールの形式(SDC、LibreLane の設定、ピン順のファイル)はそこから生成し、手では編集しない |
| 何が必須か | 最初は何も必須にしない。フローの各段階は必要なものを宣言し、できる限り意図から制約を導出する。導出に必要なものが意図にないときは止まって、何が足りないかを示す。その項目は意図のパネルに現れ、記入するか、明示的にツールに任せる |
| 自由記述は | 書ける。セル全体のメモと、各項目の理由。機械では確かめないが、エージェントには必ず渡し、エージェントはそこから構造化した項目を提案として起こせる |
| エージェントは使うか | 常に使う。エージェントがセルに対して何をするときも(アプリ内でも MCP 経由でも)、そのセルの意図とフロー設定を拠り所にする。どちらも、エージェントが受け取る設計の文脈に必ず入っている。意図と食い違うときは、黙って上書きせずに報告する。人の依頼が、続けて守るべき要求や優先順位として述べたことは、エージェントがその依頼を出典として意図に書き加える |

## 1. ビューと意図

| | ビュー | 意図 |
|---|---|---|
| 例 | 回路図、シンボル、レイアウト、ネットリスト | ポートの辺、マッチングの組、ネットの幅、仕様、メモ |
| 関係 | 同じ回路の別の表現 | それらの表現に対する要求 |
| 一致の確認 | LVS、シンボルのチェック | フローのチェック: 配置器の報告、DRC / LVS、シミュレーションの測定、STA |
| 編集の手段 | エディタ、エージェントのツール | 意図のパネル、選択からの操作、YAML、エージェントのツール |

意図はセルに結び付きますが、描くものではありません。回路図の対象を名前で指します。回路図でインスタンスの名前を変えると参照も変わります。
今、レイアウトが回路図に追従するのと同じです。

## 2. 意図を置く場所

**セルの意図**: ライブラリの中にセルごとに 1 ファイル、`<cell>.intent.yaml` を `<cell>.sch`、`<cell>.sym` の隣に置きます。
Xschem と KLayout はこれを無視します。ライブラリを依存関係として再利用するときは、セルと一緒に付いていきます。中身は次のとおりです:

- **ports**: 種類(信号の入力 / 出力、入出力、バイアス、クロック、電源、グラウンド)と、セルの外形での辺(または `auto`)
- **supplies**: どのネットが電源とグラウンドか(`vdd`、`vss` のような名前から推定して提案する)
- **items**: それぞれ id、種類、言葉で書いた意図(`text`)、任意の `reason`(理由)と `source`(誰が追加したか、どの依頼から来たか)を持つ。
  さらに、追加したときに Undine が `uid` を付けます。git のマージで読める id が振り直されても項目を見分けるための同一性で([意味的な差分とマージ](merge.ja.md))、変わることはありません。編集せずにそのままにしてください

| 種類 | 例 | 強さ |
|---|---|---|
| goal(目標) | 入力オフセットを最小にする | 最適化の方向 |
| preference(選好) | 面積より性能 | トレードオフの判断 |
| constraint(制約) | M1 と M2 を対称に(`rule`: symmetric、インスタンス M1、M2) | 守る。強さは `must`(既定)か `should` |
| spec(仕様) | DC ゲイン ≥ 60 dB(`spec`: 測定、最小 / 最大、テストベンチ) | 測って確かめる |
| context(背景) | 2 pF の負荷を駆動する | 判断の文脈 |

  制約や選好は、それが仕える目標を `serves` で指せます。回路が変わっても理由が残ります
- **notes**: セル全体の自由記述

**ビューの意図**。同じファイルの `views` に置きます。セルの意図を、あるビューがどう実現するかです。セルの意図は、セルが *何を* 満たすか
(目標、選好、仕様、背景。ビューには依存しません)。ビューの意図は、そのビューが *どう* 実現するか、つまり回路図・シンボル・RTL・レイアウト、
またはテスト(`test:<テストベンチのセル>`)ごとの制約や選択です。ビューの項目は、それが応えるセルの項目を `serves` で指します。要求を変えると、
影響するビューの意図が分かり、何にも応えていないビューの制約は「理由のない制約」として報告されます。ID はファイル全体で一意です。
セルの項目にある制約もそのまま有効ですが(古いファイル)、新しい制約は、それを満たすべきビューに置きます。

```yaml
items:
  - {id: g1, kind: goal, text: Minimise the input offset}
  - {id: s1, kind: spec, text: DC gain at least 60 dB, spec: {measure: dc_gain_db, min: 60, testbench: tb_ac}}
  - {id: x1, kind: context, text: Drives a 2 pF load}
views:
  schematic:
    items:
      - {id: c1, kind: constraint, text: Input pair M1 / M2 equal and large, serves: [g1],
         rule: {type: match, instances: [M1, M2]}}
  layout:
    items:
      - {id: c2, kind: constraint, text: M1 / M2 in common centroid, serves: [g1],
         rule: {type: symmetric, instances: [M1, M2], style: common_centroid}}
      - {id: c3, kind: constraint, text: Output on the right edge, height at most 20 um}   # このビュー固有: serves なし
  test:tb_ac:
    items:
      - {id: x2, kind: context, text: Measure with the 2 pF load; phase margin below 60 deg fails, serves: [s1, x1]}
```

**フロー設定**: プロジェクトに置く `flows/<name>.yaml`。トップのセルの作り方ごとに 1 つです(Tiny Tapeout のタイル、
LibreLane での hardening、大きなチップに入れるアナログブロックなど)。トップのセルを指し、その使い方で決まるものを持ちます:
クロック周期と I/O の遅延、コーナー、ダイの大きさや使用率、電源網、各段階のツールの設定です。Undine がモデル化していないツールの設定は、
そのまま渡します(たとえば LibreLane の変数)。

セルの意図ファイル:

```yaml
version: 1
notes: |
  Feeds a 10-bit ADC. Low offset matters more than area.
ports:
  inp: {kind: signal_in, side: W}
  inn: {kind: signal_in, side: W}
  out: {kind: signal_out, side: E}
  ibias: {kind: bias_in, side: auto, decided_by: user, reason: no preference}
supplies: {vdd: supply, vss: ground}
items:
  - {id: g1, kind: goal, text: Minimise the input offset, reason: feeds a 10-bit ADC,
     source: {by: agent:claude, request: "offset as small as possible", turn: t-7}}
  - {id: p1, kind: preference, text: Performance over area, source: {by: user}}
  - {id: c1, kind: constraint, text: M1 and M2 symmetric, strength: must, serves: [g1],
     rule: {type: symmetric, instances: [M1, M2], style: common_centroid}, source: {by: user}}
  - {id: s1, kind: spec, text: DC gain at least 60 dB,
     spec: {measure: dc_gain_db, min: 60, testbench: tb_ac}, source: {by: user}}
  - {id: x1, kind: context, text: Drives a 2 pF load, source: {by: user}}
```

`decided_by` を伴う `side: auto` は、ツールに任せるという判断の記録です(5 節)。値が欠けている状態とは別です。

## 3. 導出する制約

ツールが読む制約は、具体的でツールごとに違います。配置器の対称の組やキープアウト、配線器のネットの幅、LibreLane の SDC やピン順のファイルなどです。
これらはセルの層としては持たず、段階を実行するときに、意図、設計、フロー設定から導出します(制約生成):

- **段階ごとに導出し、実行と一緒に保存する。** 導出した制約は、それぞれ元になった意図の項目を記録します(`derived_from: [g1, c1]`)。
  回路が変わったら、同じ意図からもう一度導出します。古い制約は古い実行と一緒に残ります。
- **見えるが、編集はしない。** ネットリストと同じように、段階ごとに導出した制約を読み取り専用で(生成したツールのファイルと一緒に)見られます。
  実行の結果(守られたかどうか)と並べて表示し、回路図とレイアウトの上にも描きます(対称の軸、マッチングの組、ポートの辺)。
- **上書きは意図に戻す。** 導出した制約を固定したり変えたりすると、その判断を kind が constraint、出典が人の意図の項目として記録します。
  次の導出でもそれが保たれます。
- **誰が導出するか。** 意図からそのまま決まるもの(対称の規則、ポートの辺)は段階自身が導出します。判断が要るもの(オフセットを小さくする目標に対して、
  コモンセントロイドかインターディジットか)は、仕える意図の項目と一緒にエージェントが提案し、人が受け入れます。

## 4. 段階ごとに必要なもの

フローの各段階は、読む意図、そのうち制約の導出に必須のもの、結果を何で確かめるかを宣言します。実装済みなのは、シミュレーション(仕様ごとのテストベンチ)とレイアウト(ポートの種類と辺、電源とグラウンド)です。この 1 つの表から、段階が止まったときの説明、
パネルに出る未記入の項目、準備状況の表示の 3 つを作ります。

| 段階 | 必須 | 任意 | 確かめる手段 |
|---|---|---|---|
| シミュレーション | 測る仕様ごとのテストベンチ | 仕様 | 測定値と仕様の限界の比較(`check_specs`。コーナーと温度も。探索は `sweep`) |
| 回路図からのレイアウト(デバイスの同期) | なし | 制約(デバイスの形) | デバイスの LVS |
| アナログの配置 | ポートの辺、電源、マッチング / 対称の組(または「なし」) | キープアウト、ガードリング | 配置器の報告(組が守られているか、重なりがないか)、DRC |
| アナログの配線 | 電源、重要とされたネットの幅 | シールド、最大長 | DRC、LVS、ネットごとの抽出した幅 |
| LibreLane への書き出し(ディジタル) | クロックのポートと周期(フロー設定)、電源 | ピンの辺と順番、マクロ | STA(セットアップ / ホールド)、DRC、LVS |
| テープアウト(Tiny Tapeout) | タイルのテンプレートに合うポートの種類 | 仕様 | サインオフの一式 |

## 5. 段階が必要としたときに意図を求める

段階は、ツールを動かす前に制約を導出します(3 節)。導出に必要なものが意図にないときは:

1. 段階は止まり、どの項目が欠けていて、なぜその段階に必要かを示します(「アナログの配置には、ポート `ibias` の辺が必要です」)。
2. 欠けている項目は、意図のパネルに「アナログの配置で必要」と印の付いた未記入の行として現れます。表示するだけで保存はしません。
   誰かが記入するまで意図ファイルには何も書かないので、空の項目が差分やレビューに現れることはありません。
3. それぞれ、記入するか、明示的にツールに任せる(「ツールに任せる」)ことができます。任せた場合は、誰がなぜそう決めたかを記録し、
   その段階はもうその項目では止まりません。実行のあとで、ツールが選んだ値を固定することもできます。
4. 意図を記入したり変えたりすると、それに関わる以前の結果は古くなります。今、回路図の編集でチェックが古くなるのと同じです。

エージェントが段階を実行して止まったときは、エージェントが理由を付けた値を changeset の中で提案します(「`ibias` は西側。バイアス回路の隣」、
「`tail` は 80 µA なので幅 0.5 µm」)。人はそれを、ほかの変更と同じようにレビューして採用します。

## 6. UI での意図の書き方

**セルのページ。** セルを単位にします。セル名をクリックすると、そのセルのページが開きます。

- **冒頭。** セルが今どうなっているかを述べる文があり、続いてセルの意図(種類ごとの項目、メモ、段階ごとの準備状況、問題)が
  並びます。*意図を編集* で下にエディタが開きます。
- **ビュー。** その下にセルの **ビュー** を並べます。
  - ソース(回路図、シンボル、RTL、レイアウト)。それぞれビューの意図の件数と、回路図とまだ合っているかを示します。
  - テストベンチ。このセルを置いて駆動する回路図、または仕様が名前で指すものです。最新のシミュレーションと、それが最新かどうかを示します。
  - 使用先。このセルを置いているセルです。
- **水面線の下。** アクアの線が、書いたものの終わりを示します。その下の一段深い面には生成されるもの(必要なときに生成する
  ネットリスト、鮮度付きの DRC / LVS)が並びます。

ページは設計が持っている関係だけを表示し(`server/undine/store/cellviews.py`)、関係を作り出しません。

**各エディタでは**、Intent タブにそのビューの意図(項目の追加・編集と、応えるセルの項目の選択)と、読み取り専用のセルの意図を並べます。
このビューが応えている項目には印が付き、セルのページへのリンクがあります。回路図、シンボル、RTL、レイアウトの各エディタにあります。

セルの意図のエディタ:

- **準備状況** を上部に段階ごとに出します:「シミュレーションの準備 ✓」「レイアウト: 2 件不足」「LibreLane: 対象外」。不足があっても保存はでき、
  止まるのはそれを必要とする段階だけです。
- **区分**: ポート、電源、目標、選好、制約、仕様、背景、メモ。1 つのフォームでどの種類も追加できます。ポートは回路図から取り、電源はネット名から推定して提案します。
- **選択から**: 回路図で M1 と M2 を選び、*対称*、*マッチング*、*重要なネット*、*キープアウト* を選びます。名前を打ち込まないので、参照は常に正しくなります。
- **重ねて表示**: マッチングの組と対称の軸を回路図とレイアウトの上に、ポートの辺をセルの外形の上に表示します。
- **仕様と結果**: 仕様ごとに、確かめるテストベンチと最新の結果(満たした / 満たさない / 古い)を表示します。
- **メモと理由**: セルの自由記述のメモ欄と、各項目の理由。*メモから制約を起こす* を押すと、エージェントがメモを構造化した項目にして、提案として出します。
- **YAML**: 同じ内容をテキストで。一括の編集や読みやすい差分のためで、パネルと同期します。
- **重さ**: 求められた段階の必須項目が欠けていれば赤。もう存在しない対象を指している、または結果が古ければ黄。

## 7. エージェントは意図を拠り所にする

エージェントがセルで作業するときは毎回、意図は「調べてもよいもの」ではなく、最初から知っているものです:

- **文脈に入れる**: サーバーがエージェントのために組み立てる設計の文脈(`<design_context>`、`get_design_context`)に、セルの意図
  (ポート、電源、制約、最新の結果付きの仕様、メモと理由)と、そのセルを指すフロー設定を入れます。アプリ内のターンでも MCP のクライアントでも同じです。
  `get_intent` ツールは、ファイル全体を返します。
- **作業に使う**: エージェントへの指示に、意図を満たすことを書きます。制約に合わせてデバイスを置き、寸法を決め、影響する仕様をシミュレーションで確かめ、
  メモを設計者の優先順位として読みます(「面積よりオフセット」)。意図に関わる対象を扱うツールは、当てはまる意図を返します(「M1 と M2 は対称のペア」)。
- **食い違いは黙って解決せずに報告する**: 依頼が意図と食い違うとき(マッチングの組で「M2 を小さくして」)や、結果が仕様を満たさないときは、エージェントはそう伝え、
  意図を保つ設計の変更か、意図そのものの変更かを、理由を付けて提案します。
- **意図の変更は提案として出す**: エージェントは、changeset の中でだけ、各項目に理由を付けて意図を追加・変更できます。レビューでは意図の変更を
  設計の変更と分けて並べるので、実装だけでなく要求が変わったときに、人がそれに気付けます。
- **意図が足りないとき**: 作業に必要な意図がないときは(5 節)、エージェントは黙って推測せず、理由を付けた値を提案します。
- **依頼から意図に加える**: 人のメッセージが、その作業を超えて残すべきことを述べているときは、エージェントはそれを、作業と同じ changeset の中で意図に
  書き加えます。要求(「2 pF を駆動できること」)、制約(「`ibias` は左に」)、仕様(「GBW は 10 MHz 以上」)、優先順位(「面積よりオフセット」)が
  これに当たります。項目の出典として依頼(引用した文とターン)を記録し、何を加えたかを返答で伝えます。人があとでその項目を確認したり
  広げたりしたときは、その言葉を出典に加えます(`requests`。それぞれに日付と誰が加えたか)。元の言葉の後ろに加え、置き換えることはしません。
  項目は求められたことの記録をすべて残し、パネルにも表示されます。その場限りの指示(「W = 2 を試して」
  「M5 を下に動かして」)は意図に入れません。人はレビューで、これらをほかの意図の変更と同じように確かめ、採用の前に外すこともできます。

## 8. changeset、履歴、レビュー

意図ファイルは回路図と同じように版を管理します。編集は、項目ごとの効果(`{"k": "n", "id": "items.c1", "do": "add" | "del" | "mod"}`)を実行者と理由付きで記録するエディタを通ります。
そのため Undo / Redo が効き、提案の採用・取り消し・復元も回路図と同じように動きます。エージェントは changeset の中でだけ意図を編集します。レビューでは、意図の変更を項目ごとに設計の変更の隣に並べ
(「`ibias` の辺: 未設定 → W」「M3、M4 のマッチングを追加」)、チェックの欄には、提案がどの仕様と制約を満たしているかを示します。

## 9. ツールの形式

ツールのファイルは、実行するときに意図とフロー設定から生成し、その実行と一緒に保存します:

| 意図 | LibreLane |
|---|---|
| フロー: トップのセル、クロックのポートと周期 | `DESIGN_NAME`、`CLOCK_PORT`、`CLOCK_PERIOD` |
| フロー: I/O の遅延、フォールスパス | SDC ファイル(`PNR_SDC_FILE`)。ない場合、LibreLane はクロックの設定から作る基本の SDC を使う |
| 電源 | `VDD_NETS`、`GND_NETS` |
| ポートの辺と順番 | ピン順のファイル(`IO_PIN_ORDER_CFG`: `#N` / `#S` / `#E` / `#W` のセクションにピン名のパターン、`@min_distance`) |
| マクロのインスタンスと位置 | `MACROS`(マクロごとに、ビューと、位置と向きを持つインスタンス) |
| フロー: そのほかのツールの設定 | 設定の変数としてそのまま渡す(`pdk::` / `scl::` の上書きを含む) |

既存の LibreLane の設計を取り込むときは、意味の分かる変数を意図とフロー設定に振り分け、残りはそのまま渡す設定として持ちます。
既存の SDC は、その制約を表現できるようになるまで、フロー設定の中のファイルとして持ちます。意図への読み込みはしません。

Undine 自身が動かすツール(たとえば、レイアウトの作業でアナログの配置器・配線器を使う場合)は、生成したファイルを介さずに意図を直接読みます。

## 未決の問い

- **階層**: サブセルの中の制約と、親の文脈からの同じ制約(親がサブセルの 2 つのインスタンスをマッチさせたい場合)。おそらく、インスタンスに対する制約は、
  そのインスタンスを含むセルに属します。
- **ディジタルのセル**: RTL のビュー(Verilog)があって回路図がないセルは、ポートを RTL から取ります。その場合、参照は RTL のポートとネットに対して検証します。
- **回路図の属性**: Xschem にはすでにネットとインスタンスの属性があります。Undine は意図をそこに散らすべきではありません。パネルに読み取り専用で見せるかは未定です。
- **仕様の測定**(決定済み): measure は、テストベンチの `.meas` の名前、`run_simulation` の AC の値(仕様に `output` を書き、テストベンチが
  AC 解析を自分で実行しないなら `analysis` も書く)、`v(node)`、`<device>.<quantity>`、`<signal>.<statistic>`、
  過渡解析のスペクトルの値(`sndr_db`、`snr_db`、`thd_db`、`sfdr_db`、`enob`、`signal_dbfs`。実行のサンプルの取り方を仕様の `spectrum` に書く:
  ノードか ADC のビット、`fs`、`points`、`start`。テストベンチ自身がその値を出すなら `spectrum` は不要で、意図も
  `spectrum` がないことを警告しません。値を出すとは、`.control` の外にあるその名前の `.meas`、または `.control` の中で
  `echo Measurements for ...` のあとにその値を `print` するか `meas` で測ることです。仕様が自分の `analysis` を持つときは
  テストベンチの `.control` を外すので、その解析の `.meas` だけが数えられます)、仕様自身の `meas`(その実行にだけ加える `.meas` 文)の結果、raw ファイルから読む整定時間
  (`settle(v(out), tol=0.5m, from=10n)`)、ほかの値からの派生の値(`max(t1, t2)`、`-iavg * 1.8`)のいずれかです
  (`server/undine/simulation/specs.py`、`derived.py`、`spectrum.py`)。
- **値がないとき**(決定済み): `.meas` が値を出さない実行(レベルを一度も横切らない)では、その仕様はその点で未測定です。
  一度もなかった値は限界値と比べられないからです。ただ、その出来事そのものが要求であることもあります(「clk の立ち上がりの後に DAC の制御が
  解除された」: 解除されない制御は値を出さない)。そこで仕様は `missing: fail` と書けます。実行されたのに一度もトリガしなかった `.meas`
  (レベルを一度も横切らない。ngspice の「out of interval」。またはそのような `.meas` を使う `param=`)は、その点で未達となり、
  理由「no value」で報告されます。点の組ごとに、それぞれの理由を示します。実行できなかった `.meas`(実行にないノード、どの `.meas` も
  出さない measure、実行されない解析)は未測定のままです。間違っているのは設計ではなく仕様だからです。
- **仕様を確かめる場所**(決定済み): 仕様は `corners`、`temps`、`conditions` を持てて、check_specs や sweep で確かめる場所を指定しないときはそれを使います。
  `corners` と `temps` はリスト、または限界値が違うところの値への対応です(`{tt: {}, ss: {max: 97n}}`: tt と ss で確かめ、ss では 97 ns。
  温度の限界値はコーナーのものより優先)。遅いコーナーだけ緩めた 1 つの要求を、1 つの仕様のままにできます。
  プロジェクト単位のコーナーと温度の組をどこに置くか(フローの設定)と、最新の結果を意図のパネルに出すことは未決です。
- **代役**(決定済み): トップレベルには本物のセルを置きます(レイアウト、LVS、抽出に必要)。一方で、その測定には、遅いブロックを動作モデルに
  しないと現実的でないものがあります。たとえば、SAR コントローラをイベント駆動モデルにして、長い過渡解析から ADC の SNDR を測る場合です。
  仕様の `substitute`({lib/cell: lib/cell})は、テストベンチの下のどの深さにあるセルのインスタンスも、ピンが同じ名前・同じ順の代役として
  ネットリストにします。何も指定しない `check_specs` で同じ値を再現でき、報告には代役の名前が出ます。テストベンチ自身の意図は、そのすべての
  実行が既定で使う代役を制約 `rule: {type: substitute, cells: {lib/cell: lib/cell}}` で持てます。シミュレーションの段階はこれをほかの rule と
  同じように読み、理由(why)も付けられます。呼び出しの代役が仕様のものより、仕様のものがテストベンチのものより優先し、null は 1 つを取り消します。
  回路図の属性(上記)にも、独立した構成のビューにもしません。代役は測定のしかたについての決定なので、その測定と一緒に置きます。
  代役は実行の入力の一部(テストベンチのネットリストの項目)なので、代役を使った結果が代役なしの結果の代わりになることはありません。
  [代役](../guide/verification.md#stand-ins)を参照してください。

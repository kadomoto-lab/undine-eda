# 設計エージェントと MCP

初めての場合は、手順を順に説明した [AI エージェントをつなぐ](../getting-started/connect-ai.md) から始め、チュートリアルの
[AI エージェントと設計する](../tutorials/agent.md) に進んでください。このページはリファレンスです。

<a id="agent-in-app"></a>
## 設計エージェント(アプリ内)

アプリ内の **Agent** は、ブラウザしか使えない人(サーバーのシェルがない)や、小さなローカルモデルを使う場合のためのものです。主な使い方は
MCP でつなぐ外部のエージェントです。既定では隠れています。上部バーの **Changes** のすぐ左に常にある Agent のアイコン(ロボット)で表示・非表示を切り替えます。Undine のアドレスの末尾に `?chat=1` を付けたときと、レビューの **Request changes** でも表示されます。
左の列のセル一覧の上にあり、間の線をドラッグすると高さを配分でき、ダブルクリックで元に戻ります。
選択したものについての質問に答えます。ブラウザが送るのは ID(`M3`、`net Y`)だけで、設計データは送りません。サーバーが ID を解決し
(部品の種類、パラメータ、接続、最近の変更、DRC/LVS の結果)、文脈を組み立てるので、モデルがスクリーンショットから推測する必要はありません。
添付したオブジェクトは入力欄の上にチップ(`M3 ×`)として表示され、メッセージには何を送ったかが記録されます。選択は設計の *リビジョン* に結び付いており、
その後に設計が変わっていれば、更新するまで送信は拒否されます。

接続は常に 1 つだけで、サーバーがそれを強制します(`server/undine/agents/llm.py`):

| 接続 | 接続先 | 設定 |
|---|---|---|
| **Cloud LLM** | Anthropic API(既定のモデルは `claude-haiku-5-5`。ほかのモデル ID も接続設定で指定可) | サーバーの `ANTHROPIC_API_KEY`、または UI で追加した接続(下記) |
| **EDA サーバーの LLM**(英語の UI では *EDA-server LLM*) | サーバーの近くで動く OpenAI 互換のエンドポイント(Ollama、vLLM など。既定は `http://127.0.0.1:11434/v1`) | 接続設定でエンドポイントとモデル(または `UNDINE_LLM_SERVER_URL`)。必要なら `UNDINE_LLM_SERVER_KEY` |

`python -m undine serve --llm-policy {both,cloud,server,none}`(または `$UNDINE_LLM_POLICY`)で、何を使ってよいかを決めます。`server` にすると、
クラウドのクライアントは一切作られません。自動的に別の接続へ切り替わることはありません。会話は始めた接続に結び付いたままで
(別の接続に移すには明示的な「ここで続ける」が必要で、そのとき履歴が新しい接続先に送られます)、キーはブラウザに返されず、
送ったものはすべて `<project>/llm/audit.jsonl` に記録されます。

**UI で自分の接続を追加する。** Assistant の接続設定(スライダーのアイコン)には、組み込みの接続と追加した接続が並びます。**Add a connection** で、
プロバイダ(Anthropic、OpenAI、または任意の OpenAI 互換 URL)、名前、API キーを入力します。Undine はプロバイダのモデル一覧を取得してキーを確かめ、
サーバーの `~/.undine/connections.json`(権限 0600、どのプロジェクトの外。`$UNDINE_HOME` で場所を変更可)に保存します。キーは二度と表示されず
(末尾 4 文字だけを表示)、プロジェクトにも監査ログにも書かれず、接続と一緒に削除できます。接続とモデル(プロバイダの一覧から選ぶか入力)を選んで
**Use this connection** を押すと、切り替えるまでそれが唯一の有効な接続になります。`--llm-policy` の判定では、公開されたエンドポイントへの接続は `cloud`、
このマシンや社内ネットワーク上の接続は `server` として扱います。

API: `POST /api/llm/connections {provider, label, api_key, base_url?}`、`POST /api/llm/connection {connection, model}`、
`POST /api/llm/connections/<id>/models`(一覧を取り直す)、`DELETE /api/llm/connections/<id>`。

**サーバーに API キーを渡す(別の方法)。** UI で接続を追加する代わりに、サーバーのプロセスの環境変数でキーを渡すこともできます。
プロジェクトには保存されません。本人だけが読めるファイルに書き、`scripts/restart.sh` に読み込ませます:

```sh
mkdir -p ~/.undine && install -m 600 /dev/null ~/.undine/env
echo 'ANTHROPIC_API_KEY=sk-ant-...' >> ~/.undine/env      # optional: UNDINE_LLM_SERVER_KEY=...
./scripts/restart.sh
```

<a id="design-intent"></a>
## 設計意図

各セルは、ビューの隣に設計意図を持てます。そのセルが実現すべきこと、守るべきことです。回路図のサイドパネルの **Intent**(意図)で開きます。
中身は次のとおりです:

- **ポート**(セルの外形での種類と辺。*ツールに任せる* も選べる)と **電源**(どのネットが電源とグラウンドか。*推定した電源を使う* で
  `vdd`、`vss` のような名前から埋められる)
- **目標**(最適化の方向)、**選好**(トレードオフの判断)、**制約**(守ること。*厳守* か *推奨*。回路図で選んだインスタンスから、
  対称やマッチングなどの規則を付けられる)、**仕様**(最小値 / 最大値のある測定と、それを確かめるテストベンチ)、**背景**。
  それぞれに理由と、誰が追加したかが付く
- 自由記述の **メモ**、同じ内容の YAML(パネル上部の **YAML**)

上部には、フローの段階ごとに、必要なものがそろっているかを表示します(「レイアウト: 7 件不足」。マウスを乗せると一覧)。
回路図にもうないインスタンスを指す制約のような問題は、その下に並びます。意図の編集は Undo / Redo 付きで記録され、提案の中では、
ほかの変更と同じようにレビューに現れます。ファイルはライブラリの中の `<cell>.intent.yaml` です。

エージェントは、作業するセルの意図を必ず受け取ります(設計の文脈に入り、全体は `get_intent`)。意図を拠り所に作業し、
*厳守* の制約や仕様を自分で緩めることはせず(変更は提案として出す)、あなたが続けて守るべき要求や優先順位として述べたことは、
あなたの言葉を引用して `add_intent` で記録します。その場限りの指示は記録しません。あとであなたが項目を確認したり広げたりしたときは、
その言葉を `update_intent`(`request`)で項目に加えます。パネルは、項目の元になった言葉の下に、日付付きでそれらを表示します。
どれも置き換えられることはありません。意図のツールは `add_intent`、`update_intent`、
`remove_intent`、`set_port_intent`、`set_supply_intent`、`set_intent_notes` です。背景にある設計は [設計の意図](../design/intent.md) にあります。

<a id="the-tool-surface"></a>
## ツール

何かを変えるよう頼まれると、エージェントは changeset を開いてその作業コピーを編集し(`set_instance_params`、`add_instance`、`add_wire`、
`delete_objects`)、`run_checks`(変更前後の DRC/LVS)と `run_simulation` を実行し、`get_selection`、`get_design_context`、`get_checks`、
`get_lvs_report`、`get_drc_report`、`check_device_integrity`、`get_history`、`list_cells`、`get_changeset` で読み取ります(`server/undine/agents/agent_tools.py`。
`get_changeset` は `id` を渡せば、閉じたものも含めどの changeset でも読めます。採用、破棄、取り消しのされ方、そのコミット、操作、
そのときに保存した証拠を返します)。
採用はできません。チャットに行った手順と changeset へのボタンが表示され、人がそこでレビューして採用します。レイアウトのツール
(座標は µm、5 nm にスナップ): `get_layout_info`、`get_device_geometry`、`query_shapes`、`sync_layout`(レイアウトビューを作る。回路図の
パラメータ変更に合う PCell に、その場で差し替える。足りないデバイスを置き、`sky130_fd_sc_hd__inv_1` のような PDK の標準セルは PDK の GDS
から取る)、`place_pcell`、`place_array`、`add_box`、`add_path`、`add_label`、`move_instance`、`swap_instances`、`delete_instances`、
`delete_shapes`、`delete_unused_cells`、`delete_cell`、`restore_changeset`、ブロックを組み立てる `create_library`、`place_cell`、`import_layout`(後述)。
PDK のレイヤースタック上に描くツール(sky130、GF180MCU、IHP SG13G2。タップとリングは sky130 のみ): `route`(1 層の配線を 2 つの端の間に引く。端は点、`"XMS:S"` のようなデバイス端子(1 つの部品のものは `"child@x,y:S"`)、
名前で指したネット。端が別の層にあればビアスタックでつなぐ。直線、L 字、Z 字、行く手にあるものを回り込む道のうち、ほかのネットに触れず
スペースを守る最初のもの。ポリを拡散の上には通さない。点と曲がり角はすべて 5 nm グリッドに乗る。ビアのパッドは出ていく向きに沿わせ、
それでは収まらないときは 90 度回して収まればそちらにする。横切って来たストリップの上ならストリップに沿う向き)、`add_via`(PDK のカットの大きさ、間隔、エンクロージャ、パッドの面積を守るビアスタック。ポリコンタクトの npc は隣のものとつなぐ)、
`add_tap` と `guard_ring`(インプラント、コンタクト、メタルを含む基板タップと n ウェルタップ、閉じたリング。インプラントはデバイス自身の
ものから離し、n ウェルはほかの n ウェルと n+ 拡散から離す)。ほかのネットに触れる形(n ウェルを通じてでも)やスペースを破る形(自分のネットのメタルに残す狭い切り欠きも)、
配置したセル自身のビアの隣で Magic が受け付けないビア(そこにある同じ種類のビアに接する、または半分重なるもの。Magic はアレイのカットを 1 つのコンタクトとして読むので、
ビアは同じアレイにぴったり重ねるか、離して置きます。MIM キャパシタ自身の
コンタクトの上のビアはどれも。たとえば上部極板の via3 アレイの上の via4: 先に極板を capm の外へ引き出します)は、
何がどこでぶつかるかを示して断ります。ネットはレイアウトの接続抽出(ラベルと、回路図に紐付いたデバイス端子の回路図上のネット)から
求め、`dry_run` で何を描くかだけを確かめられます。`get_device_geometry` はデバイスの層(名前でも番号でもどの層でも。コンタクトは配列として)と
端子(S / G / D / B、MIM の極板)を、今のレイアウトと最新の LVS でのそれぞれのネットとともに返します。いくつかの `place_pcell` の部品で
置いたデバイスは、名前で指せば部品すべて(`pieces` にそれぞれの id)、id で指せばその 1 つです。複数フィンガーの PCell をそのまま置いた
もの(nf 2 など)にも端子があり、それぞれ全フィンガーのストリップで、まだつながっていない間は `nets` を添えます。
そのような端子へ、その一部とつながったものから `route` すると、残りのストリップの 1 つへ引きます(1 つのネットだと断られるまで繰り返します)。`around` に名前を渡した
`guard_ring` は、その名前に結び付いた部品をすべて囲みます。`render_layout` はネットの強調表示、
最新の DRC のマーカー(チェッカーごとの最新の実行のもの、ルールごとの色)、層の塗りつぶしができます。答えは短く保ちます: `batch` は変えたことを理由ごとに、`get_changeset` は手順ごとに
(同じような手順は 1 つに)まとめ、理由は 1 度だけ書き、効果はセルごとに数えます(`add box met1 ×20`、インスタンスは名前と位置で。
`detail` で操作ごと)。`get_history` は手順を丸ごと返し、座標はグリッドに丸め、`get_netlist` は求めればテストベンチの長いコードを
省きます(`code: false`、`code_limit`)。回路図のデバイスは `connect_pins` でネット名を使って
接続します(`net: "out", pins: ["M2:d", "M4:d"]`)。モデルはピンの座標を知る必要がありません。人が描くのと同じように、各ピンから、そのネットに
すでにあるいちばん近いピンや配線まで、配線ツールと同じルーターでデバイスを避けて配線を引き、最初の配線にネット名を付けます。電源とグラウンド
(`vdd`、`vss`、`gnd` など)、ピンが 8 本を超えるネット、安全な経路のないピンには、代わりにデバイスの外向きにネットラベルを置きます。
`style: "wire"` または `"label"` でどちらかに固定できます。同じ名前のポート(ipin / opin / iopin)はそのネットにつながります。すべてのピンが
そのネットに載り、ほかのネットをつないでいない場合にだけ書き込みます。`list_symbols` に `ref` を指定すると、シンボルのピンとその位置を返します。
`add_instance` は `rot` と `flip`(左右反転。差動ペアの右側など)を受け付けます。`add_instances` と `connect_nets` では、複数のシンボルの配置や
複数のネットの接続を 1 回で行えます(すべて成功するか、何も変えないか)。書き込みには `reason` が必要で、実際の設計には決して触れません。回数の上限はありません
(サーバーで `UNDINE_AGENT_MAX_WRITES` を設定した場合だけ、changeset ごとに数えて上限を付けます)。

**描いた回路図の手直しとシンボル。** 配線はどれも 10 単位のグリッド上に引かれ、折れ点や接続点はほかのネットのピンや配線から
1 グリッド以上離します(つながっていないものがつながって見えないように)。そう引けないピンにはラベルを付けます。

- `get_drawing` は描き方を返します: 範囲が重なっているインスタンス、各インスタンスの位置・回転・反転と範囲(テキストを含む)、
  ネットごとの配線 ID・ラベル・ピン。`net`、`instances`、`region`(`[x1, y1, x2, y2]`)で絞り込めます。1 回の答えに収まらない大きな図面は、
  重なりを先頭に、詳しさを落として返します(位置、次に名前、次に数)。配線 ID は端点 `x1,y1,x2,y2`(端点を並べ替えたもの)で、
  `delete_objects` や `label_net` にそのまま渡せます。
- 別のネットに描かれているピンは、`connect_pins` / `connect_nets` に `move: true` を付けると同じ 1 手順でそのネットから外してつなぎ直します
  (`disconnect_pins` だけでも外せます)。ピンから最初の分岐点か別のピンまでの配線と、ピン上のラベルを取り除き、残りのネットはつながったまま
  (切れたところは配線し直し)、名前も保ちます。段を挿入するには `connect_nets(nets={"a": ["x5:X", "xd:A"], "b": ["xd:X", "xr:B"]}, move: true)`。
- `label_net(net, wires?)` はネットの配線(指定した ID、または全部)をネットラベルに置き換えます。ぶら下がった残りも消し、ネットの各部分の
  ピンにラベルを付けます。回路は変わりません。図面を横切る長い配線に使います。
- `move_instance` に `view: "schematic"` を付けると回路図のシンボルを動かします(`instance` / `instances`、`dx`, `dy` または `x`, `y`。
  グリッドにスナップ)。ピンの配線は引き直され、それができないときは何も動きません。
- `set_port_order(order)` はポートの順序(サブサーキットのピン順)を決め、シンボルのピンも同じ手順で同じ順に並べ替えます。シンボルの
  ほかのところは変えません(その手順が失敗したときは答えにそう書き、回路図の順序は決めたままです)。`check_symbol` は
  シンボルを回路図のポートと比べます(足りない・余分・重複したピン、向き、ピン順 `pin_order_mismatch`、意図のポートの辺との違い)。
  食い違いは `get_design_context` と `run_checks`(kind `schematic`)にも出ます。`sync_symbol(sides?, regenerate?)` はシンボルをポートに
  合わせます(順序、向き、ピンの追加と削除、辺。`sides` がなければ `set_port_intent` の辺)。手描きのシンボルは図形を保ち、単純な箱の
  シンボルはピンに合う大きさで描き直します。シンボルを置いている回路図の接続は保たれます。それらが接続しているピン(描いた配線でも
  保留の接続でも)は削除できません。
- `sky130_stdcells` の標準セルは電源をパラメータ(`VPWR`、`VGND`、`VPB`、`VNB`)で受け取ります。`get_netlist` はこれを `supply_pins` として
  ネットとの接続に示し、回路図の何も載っていないネット(ピン・ポート・ラベルがなく、コードブロックのノードでもない)を指すもの
  (既定値 `VPWR` のままなど)をインスタンスより前に警告します。この警告はネットリスト、回路図エディタ、`run_checks` にも出ます。

**レイアウトの組み立て。** ADC のようなブロックはセルから組み立てます。ほかの編集と同じく changeset の中で行います。

- `create_library(name)` はプロジェクトにライブラリを追加します(名前は **新しいライブラリ** と同じ規則で、英数字と `_ . + -`。PDK や
  依存ライブラリのものも含め、プロジェクトにすでにあるライブラリの名前は使えません)。新しいライブラリのログに記録されてレビューに表示され、
  changeset を採用すると `project.json` に加わります。
- `place_cell(lib, cell, child, x, y)` はレイアウトセルを、その原点が x, y に来るように置きます。置けるのは、`lib` のセル、ほかのライブラリの
  セル(`child_lib`。レイアウトエディタでほかのライブラリのセルを置くときと同じく、下のセルごと `lib` にコピーします)、名前で指定した PDK の
  標準セル(`sky130_fd_sc_hd__nand2_1`。ライブラリは名前から決まり、レイアウトは置くときに PDK の `libs.ref/<library>/gds` の GDS から
  読みます)です。`lib` に同じ名前のセルがあるときは、下のセルも含めて指定したものと同じ場合だけそれを置き、違えば断ります。コピーするセルの
  下のセルと同じ名前で中身の違うセルが `lib` にあれば、別の名前(`via$1`)でコピーし、応答でそれを示します(`renamed`)。`rot`(0、90、180、
  270)と `mirror`(先に x 軸で反転)で向きを決めます。`columns`、`rows`、`pitch_x`、`pitch_y` を指定すると、要素数 1048576 までの 1 つの
  規則的なアレイインスタンスになります(CDAC の単位容量など)。LVS はその要素をすべて抽出し、レビューとログには 1 つのインスタンスとして
  残ります。要素が別々の回路図インスタンスに属する場合(コモンセントロイド配置など)は、アレイや単独のインスタンスをいくつかに分けて置きます。
  `name` は `sync_layout` と同じようにインスタンスを回路図インスタンスに結び付けるので、`get_layout_info` はそれをそのデバイスとして扱います。
  結び付けたアレイや、デバイスの PCell ではないセル(回路図の容量に結び付けた単位容量など)は、レイアウト独自のものです。回路図のパラメータが
  変わっても、`sync_layout` がそれを 1 つの PCell に置き換えることはなく、`get_layout_info` は回路図から決まるセルとともに `own_layout` に
  挙げます。LVS は結び付けによらず、抽出したデバイスを回路図と比べるので、回路図にも同じ数のデバイスが必要です(たとえば `MF` を単位容量の
  数にする)。回路図にそのインスタンスがないとき、また `sync_layout` がその結び付けをどう扱うかは、応答で警告します。
- `import_layout(lib, path | job)` は GDS / OASIS ファイルのセルをライブラリに取り込みます。ジェネレータが書いたファイル(**インポート** と
  同じく、サーバーのインポート用ディレクトリ `--import-root` の下にあるもの)か、`run_librelane` の実行の最終 GDS(`job`)です。新しいセルは
  追加してすぐに保存し、同じ中身のセルがすでにあればそのままにします。中身の違うセルを黙って上書きすることはありません。そのセルの名前を挙げて
  取り込みを断り、`replace` に挙げたときだけ置き換えます。置き換えたセルは、古い図形とインスタンス、新しい図形とインスタンスを記録するので、
  レビューに表示され、元に戻せます。ファイルが定義せずに置いているセルは、ライブラリにあるか、PDK の標準セルでなければなりません。

changeset をコピーや取り込みの前のチェックポイントに戻すと、それで入ったセルも取り除きます。ただし、ほかの何かがそのセルを変えていない場合に
限ります(記録には、入ったときの中身が残っています。ライブラリのセルファイルから読み直しても、その中身は変わりません)。`create_library` の前の
チェックポイントに戻すと、セルがなくなったあとでライブラリもログごと取り除きます。記録された操作が作っていないファイルがあれば、戻すのを
断ります。

**エージェントが操る回路図駆動のデバイス。** `sync_layout` は、回路図しかないセルにレイアウトビューを作ります。MIM コンデンサの `MF` が
求める数のユニットを、ルールどおりのピッチの 1 つのアレイとして置きます。MOSFET には、ソース / ドレインがバルクのネットにあるときだけ
突き合わせのタイを付け、そうでなければガードリングを付けます([レイアウトエディタ](layout.md#schematic-driven-layout)を参照)。引数 `layout` は
デバイスのレイアウトパラメータを設定し、それはレイアウトインスタンスに保存されます:

- `{"XMS": {"nf": 4}}` は、回路図の 20 µm 1 本のフィンガーを、つないだ 5 µm 4 本で描きます。LVS は W 20 のまま一致します。
- `bulk`、`tap_side`、`gate`、`sd_contacts` でタップとコンタクトを選びます。
- `columns` でユニットのアレイの形を決めます。

ほかのツールは次のとおりです:

- `place_pcell(pcell, params, x, y, rot, mirror, name?)` は、PDK の任意の PCell を選んだパラメータで生成して置きます。ダミーにも、
  回路図インスタンスの一片にもでき、一片は `sync_layout` が設計者に任せます。知らない PCell やパラメータは、有効なものの一覧とともに
  断ります。ライブラリにすでにあるバリアントは生成し直しません。
- `place_array(devices, pattern, origin, ...)` は、いくつかのデバイスのユニットを 1 つのグリッドに置き、各ユニットをそのデバイスに
  結び付けます。`common_centroid`(各デバイスのユニットを中心に対して点対称に置く)、`interdigitated`、またはマスごとに与える行から
  選びます。ダミーの輪も付けられます。ダミーは結び付けないか、ちょうど同じ数のユニットを持つダミー用のデバイスに結び付けます(数が
  合わなければ LVS が数え違えるので断ります)。応答はユニットの配置図、各デバイスの重心のずれ、使ったルールのピッチと、各ユニットの原点の
  位置です(配置図からユニットの id が分かります)。MOSFET のユニットは 1 つのウェルとインプラントを共有し、ガードリングの中に入ります。
  厚膜酸化膜のユニットでは、リングとそのウェルも hvi の中に入れます。
- `delete_instances` は、id(`get_layout_info` が示す `child@x,y`。原点をグリッドどおりの µm で書きます)、結び付いた回路図インスタンス、
  箱、セルのいずれかでインスタンスを削除します。
- `move_instance` は、結び付いたものも結び付いていないものも、`dx` / `dy` だけ、または `x` / `y` へ動かし、`rot` / `mirror` を設定します。
  指定しなかったほうはそのままです。`x` / `y` がなければその場で回してから `dx` / `dy` だけ動かします。
- `swap_instances(instances: [a, b])` は、2 つのインスタンスを 1 つの記録された手順で入れ替えます。場所(それぞれが相手の原点と向きを
  取る)を入れ替えるか、`what: "binding"` なら結び付いた回路図インスタンスを入れ替えます(どちらも動かず、同じセルのインスタンス同士のみ)。
  id は場所を表すので、CDAC の結び付いたユニット 2 つをこれで入れ替えれば途中の空き場所はいりません。場所を入れ替えたあとは、それぞれの
  id が相手のインスタンスを指します。
- `restore_changeset(to)` は、`get_changeset` が挙げる戻せる時点の 1 つへ changeset を戻します。既定では最新の 12 個を挙げ、
  それより古いものの数を `restore_points_more` で示します。`restore_points`(数か `all`)と `restore_before`(時点。それより前のもの)で
  どれにも届きます。時点は changeset の記録の番号で(`restore_point_now` が今の位置)、`operations` は効いている操作の数なので、
  取り消した操作、undo / redo / restore の記録、取り消された batch の分だけ違います。batch がまだ適用中のとき(呼び出した側が
  いなくなっていても)は `in_progress` がどこまで進んだか(`of` のうち `done`)を示し、終わるまでその操作は数えも挙げもせず、時点もありません。
- `delete_unused_cells(lib, cells?, include_baseline?, dry_run?)` は、Undine が生成した PCell のバリアントのうち、もうどこにも
  置かれていないもの(nf やゲートの側を変えた `sync_layout`、消した `place_pcell` の部品が残すもの)を、それを包む `sync_layout` の
  `_par` / `_tie` セルとともに取り除きます。`cells` がなければ、この changeset が作ったものだけを取り除きます。changeset より前から
  あったもの(先に採用された changeset が残したもの)は `baseline_unused` に数だけ示し、`include_baseline: true` か名前を挙げたときだけ
  取り除きます。対象はそうしたセルだけで、設計者のセルやまだ置かれているセルは断ります。各セルの中身ごと記録するので、
  戻せば元に戻ります。`run_checks` はそうしたセルをもともと検査せず(バリアント単独では設計ではなく、Magic の LU.2 で落ちるため)、
  その数を `skipped_unused_cells` で示します。
- `delete_cell(lib, cell, views?)` は、changeset のセルを削除します。レイアウト、回路図、シンボルのどれか(既定では持っているビュー
  すべて)で、もういらなくなった試作のセルなどに使います。どこかに置かれている間は断ります(レイアウトのセルが別のレイアウトに、
  シンボルが回路図やテストベンチに置かれているとき、置かれたシンボルを残して回路図だけを消すとき)。中身ごと記録するので、戻せば
  元に戻り、changeset を採用するとプロジェクトから取り除かれます。そのレイアウトが置いていたセルは残ります。
- `get_changeset` は、この changeset が作ってまだ残っているセルをすべて `new_cells` に挙げます(`lib/cell` とそのビュー。生成した
  PCell のバリアントと、それを包む `_par` / `_tie` セルも含みます)。それ以外のセルはすべてベースラインのものです。

`get_layout_info` はアレイを列数、行数、ピッチとともに示します。結び付いていないインスタンスは id とともに挙げ(セルごとの数も示します)、
`sync_layout` が触れない結び付いたインスタンスも挙げます(`own_layout`)。

その `wiring`(sky130)は、描いた導体を KLayout で LVS デッキと同じつなぎ方でフラットに抽出し、置いた各デバイスの端子で調べた
結果です:

- `unrouted_nets`: 端子がまだつながっていないネット。離れているピンも示します。ポートのラベルもそのネットのピンの 1 つと数える
  ので(`vout (label)`)、取り残されたピンも見つかります。基板も n ウェルも配線ではないので、ここでは何もつなぎません。
  `substrate_only` は基板だけがつなぐはずの未配線のネット(レールのない `vss` など)、`well_only` は n ウェルだけがつなぐネット
  (1 つのウェルにある `bt` の pMOS のタイ 2 つで、間に金属がないもの)を挙げます。デッキがすべての p タップを基板のネットに、
  n タップをそのウェルにつなぐので、LVS はどちらでも一致します。
- `body_ties`: 自分のタップを持たないデバイス(bulk `none` で同期したもの)のボディは、バルクのネットのタップが同じ基板の領域
  (pMOS なら同じ n ウェル)にあり、拡散からラッチアップ距離(sky130 では 15 um、LU.2 / LU.3)以内にあれば、つながっていると数えます。
  たとえば周りの `vss` のガードリングや、隣のレールの p タップです。各項目はそのタップ(`tap_um`)と、拡散のいちばん遠い角までの距離を
  示します。ネットのタップとは、そのネットのほかのピンかラベルに配線されたタップです。そのようなボディだけのネット(セル内にラベルの
  ないウェルのバイアスなど)では、ほかのネットに配線されていないタップです。`bodies_untied` は、つながっていないボディとその理由
  (そのようなタップがない、いちばん近いタップが遠すぎる)を示します。
- `shorts`: 触れ合っているネット。タップ(またはボディ)が 1 つの n ウェルを共有する 2 つのネットも挙げます(`on: nwell`)。
- `butted_taps`: ほかのネットのソース / ドレインに突き合わせたタップ。LVS はこれを見ません。

`route` も同じ見方をします。n ウェルだけがつなぐ 2 つの端は「すでに 1 つのネット」ではないので、その間の金属を描きます(答えの
`note` がそう言います)。

`batch` は 1 歩で 2000 操作まで受け付けます。sky130A のプロジェクトで `add_box` 2000 回は、1 回の `batch` で約 4 秒、別々の呼び出しで
約 6 秒、32 × 64 の `place_cell` アレイは 0.01 秒です(`server/tests/bench_layout_assembly.py`)。

`run_simulation` は、設計者がグラフから読み取る値を返します。動作点では、すべてのノード電圧と、各トランジスタのバイアス
(`id`、`vgs`、`vds`、`vth`、`vdsat`、`gm`、`gds`、動作領域、`vds_minus_vdsat`)、それに飽和領域にないデバイスの一覧。AC では `output`
(と `input`)を指定すると、低周波利得、-3dB 周波数、利得帯域幅、位相余裕、利得余裕と、10 倍ごとの利得・位相。過渡解析と DC スイープでは、
信号ごとの初期値、最終値、最小、最大、最も急な傾きと、間引いた波形。そして `.meas` の結果です。解析の引数はチェックされます
(`ac`: `sweep`、`points`、`fstart`、`fstop`、`tran`: `step`、`stop`、`tstart`、`tmax` または `maxstep`、`uic`、`dc`: `source`、`start`、`stop`、`step`)。失敗した場合は、ログのエラー行と
その一般的な意味を返し、モデルが受け付けない寸法のデバイスがあればその名前も示します。モデル指定のないテストベンチには PDK のモデル
(typical コーナー)を読み込み、そのことを伝えます。PDK のコーナーシンボル(`sky130_fd_pr/corner.sym`)を置くと、別のコーナーを選べます。
`corner`、`temp`、`options`(シミュレータのオプション: `reltol`、`abstol`、`method`、`maxstep` など)を渡すと、テストベンチを編集せずに、
PDK のコーナー、温度、別の許容誤差で実行します。`measure` には、その実行にだけ加える `.meas` 文(`vm()` / `vp()` を使う AC のものも)と、
Undine が実行結果から読む値を書けます。`settle(v(out), tol=0.5m, from=10n)` は、`from` のあと信号が最終値(`target` を書けばその値)の
`tol` 以内に入り、`to`(既定は実行の終わり)まで出なくなるまでの時間です。`max(t1, t2)` や `-iavg*1.8` のような派生の値も書けます。別の測定値をレベルに使う `.meas`
(`WHEN v(out)='vf-1m'`)は、ngspice がそれで実行全体を止めてしまうため、実行の前に拒否します。

過渡解析は `tstart`(この時刻以降の結果を残す)、`tmax`(最大の時間刻み)、`uic: true`(`.ic` の値から始める)も受け付けます。`analysis` を
指定すると、その実行ではテストベンチ自身の `.control` ブロックと解析行を置き換えます。値の出なかった `.meas` は、ngspice の理由と文とともに
`measurement_errors` にすべて並びます(`v(a,b)` のような存在しないベクトル、一度も横切らないレベルなど)。テストベンチ自身の `.control`
ブロックの後に ngspice がもう一度評価した測定は失敗として報告しません。また、そのブロックがすべての解析をすでに実行している場合は、Undine が
ブロックの最後に `quit` を加えるので、解析は 1 回だけ走ります。1 回の実行で 99 個を超える `par()` の測定も使えます(ngspice 自身の上限は
99 個です。Undine が B ソースで計算します)。モデルについてのヒントは、モデルが実行を止めたときにだけ表示し、そのトランジスタ、W / L / nf
(フィンガーあたりの W)、モデルのビンを示します。解析が途中で止まった実行(時間刻みが小さくなりすぎた、モデルがデバイスを受け付けない)は、
途中までの raw ファイルがあっても失敗です。最後まで終わった実行のログにあるエラー行は `warnings` に入ります。PDK のスタンダードセルのシンボル(`sky130_stdcells/inv_1.sym`)を置いたテストベンチには、
モデルと同じようにセルの SPICE(`sky130_fd_sc_hd.spice`)を読み込みます。コーナーも引き続き選べます。

**依存関係のコード。** 依存関係のセルや RTL がコードを実行したり PDK の外のファイルを読んだりし、その依存関係を人がまだ信頼して
いないとき、`run_simulation`、`sweep`、`check_specs`、`lint_rtl`、`run_rtl_sim` は拒否されます
([依存関係のコードを信頼する](libraries.ja.md#trusting-a-dependencys-code))。ツールは拒否を結果として返します: セル、見つかった
もの、人が `lib trust` か Undine の **信頼...** で信頼すること。エージェントのツール、`undine call` のコマンド、クライアントの
メソッドのどれも、依存関係を信頼することも、ブラウザのダイアログが使う確認を求めることもできません。エージェントは拒否をそのまま
伝え、あなたに尋ねます。

**長い実行。** 各実行は ngspice のスレッドを 1 つ使い、サーバーが同時に走らせるシミュレーションの数には上限があります(既定はコア数から 2
を引いた数。[設定](../reference/cli.ja.md))。それ以外は順番に待ちます。`run_simulation` は `wait_s`(既定 150 秒、0 ですぐに返す)だけ待ちます。
まだ続いている実行はエラーではありません。答えにはその `job` と `state`(`queued` なら待ち順の `queue_position`、`running` なら
`elapsed_s`)と、続け方が入ります。`wait_for(events=["job:<id>"], timeout_s=1800)` で終わりを待ち、`run_simulation(lib, cell, job="<id>")`
で結果を受け取ります(`signals`、`output`、`spectrum` は自由に指定できます)。`cancel_job(job)` はエージェント自身の実行(自分の changeset の
もの、または自分のセッションが始めたもの)を止めます。実行は時間の上限(既定 1 時間)で止まります。`run_simulation`、`check_specs`、
`sweep` に `time_limit_s` を渡すと、より長い実行を許せます(既定では最大 12 時間)。時間切れや取り消しのときは ngspice を終了させ、
応じなければ強制終了します。

**サーバーを再起動しても**(変更を反映するため)実行は続きます。ngspice は走り続け、次のサーバーがそれぞれの実行を引き継ぎ(枠、
時間の上限、`cancel_job`、結果の受け取りはいつもどおり)、待っていた実行を順番どおりに始めます。`wait_for` や `run_simulation(job=...)`
は同じジョブ ID のまま使い続けられます。待つ呼び出し(`wait_for`、`run_simulation`、`check_specs`、`run_checks`、
`extract_parasitics`)は、サーバーに停止が求められるとすぐに答えます(`wait_for` の答えには `"stopping": true`)。数秒後にもう一度
待ってください。エージェントのセッションと変更セットも引き継がれます([サーバーの再起動](../reference/cli.ja.md#restarting-the-server))。
どのサーバーも終わらせられないシミュレーション(ngspice が強制終了された、異常終了した、マシンが再起動した)だけが、理由とともに
`interrupted` になります。実行し直してください。それ以外の実行は引き継がれません。DRC(KLayout または Magic)、LVS、ERC、寄生抽出、
RTL、LibreLane の実行はサーバーと一緒に `interrupted` で終わります(`wait_for` は `ended` に挙げます)。サーバーが戻ってから実行し直して
ください(チェックは `run_checks` または `extract_parasitics` で)。

`spectrum` を指定すると、過渡解析を ADC やサンプル&ホールドと同じ方法で測ります。回路のクロックに合わせて `start + k / fs` の時刻で
`points` 個のサンプルを取り(シミュレータの時刻点の間は線形補間)、ノード(`signal`。差動なら 2 つ)か、ビットから組み立てた ADC の出力コード
(`bits`。LSB から順に並べ、それぞれをロジックレベルの中間か `threshold` で 0 / 1 に判定します。冗長なコードには `weights`)を対象にします。
コヒーレントサンプリング(fin = fin_bin × fs / points。fin_bin は奇数で points と互いに素)を前提とした矩形窓の FFT 1 回から、
`sndr_db`、`snr_db`、`thd_db`(第 2 から第 6 高調波。第 1 ナイキストゾーンに折り返して数えます。数は `harmonics` で変えられます)、
`sfdr_db`(そのスプリアスの位置も)、`enob` = (SNDR − 1.76) / 6.02、`full_scale`(ピーク・ツー・ピークの電圧、または 2^N コード)を指定すれば
`signal_dbfs` を求めます。信号のビンの隣への漏れ(コヒーレントでないサンプリング、またはまだ整定していない信号)は、使うべきコヒーレントな周波数とともに警告として返します。
信号のないサンプル(止まった ADC)は最悪の結果として扱い、仕様を満たさないようにすべての値を -300 dB(THD は +300 dB)にします。
実行した時間の範囲外のサンプルや、過渡解析でない実行は拒否します。

**仕様。** `check_specs(lib, cell, corners?, temps?)` は、セルの意図にある仕様をそれぞれのテストベンチで測り、満たしているか、
どれだけ余裕があるか、最悪の条件はどこかを返します(測れなかった点がある仕様は、満たしているとは言わず not fully measured とします)。仕様の measure には、`.meas` の名前、AC の値(仕様に `output` を書き、テストベンチが
AC 解析を自分で実行しないなら `analysis` も書く)、動作点の `v(node)`、`<device>.<quantity>`、`<signal>.<min|max|final>`、
過渡解析のスペクトルの値(`sndr_db`、`snr_db`、`thd_db`、`sfdr_db`、`enob`、`signal_dbfs`。仕様に上と同じ `spectrum` を書く)、仕様自身の `meas` の結果(その実行にだけ加える `.meas` 文。
テストベンチを変えずに遅延や立ち上がり時間を測れます。評価できなかったものは ngspice の理由付きで報告します)、整定時間や派生の値(上と同じ)が使えます。
`corners: ['all']`、`temps: [-40, 27, 125]`、`conditions`(電源のようなテストベンチのプロパティ: `{'tb_ac/V1.value': ['1.62', '1.98']}`。
数値的な限界を確かめるなら `options.reltol` のようなシミュレータのオプション)
を指定すると、すべての組み合わせを実行します(実行ごとに PDK のモデルライブラリのセクションを選び、`.temp` を設定します)。
仕様は自分の `corners`、`temps`、`conditions` を持てて、呼び出しで指定しないときはそれを使います。`corners` と `temps` は、
限界値が違うところの値への対応(`{tt: {}, ss: {max: 97n}}`)でも書けます。点が複数あるときは、各点での各仕様の値を返します。
実行が失敗した点や値が出なかった点はそのまま示し、別の点の値で置き換えることはしません。`missing: fail` を持つ仕様は、実行された `.meas`
が値を出さなかった(一度もトリガしなかった。たとえばクロックの後に解除されない制御信号)点を、未測定ではなく、理由「no value」の
未達とします。実行できなかった `.meas`(実行にないノードなど)は未測定のままです。入力がまったく同じ実行は再利用し、
どれを再利用したか、それがいつ実行されたかを返します。`fresh: true` を渡すと、独立に確かめるためにすべて実行し直します。
`mismatch: {runs, seed}` は、PDK のデバイスミスマッチのモデル(sky130 では `_mm` セクション、`MC_MM_SWITCH=1`)で各点をその回数、
実行ごとに別のシード(1 から)で実行し、仕様ごとに平均、標準偏差、最小・最大、限界値に対する歩留まり(終わった実行についての値で、
実行中のものは別に数えます)と最悪のシード(`missing: fail` なら値を出さなかった実行も)を返します。1 回の呼び出しの 120 回のシミュレーションを超える分は減らし、そのことを伝えます。
途中で止まった過渡解析(`Timestep too small`)は失敗した実行として扱います。
`sweep(lib, cell, vary, ...)` は、設計を編集せずに寸法を探ります。`vary` に書いた設計の選択肢の組み合わせごとに、編集したかのように
ネットリストを作り(`{'M1.W': [1, 2, 4]}`、別のセルなら `cell/instance.property`、範囲なら `{from, to, steps, scale}`)、すべての条件で仕様を測り、
各設計点を最悪の条件で評価して、限界に対する最悪の相対余裕の順に並べます。1 回の呼び出しで最大 120 回のシミュレーションを、
数本ずつ並行して実行します。入力がまったく同じ実行は再利用するので、もう一度呼ぶとすぐに返り、実行中だったスイープの続きも集めます。
エージェントはそのあと、選んだ値を changeset で設定し、`check_specs` で確かめます。

**ポストレイアウト。** DRC と LVS が通ったら、`extract_parasitics(lib, cell, mode)` でレイアウトのセルを Magic で抽出します。
モード `c` は各ネットの基板への容量とほかのネットとの容量を、モード `rc` はさらに配線の抵抗を加え、カップリング容量はそのまま残します
(Magic 自身の抵抗抽出はカップリングを二重に数えます。[検証](verification.md#parasitic-extraction-and-post-layout-simulation)を参照)。
結果は、ネットごとの容量、大きいカップリング、ネットごとの抵抗、デバイス、ポートが回路図と合っているかを返します。`get_parasitics` で
読み直せます(`net` を渡すとそのネットの行だけ。ないネットの名前なら、近い名前を添えたエラー)。LVS が合わないレイアウトでも診断のために
抽出し、`warning` を付けます。`runtime_s` はかかった時間です。`run_simulation`、`check_specs`、`sweep` に `extracted: ['lib/cell']` を渡すと、そのセルを
抽出結果に置き換えてシミュレーションします。抽出結果がない、古い、または回路図のポートが足りない場合は、何を実行すべきかを添えて拒否します。

**代役。** 同じツールに `substitute: {'lib/cell': 'lib/cell'}` を渡すと、セルのすべてのインスタンスを、ピンが同じ動作モデルとして
シミュレーションします。たとえば、長い FFT の実行での ADC の SAR コントローラです。仕様やテストベンチの意図に残すこともでき、
答えには使った代役が出ます([代役](verification.md#stand-ins)を参照)。

## ターンを見る・止める

依頼はすぐに受け付けられ、*ターン* としてバックグラウンドで動きます。チャットには 1 手ずつ表示されます: エージェントの発言、各ツール呼び出しの開始と終了
(引数、理由、エラー)、作業している changeset。**Stop** を押すと、次の手の前でターンを終えます。すでに変更した内容は changeset に残ります。
ページを再読み込みしたり、別の画面で会話を開いたりすると、実行中のターンの表示が戻ります。サーバーの再起動で途切れたターンは *interrupted* と表示され、
自動で再実行はされません。

依頼した画面では、作業が進むのがそのまま見えます。エージェントが最初の変更を確定すると、その changeset のレビューが提案版で(一度だけ)開き、
図面は編集中のセルに追従して、育っていく全体を表示します。再読み込みするのは変更したセルのビューだけです。別のタブを選ぶか **Stop following** を押すと
追従は止まり(エージェントは作業を続けます)、**Back to latest** で再開します。レビューを閉じた場合は、それに従います。ほかの画面にも、エージェントが
作業中であることが表示されます。

ターンが changeset で作業している間は、ほかの誰もその changeset を変更できません。手動の編集、Undo、採用、破棄は拒否され(HTTP 409)、
レビューには誰が編集しているかと、そのための **Stop** が表示されます。MCP 経由の外部エージェントも、書き込んでいる間は同じロックを持ちます
(書き込みが 120 秒途絶えると解除)。外部エージェントを止めると、そのセッション(またはそのエージェント)のそれ以降の書き込みは拒否されます。設計は
[ライブ changeset](../design/live-changesets.md) を参照してください。

API: `POST /api/p/<project>/chat` は `{conversation, turn, state}` を返します(`?wait=true` ではターンの完了を待ってから応答し、同じ `client_id` を再送すると
受け付け済みのターンを返します)。`GET .../turns/<id>?after=<n>` は状態とインデックス `n` 以降のイベントを返します。`POST .../turns/<id>/stop`。
`POST .../changesets/<id>/writer/stop` は、changeset を編集している誰かを止めます。

<a id="mcp-external-llm-clients"></a>
## MCP(外部の LLM クライアント)

同じツールを MCP(Streamable HTTP)でも提供しているので、Claude Code や Claude Desktop など、普段使っている LLM ツールから使えます。
既定では無効です。サーバーを `--mcp`(または `UNDINE_MCP=1`)付きで起動します。`--llm-policy none` では使えません。Bearer トークンは
`<projects root>/mcp-token` に作られます。どのツールも `project` を受け取り、編集は changeset に入り、ツールが返したものはすべて
`<project>/llm/audit.jsonl` に記録されます(接続の種類は `mcp`。20000 文字を超える結果は、クライアントが多く求めたときだけ返るもので、先頭と長さとハッシュを記録します)。GUI は現在の選択をサーバーに知らせるので、`get_selection` で「このトランジスタ」が通じます。

```sh
UNDINE_MCP=1 ./scripts/restart.sh
claude mcp add --scope user --transport http undine http://127.0.0.1:8700/mcp \
  --header "Authorization: Bearer $(cat ~/undine-projects/mcp-token)"
```

<a id="several-agents-on-one-connection"></a>
### 1 つの接続で複数のエージェントが動くとき

複数のエージェントを同時に動かすクライアント(たとえば Claude Code のサブエージェント)は、それらの呼び出しをすべて 1 つの MCP 接続で
送ります。`mcp-stdio` の中継 1 つが MCP のセッション 1 つです。Undine は書き込み中の changeset をセッションごとに持つので、そのままでは
エージェントたちが 1 つを共有してしまいます。あるエージェントが開いた changeset が他のエージェントのものにもなり、その編集もそこに入ります。
そこで、各エージェントは自分の名前を `agent` として渡します。どのツールも受け取ります(`agent: "layout"`)。

- 同じ名前の呼び出しは、1 つのセッションの呼び出しと同じく、changeset とその書き込みロックを共有します。
- 他のエージェントが持っている changeset には書き込めません(下の、書き手は 1 人のロック)。拒否のメッセージは持ち主の名前を示し、
  `list_changesets` と `get_changeset` は、どれが自分の changeset か、それぞれを誰が書いているかを示します。
- 履歴は編集ごとにエージェントを記録し(`agent:claude-code/layout`)、レビューもそれを書き手として表示します。**停止** はそのエージェントだけを止めます。
- セッションが終わると(チャットを閉じると)、すべてのエージェントのロックが解放されます。

`agent` がなければ、その接続の呼び出しはすべて 1 つの changeset を共有します。シェルでは `--session NAME` がエージェント `NAME` になります(下記)。

<a id="checking-another-agents-changeset"></a>
### 他のエージェントの changeset を確かめる

他のエージェントの作業を検証するエージェント(レビュー役、別の目)は、その changeset の書き手にならずに、読み取りとチェックができます。
読み取りとチェックのツールが `changeset: cs-...` を受け付けます(`get_layout_info`、`get_device_geometry`、`render_layout`、
`get_drc_report`、`get_lvs_report`、`run_checks`、`check_specs`、`extract_parasitics`、`get_parasitics`、`run_simulation`、
`wait_for` とその他の読み取り)。

- 呼び出しはその changeset の作業コピーに対して動きます。書き込みのロックは取らず、自分の changeset(あれば)も自分のままです。
  `open_changeset id=...` は要りません。自分のセッションが以前にその changeset を開いていても、読み取りになります。自分のものとして
  その中で動くのは、書き手(書き込みのロックを持つもの)だけです。
- そこで始めたものは、書き手の実行と同じくその changeset に記録されます。`run_checks` の行、作業コピーでの抽出とシミュレーションです。
  書き手はそれを見られ、その間も編集を続けられます。チェックの後の編集で、そのチェックは「古い」になります。
- changeset のものは何も編集しません。`changeset` を渡した書き込みのツールは拒否され、`cancel_job` が止めるのは自分がそこで始めたジョブ
  (シミュレーション、チェック、抽出など、どのジョブでも)だけです。`batch` は他の changeset の読み取りを受け付けません。それだけで呼びます。
- 答えは読んだ changeset を示します。JSON の答えは先頭に `"changeset": "cs-..."`、テキストの答えは先頭に `changeset: cs-...` の行が
  付きます。次に呼ぶよう示すもの(`wait_for`、`get_parasitics`、`run_simulation job=`)にも `changeset` が付くので、それも渡します。

```sh
undine call run_checks changeset=cs-cd6857 --session verify
undine call check_specs lib=sar cell=sar_bootsw extracted:='["sar/sar_bootsw"]' changeset=cs-cd6857 --session verify
```

<a id="watching-an-external-agent-in-undine"></a>
### 外部エージェントの作業を Undine で見る

外部のエージェント(MCP、`undine call`、Python)の作業も、Undine にそのまま表示されます。ターミナルとブラウザを並べておけば、ブラウザが自分で追従します。

- **画面が自分で追従します。** エージェントが書き始めると、そのプロジェクトを開いている画面が、その changeset のレビューを提案版で開きます。
  図面はエージェントが変更したセルに追従し、そのセルだけを再読み込みします。
  - 自動で追従するのは、画面が空いているとき(レビューを開いておらず、未保存の編集もない)だけです。そうでなければ
    「*claude-desktop* が MCP 経由で「*タイトル*」を編集中」というバーと **作業を見る** を出します。
  - 追従の仕方はアプリ内のエージェントと同じです。別のタブを選ぶか **追従を停止** で止まり、**最新に戻る** で再開します。
    レビューを閉じると、その changeset はもう追従しません。
- **誰が編集しているか。** レビューには誰が編集しているかと **停止** が表示され、押すとそのセッションのそれ以降の書き込みを拒否します。
- **エージェントが書き終えると**、レビューは通常のものに戻ります。レビューを閉じていれば「*エージェント* が「*タイトル*」を終えました。
  レビューを待っています」というバーと **レビューする** が出て、**変更** の件数も増えます。
- **ブラウザのタブを二重に開きません。** ローカルの起動役(`mcp-stdio`)は、作業開始時に、そのプロジェクトを開いている Undine の画面がない
  ときだけレビューをブラウザで開きます。画面があれば追従をその画面に任せます(`GET /api/p/<project>/presence`)。
- **レビューの URL。** `undine call open_changeset` は、それを `review` として表示します。
`GET /api/p/<project>/live` は誰がどの changeset を編集しているかと、採用・破棄・取り消しの処理中の changeset とその進み具合(`closing`。
その `writer` は null)を、`GET .../changesets/<id>/activity?after=<gseq>` はある時点以降に確定したセルのビューを返します。

### Claude Desktop の拡張

Claude Desktop につなぐ一番簡単な方法です。拡張を作って Claude Desktop で開きます(またはその **Settings → Extensions** のページにドラッグします)。

```sh
pixi run mcpb      # -> dist/undine-<version>.mcpb
```

Claude Desktop は **Undine checkout**(undine-eda の場所。`pixi install` 済みであること。Windows では WSL の中のパス、例: `~/undine-eda`)と、
任意でサーバーと UI の URL を尋ねます。拡張は下で説明するローカルの起動役を動かします。macOS / Linux ではチェックアウトの pixi 環境から、
Windows では `wsl.exe` 経由で起動します(レビューは Windows のブラウザで開きます)。サーバーのコードは含まないので、チェックアウトを更新すれば
動くものも更新されます。バンドルは署名していません。

<a id="desktop-clients-the-local-launcher"></a>
### デスクトップのクライアント: ローカルの起動役

同じコンピューター上のチャットアプリ(Claude Desktop、Claude Code など)では、Undine を *ローカル*(stdio)の MCP サーバーとして登録します。
クライアントは `python -m undine mcp-stdio` を起動し、これが次のことを行います:

- Undine のサーバーが動いていれば再利用し(既定は `http://127.0.0.1:8700`、または `--url` / `$UNDINE_URL`)、なければ MCP を有効にして
  バックグラウンドで起動します(`scripts/restart.sh` と同じく `~/.undine/env` を読み込み、ログは `~/.undine/serve.log`)。サーバーはチャットが終わっても動き続けるので、
  提案は Undine に残り、あとでレビュー、採用、続きの作業ができます。
- サーバーは、`pixi run` と同じく自分の環境のツールで起動します(`UNDINE_TOOLS`、`SPICE_LIB_DIR`。`~/.undine/env` で設定したものはそのまま)。
  `~/undine-tools` にある古い ngspice が環境のものの代わりに使われることはありません。ngspice のない環境(ふつうの venv)や
  システムの Python はツールの場所にはせず、そのサーバーはほかのサーバーと同じく `~/undine-tools` と `PATH` から探します。
- 会話のツール呼び出しを、Bearer トークン付きでサーバーに中継します(トークンを手でコピーする必要はありません)。
- 作業が始まったときに一度だけ、changeset のレビューをブラウザで開きます(UI が別の場所にある場合は `--ui-url`。例: Vite の開発サーバー。
  開かないようにするには `--no-open`。開くコマンドは `$UNDINE_OPEN` で指定でき、`{url}` が置き換わります)。もう一度開くための
  `open_in_undine` ツールも追加します。
- チャットを閉じると MCP のセッションを終了するので、書き込んでいた changeset はすぐに解放されます(そうでなければ、ロックは 120 秒後に切れます)。

MCP を有効にせずに動いているサーバーは再起動しません。クライアントには `UNDINE_MCP=1 ./scripts/restart.sh` で再起動するよう伝えます。
あとのチャットからは、`list_changesets` と、`id` を指定した `open_changeset` で提案の続きを作れます。

```sh
claude mcp add --scope user undine -- /path/to/undine-eda/.pixi/envs/default/bin/python -m undine mcp-stdio   # Claude Code
```

`--scope user` を付けると、どのフォルダからでも使えるように登録します。付けないと、コマンドを実行した git リポジトリ(git の外なら、そのフォルダ)だけの登録になります。
確かめ方を含めた手順は [AI エージェントをつなぐ](../getting-started/connect-ai.md#claude-code) にあります。

Claude Desktop(`claude_desktop_config.json`)。Windows でサーバーが WSL の中にある場合は、`wsl.exe` 経由で起動します:

```json
{"mcpServers": {"undine": {"command": "wsl.exe", "args": ["-e", "bash", "-lc",
  "cd ~/undine-eda/server && ../.pixi/envs/default/bin/python -m undine mcp-stdio"]}}}
```

WSL では、レビューは Windows のブラウザで開きます。

<a id="undine-on-another-machine"></a>
#### Undine が別のマシンにある場合

Undine が(PDK のある)サーバーで動き、チャットアプリが手元のコンピューターにある場合は、`--ssh HOST` を付けます(`$UNDINE_SSH`
でも、拡張なら **SSH host** でも指定できます)。`HOST` は `user@host` か `~/.ssh/config` の別名で、踏み台、ポート、鍵はそこから
決まります。起動役は次のことを行います:

- 手元のポート(`127.0.0.1`。空いていればサーバーと同じ番号、なければ空いている番号)を、SSH でサーバーに転送します。
  `--url` は `HOST` から見たサーバーです(既定は `http://127.0.0.1:8700`)。
- トークンを `HOST` 上で読み(`ssh HOST cat <プロジェクトのルート>/mcp-token`)、メモリにだけ保持します。
- レビューは転送したポート経由でブラウザに開きます。転送が切れたら張り直します。
- 向こうのサーバーは起動しません。`HOST` 上で `UNDINE_MCP=1 ./scripts/restart.sh` で起動しておいてください。

ssh は端末なしで動く(入力はチャットに使われる)ので、パスフレーズのない鍵か ssh-agent と、登録済みのホスト鍵が必要です。
先に一度、端末で `ssh HOST true` を実行してください。起動役そのものは、手元の Undine のチェックアウトから動きます。

```sh
claude mcp add --scope user undine -- ~/undine-eda/.pixi/envs/default/bin/python -m undine mcp-stdio --ssh me@eda-server
```

SSH を使わない場合(VPN や同じネットワーク)は、`--url` でサーバーを指し、トークンを `$UNDINE_MCP_TOKEN` で渡します。
`undine call` と Python のクライアントも、同じく `--ssh` / `ssh=` を受け付けます(下を参照)。

ブラウザ版のチャット(リモートコネクター)は、あなたのコンピューターからではなく、提供元のクラウドから
サーバーに接続します。そのためには外から届く、認証付きのエンドポイントが必要で、ここでは扱っていません。

アプリ内のエージェントとの違いに注意してください。MCP では、データの送り先を決めるのは外部のクライアントです(接続を 1 つに限る保証は、
アプリ内のエージェントにだけ当てはまります)。サーバーから出ていくのはツールが返したものだけで、それは記録されます。

<a id="scripts-and-the-shell"></a>
## スクリプトとシェル

MCP クライアントがなくても、シェルと Python から同じツールを使えます。Claude Code や Codex のようなコーディングエージェントはシェル経由で使え、
人が変更をスクリプトにすることもできます。MCP を有効にしたサーバーが動いている必要があります。

```sh
undine tools                                   # ツールの一覧。`undine tools write_rtl` で 1 つの引数を表示
export UNDINE_PROJECT=demo
undine call get_netlist lib=mylib cell=inv
undine call open_changeset title="Wider pull-down" reason="fall time misses s1"
undine call set_instance_params lib=mylib cell=inv instance=M2 params:='{"W": "1.5"}' reason="faster fall"
undine call write_rtl lib=mylib cell=counter text=@counter.sv reason="add a synchronous clear"
undine session end
```

- **引数。** `key=value` は文字列、`key:=json` は任意の JSON の値、`key=@path` はファイルの中身です。
  `key:=@path` はファイルに書いた JSON の値、`--json @path`(標準入力からは `--json -`)は引数全部を 1 つのオブジェクトで渡します。
  `batch` の ops のような長いリストに使います。はい / いいえの引数は `key=true` / `key=false` でも渡せます(`move=false` は false)。
- **出力。** 結果は JSON で表示します。ツールが拒否すると終了コード 1(理由は標準エラー)、Undine につながらないと 2 です。
- **リクエスト ID。** 呼び出しはまず標準エラーにリクエスト ID を表示します(`undine: request id ...`)。呼び出しが途中で切られたとき
  (実行しているシェルの時間切れなど)は、`--request-id` を付けてもう一度送ります。すでに済んだ書き込みは、二度実行せずに最初の結果を返します。
- **サーバー。** `--url` でサーバーを選び(既定は `$UNDINE_URL` か `http://127.0.0.1:8700`)、`--start` で MCP を有効にして起動します。
  `--ssh HOST`(または `$UNDINE_SSH`)で、別のマシンの Undine に [起動役と同じように](#undine-on-another-machine) つなぎます。
  呼び出しのたびに、その間だけポートを転送し、トークンを `HOST` 上で読みます。セッションはホストごとに保ちます。出力のレビュー URL は
  `HOST` から見たものです。
- **セッション。** シェルは `--session` の名前ごとに MCP のセッションを呼び出しの間で保ちます(`~/.undine/cli-sessions.json`、
  または `$UNDINE_CLI_SESSIONS`)。そのため、ある呼び出しで開いた変更セットは、次の呼び出しでもあなたのものです。`undine session end`
  で手放しても、変更セットはレビューのために開いたまま残ります。
- **名前付きのセッションはエージェント。** `--session NAME` は、エージェント `NAME` としてツールを呼びます(`agent` を渡さない
  呼び出しすべてに `agent=NAME`)。履歴(`agent:undine-cli/NAME`)、レビュー、書き込みのロックはその名前で示され、名前付きの
  セッション 2 つは、1 つのセッションファイルの中でも 2 人の書き手です。`--session` がなければ、これまでどおり名前なしです。
  名前は英数字、`.`、`_`、`-` の 64 文字までで、それ以外の名前はセッションの名前としてだけ使います。各呼び出しは stderr に誰として
  動くかを示し(`undine: request id ... (agent NAME)`)、`open_changeset` と `list_changesets` は `you` を返します。並んで動く
  エージェントは、それぞれ自分の `--session`(と補助スクリプト)を使ってください。

Python では、ツールがメソッドになり、結果は解析済みの値で返ります。

```python
from undine.client import Undine, ToolError        # undine.agents.client でも同じ

with Undine(project="demo", agent="layout-1") as u:   # agent: 自分の名前(シェルの --session NAME と同じ)
    cs = u.open_changeset(title="Wider pull-down", reason="fall time misses s1")
    for m in ("M2", "M4"):
        u.set_instance_params(lib="mylib", cell="inv", instance=m, params={"W": "1.5"}, reason="faster fall")
    print(u.run_checks(), u.review_url(cs["id"]))
```

`agent=` は、シェルの `--session NAME` が与える名前です。履歴、レビュー、書き込みのロックはこの名前で示されます。`session=` は別のもので、
続けたい MCP セッションの ID(別のクライアントの `u.session`)です。名前を渡すと、そのことを添えて拒否します。

クライアントは標準ライブラリだけで動き、設計の状態は持ちません。ほかの MCP クライアントと同じ決まりに従います。

- 編集は、人がレビューして反映する変更セットに入ります。
- ツールが返したものは、クライアント名(`undine-cli`、`undine-python`)付きで記録されます。

柔軟さは、サーバーの中でコードを実行することではなく、型の決まったツールをスクリプトで組み合わせることで得ます。

<a id="long-results"></a>
### 長い結果

ツールの結果は長くなることがあります。100 素子のセルのネットリスト、batch の結果、多くの信号を含むシミュレーションなどです。
読み手ごとに使える量を返し、収まらない結果は途中で切らずに中を縮めるので、正しい JSON のままです。

- 結果の多くを占める部分から縮め、大きな部分がいくつもあれば(`batch` の複数のネットリストなど)同じくらいずつ縮めます。
  リストや項目の多いオブジェクト(名前ごとのインスタンスなど)は先頭の項目を、文字列は先頭を残します。縮めた場所には
  `"…": "76 more (116 in all)"` のように、そのことを書きます。
- 結果に `_truncated` が付きます。元の大きさ、上限、縮めたもの(`"instances": "40 of 116"`)、残りの求め方です。
- 残りはツールの絞り込みとページで求めます。`get_netlist` の `offset` / `limit`、`instances`、`nets`、`get_intent` の `ids`、`kinds`、
  `get_design_context` の `objects`(最初に並びます)です。

| 読み手 | 1 つの結果の文字数 |
|---|---|
| アプリ内のアシスタント | 9000。結果は会話に残るため |
| MCP クライアント | 20000。クライアントが `_meta: {"undine/max_chars": N}` で求めればその数(0 で全部) |
| `undine call` | サーバーからは全部を受け取り、表示は最大 25000(`--max-chars N` か `$UNDINE_MAX_CHARS`。0 で全部。ファイルや `jq` に渡すとき) |
| Python | 全部(`Undine(max_chars=N)` で少なくできます) |

シェルが受け取るより少なく表示するのは、エージェントが自分のシェルで出力を読み、そのシェルが長い出力を切るためです(Claude Code では
約 30000 文字)。スクリプトには全部が必要です。

### 人やジョブを待つ

`wait_for(events, timeout_s)` は、何かが起きるまで待ち、起きたことを返します。結果は文字で返るので、どのクライアント(MCP、`undine call`、Python)でも
使えます。MCP の通知は、多くのクライアントが処理しないためです。

- `changeset`: 人がエージェントの変更セットを反映または破棄したとき。
- `selection`: Undine で何かを選択したとき(次に見てほしいものを指すときなど)。
- `job:<id>`: ジョブが終わったとき(LibreLane の実行など)。
- `design:<lib>/<cell>`: 本物の設計でそのセルが変わったとき。

最初に起きた出来事を返します。何も起きなければ期限切れを返します(既定 60 秒、最大 300 秒。`job:<id>` では最大 1800 秒で、
期限切れの答えはジョブがまだ待っているか走っているかを示します)。終わったシミュレーションには、その結果の読み方が付きます。

### 複数の編集を 1 歩で、安全な再送

- **`batch`** は、複数のツール呼び出しを変更セットの中で 1 歩として実行します(`ops=[{tool, args}, ...]`)。全部か無しかです。
  - 1 つでも失敗すると、作業用コピーはその歩の前の状態に戻り、エラーはどの操作かを示します。
  - レビューの履歴では 1 つの操作(1 つの復元点)になります。
  - 編集の合間に `get_netlist` などの読み取りを挟めます。
  - 2000 操作まで実行できます。40 を超えると、応答には最初の 20 の結果、残りの結果の警告(操作の番号付き、`warnings`)、セルと操作ごとに
    数えた変更を返します。
- **`dry_run: true`** は、同じように実行して、各結果と変わる内容(セル、ビュー、効果)を返し、何も残しません。変更する前に試すのに使います。
- **要求 ID。** 書き込み系のツールはどれも `request_id` を受け取ります。同じ ID でもう一度呼ぶと、二度実行せずに最初の結果
  (再送への応答であることを示す印付き)を返します。ID はプロジェクトごとに保存し、サーバーを再起動しても有効です。
  ID は `agent` ごとでもあり、1 つの接続の 2 つのエージェントが同じ ID を選んでも、別々の呼び出しになります。
  - そのため、呼び出しが通ったか分からないとき(タイムアウト、接続断)は、そのまま送り直せば済みます。
  - Python クライアントと `undine call` は、すべての呼び出しに ID を付け、応答が失われたら送り直します。`--request-id` で
    手で指定することもできます(スクリプトを安全にやり直すときなど)。

変更セットを追っている画面には、実行中の歩は見えません。歩を元に戻した後も通し番号は先へ進むので、見落としも二重表示もありません。

## エージェント向けの手順書(スキル)

Undine は、エージェント向けの手順書を [Agent Skill](https://agentskills.io) の形で同梱しています。短い `SKILL.md` に作業の流れ
(読む、変更セットを開く、編集、検証、引き渡し)と決まりを書きます。作業ごとの参照(接続、回路図、レイアウト、意図、検証、
RTL / LibreLane)は別のファイルにあり、エージェントは必要なものだけを読みます。

- **MCP クライアント**には資料(resources)として渡します(`undine://skills/undine/SKILL.md` とその参照)。サーバーの指示文も
  そこを案内します。`mcp-stdio` は、サーバーが動いていなくても手順書を返します。
- **スキルのフォルダを持つエージェント**(Claude Code など)には、`undine skills install` で `~/.claude/skills/undine` に
  コピーします(別のフォルダは `--dest`)。
- **シェルからは** `undine skills` で一覧、`undine skills show layout` で 1 つを表示します。

ファイルは `server/undine/data/skills/undine/` にあります。テストで、書かれているツールが実在すること、リンクが切れていないことを
確かめています。

## 画像

レイアウトのビューでは、チャットに **Image** ボタンがあります。選択範囲(何も選んでいなければ見えているレイアウト)を最大 1024 px に縮小して取り込み、
送信前に取り除けるサムネイルとして表示します(既定ではオフ)。画像はそのメッセージと一緒にだけ送られます。監査ログにはハッシュを記録し、
ファイルは `<project>/llm/images/` に保存するので、何がマシンの外に出たかを確認できます。EDA-server の接続では、モデルが画像を受け付ける必要があります。

外部のエージェント(MCP、`undine call`、Python)は、自分で画像を求められます。画像は見るため、数値は証拠なので、どの画像にも、
それが示す数値が付きます。

- **`render_schematic`**: エディタと同じ描き方の回路図と、その数(インスタンス、配線など)です。`around`(インスタンス名)か `box` で、
  大きな回路図の一部を近づけて描きます。描いた範囲も返します。
- **`render_layout`**: セル全体か µm で指定した範囲のレイアウトで、レイヤーを絞ることもできます。PDK の色と縮尺の目盛りで描き、
  描いた範囲と 1 ピクセルあたりの µm も返します。`markers: true`(またはルールのリスト)で、セルの最新の DRC の違反をルールと
  チェッカーごとの色で重ねて描き、凡例を返します。同じマーカーを µm でルールごとに返すのが `get_drc_report` です。
- **`plot_waveform`**: テストベンチの直近の完了したシミュレーションです。AC は対数周波数で利得と位相を描きます。各波形の色と範囲も返します。
  信号は `run_simulation` と同じ名前(`out`、`x1.b9`)で指定します。`tstart` / `tstop` で、1 µs の実行のうち数 ns のような一部を描きます。
  長い実行では区間ごとの最小と最大を残すので、細いスパイクも見えます。

描画はサーバー側で、レイアウトのタイルと同じ KLayout が行います。MCP では画像ブロックとして返り、監査ログには中身を写さず枚数だけを
残します。`undine call` はファイルに書き出し(`--out FILE.png`。`--out` がフォルダならその中の新しいファイル、指定がなければ `--out-dir`、
`$UNDINE_OUT_DIR`、`$UNDINE_CLI_SESSIONS` があればそのフォルダ、なければカレントフォルダの新しいファイル)、そのパスを表示します。
Python クライアントは PNG のバイト列を `images` として返します。アプリ内のアシスタントは文字しか受け取れないので、これらのツールは渡しません。

# 変更セット (changeset)

レビューでき、取り消せる変更の単位です。

エージェントや人が変更を提案するときは、changeset を開きます。changeset はプロジェクトの git ブランチ `undine/<project>/<id>` と、
その作業コピーです。人が採用(Adopt)するまで、実際の設計は変わりません。

```sh
H='content-type: application/json'; A='X-Undine-Actor: agent:optimizer'
curl -XPOST $URL/api/p/demo/changesets -H "$H" -H "$A" -d '{"title":"Widen NMOS","reason":"faster falling edge"}'
#  -> {"id": "cs-4ce078", "preview": "demo~cs-4ce078", "git": {"branch": "undine/demo/cs-4ce078", ...}, "git_setup": false, ...}
# edit the working copy with the normal APIs, using the preview as the project name:
curl -XPOST $URL/api/p/demo~cs-4ce078/l/mylib/c/inv/schematic/edit -H "$H" -H "$A" \
     -d '{"op":"set_props","kind":"i","id":"M2","props":{"W":"1.5"},"reason":"wider pull-down"}'
curl -XPOST $URL/api/p/demo/changesets/cs-4ce078/verify -d '{}'   # needed DRC/LVS checks, baseline vs proposal
curl $URL/api/p/demo/changesets/cs-4ce078                         # what changed, by whom and why, plus checks
curl $URL/api/p/demo/changesets/cs-4ce078/diff                    # its files, from where it started to now
curl -XPOST $URL/api/p/demo/changesets/cs-4ce078/apply -d '{}'    # human: merge it into the real design (all-or-nothing)
curl -XPOST $URL/api/p/demo/changesets/cs-4ce078/revert -d '{}'   # later: take it back (refused if later edits conflict)
```

作業コピーは、プレビュー名(`demo~cs-4ce078`)をプロジェクト名として、通常の API で編集します。`verify` は必要な DRC/LVS を元の設計と提案の両方で実行し、
`diff` は提案の起点から今までのファイルの差分を返します。`apply` は人が実際の設計にマージする操作(全か無か)、`revert` はあとから取り消す操作です
(その後の編集と衝突する場合は拒否されます)。

UI には **Changes** ボタンがあります(レビュー、チェックの実行、プレビューを開く、採用、破棄、取り消し)。採用では、提案のブランチを実際の設計に
オブジェクト単位でマージします(Undine のファイルを git でマージするときと同じ[意味的なマージ](../design/merge.md)です)。そのため、その間に実際の設計で
行われた無関係な編集とは衝突しません。両方で同じオブジェクトを違うように変えていれば衝突し、その場合は何も書き込みません。
レイアウトの編集も記録されます(持ち運べる効果、再起動後も残る Undo、未保存の編集は再起動後に再適用)。`server/undine/store/oplog.py` と
`server/undine/store/changeset.py`、設計の[git ブランチ上の changeset](../design/changeset-branches.md)を参照してください。

<a id="a-changeset-is-a-git-branch"></a>
## changeset は git のブランチ

- **最初の changeset でプロジェクトを git で管理します。** changeset には、プロジェクトが git のリポジトリにあることが必要です。どのリポジトリにも
  入っていないプロジェクトで changeset を開くと、[履歴パネル](history.md)の **git をセットアップ** と同じこと(`git init`、属性、ドライバ、フック)を行い、
  続けてプロジェクトのファイルをそのまま、あなたのブランチの最初のコミットにします(`Project <project>: its files when Undine set up its repository`。
  下の起点と同じく、Undine 自身の出力と changeset の記録は含まず、まだ保存していないレイアウトの編集は起点と同じくログにあるまま含みます)。
  後で採用したものは、その上にコミットされます。パネルにはそのことが表示され、
  エージェントには `open_changeset` の結果で伝えられます(`"git_setup": true`、`"first_commit"`)。まだコミットのないリポジトリで、Undine がその場で
  作ったものではないもの(自分で `git init` した、または以前の Undine が設定した)には、開いてもコミットしません。そこで採用するとマージは未コミットの
  まま残り、レビューはそのときリポジトリにまだコミットがなかったことを示し、採用時のメッセージが履歴パネルの **最初のコミットを作成** へ
  案内します。
  Undine 用に設定されていないリポジトリ(たとえば git で管理しているホームディレクトリ)の中にあるプロジェクトでは、開くのを拒否し、
  どうすればよいかを示します: リポジトリを設定する(履歴パネルの **セットアップ**、または `undine git-setup <project>`。既定ではない
  プロジェクトのルートでは、メッセージは `--root` を付けたコマンドも示します)か、プロジェクトをそこから移します。新しい変更セットの
  ダイアログは、そのことを UI の言語で、リポジトリの場所とプロジェクトの名前とともに表示します。誰も Undine 用に設定していないリポジトリに、
  Undine がブランチや設定を書き込むことはありません。
- **起点。** 開くと、プロジェクトのファイルをそのままコミットにします。これが *起点(base)* です。未コミットの編集や新しいファイルは含み、
  Undine 自身の出力(`runs/`、`tapeout/`、`llm/`、`.undine/`)と changeset の記録(`changesets/`)は含みません。保存していないレイアウトの編集も
  含まないので、先に保存してください。あなたのブランチ、インデックス、作業ツリーには触れません。
- **作業コピーが持てないライブラリ。** worktree が持てるのは git が保存するものだけで、その中のシンボリックリンクは作業コピーの場所から
  たどられます。そのため、プロジェクト自身のライブラリのフォルダ、その上、その中、またはそれらのリンクの先に次のどれかがあると、開くのを
  拒否します。新しい変更セットのダイアログは、ライブラリの名前とパス、どうすればよいかを UI の言語で表示します(HTTP では、コード
  `unsupported_library` の 400 です)。これはほかの何よりも先に確かめるので、拒否された場合、どのリポジトリにも入っていないプロジェクトが
  git で管理されることはありません。下に書いた直し方のほかに、リンクの代わりにファイルそのものをプロジェクトに置くか、ライブラリを
  [依存関係](libraries.md)(`project.json` の `"git"` のライブラリ)にすれば、いつでも開けます。直したら、もう一度開いてください。
  プロジェクトの中の、git が保存するほかの場所を指す相対リンクは問題ありません。
    - プロジェクトの外か、存在しない場所を指すシンボリックリンク: 作業コピーはリンクをそのまま持ち、リンクを通って実際のファイルに書き込むか、
      何も見つけられません。
    - 絶対パスで書いたシンボリックリンク(プロジェクトの中を指していても)や、途中でプロジェクトの外へ上がる相対リンク(`../../...`):
      作業コピーからは実際のファイルか、別の場所を指します。プロジェクトの中を指す相対リンク(`ln -sr`)にしてください。
    - プロジェクトのリポジトリが保存しないシンボリックリンク、またはそのリンク先(`.gitignore` が外している、または `llm/` のような
      Undine 自身の出力): 作業コピーにはそれがありません。git に保存させてください。
    - それ自身が git リポジトリであるもの(クローンやサブモジュール): git はその参照しか持たず、作業コピーではライブラリが空になります。
      依存関係にするか、その `.git` をプロジェクトの外に移してください。

  `project.json` で絶対パス(または `~/...`)で指定したライブラリはプロジェクトの中にありません。作業コピーはそれを元の場所から読み、
  依存関係と同じく読み取り専用にするので、提案がそこに書き込むことはありません。編集はプロジェクト自身から行ってください。
- **編集する場所。** ブランチ `undine/<project>/<id>` は起点から始まり、その git worktree `<projects root>/.changesets/<project>/<id>/work` が
  作業コピー(プロジェクト `<project>~<id>`)です。起点もその隣に読み取り専用でチェックアウトされます(`.../base`。チェックで比べる元の設計
  `<project>~<id>~base`)。`.changesets/` フォルダは自分自身を無視させます: Undine はそこに `*` だけの `.gitignore` がなければ書き
  (そのまま残します)、プロジェクトのルートを管理しているリポジトリがどれであっても、作業コピーやその隣に置くものは `git status` に出ず、
  `git add -A` もそれに触れません。最後の作業コピーがなくなった後も同じです。プロジェクトのルートがプロジェクト自身のリポジトリの中にある
  ときは、作業コピーがある間、`.git/info/exclude` でもフォルダを除外します。
- **コミット。** 作業コピーは、エージェントのターンや MCP セッションが終わったとき、チェックを実行する前、採用・破棄の前に、ブランチにコミットされます
  (開いているレイアウトは先に保存します)。コミットのメッセージには、タイトル、誰が、どのターンで、前のコミット以降のどの操作を行ったかが入ります。
  ブランチは普通の git のブランチです: `git log undine/demo/cs-4ce078`。
- **レビューでは**、ブランチ、起点(`起点 423b409`。ツールチップに完全なコミット)、コミット数が表示されます。プレビューの[履歴パネル](history.md)は、
  ブランチと起点を示し、レビューとプロジェクトの履歴へ案内します。
- **閉じた後**(採用または破棄)は worktree を削除し、ブランチを `refs/undine/changesets/<project>/<id>` として残します。そのため、コミットは証拠と
  取り消しのために残ります(`git log refs/undine/changesets/demo/cs-4ce078`)。レビューにはその参照が表示されます。

<a id="review-screen"></a>
## レビュー画面

Changes の一覧で changeset を選ぶと **レビュー** が開きます。左に Agent(設計エージェント)とセル一覧、中央に図面、右に changeset が同時に表示されるので、
パネルを切り替えずに、提案を見比べ、相談し、判断できます。

- **変更したオブジェクト**(*対象ごと*)。操作ログをオブジェクトごとにまとめて、`R1  value: 1k → 12k` と理由を表示します。同じオブジェクトを何度編集しても、
  最初の値と最後の値だけを表示します(追加して削除したオブジェクトや、元に戻した値は表示しません)。元の操作は *操作ログ* にあります。
- **変更されたファイル**(*ファイルごと*)。ブランチの[意味的な差分](history.md)を、履歴パネルと同じくセルとビューごとに表示します。開いている間は
  起点から作業コピーまで、閉じた後は最後のコミットまでの差分です。操作として記録されていない変更(作ったライブラリ、取り込んだレイアウト、
  Undine の外で変えたファイル)も表示するので、採用でマージされる内容そのものです。作業コピーが進むと読み直し、隣のボタンで手動でも読み直せます。
  開くボタンは、作業コピー(採用後は設計)のビューを開きます。記録した操作もコミットもまだない間は、レビューがこの差分を自分で読むので、
  *ファイルごと* にだけ出る変更でも **Adopt** と **Run needed checks** を使えます。一度に読むのは 1 つだけです: 取り込んだ大きなレイアウトの
  差分には数秒かかることがあり、レビューは更新のたびにやり直さず、読み終わるのを待ちます。
- **Diff。** 切り替えの 3 つ目のモードでは、提案版の上に、確定版との違いを重ねて描きます。追加は緑、削除は赤、変更は黄です。回路図ではインスタンスごと
  (ID で比較。移動、反転、別のシンボル、別のパラメータは変更として扱い、削除したインスタンスは元の位置に破線で描きます)と配線ごと(端点で比較)に、
  レイアウトではレイヤーごとに平坦化した形状の差(`GET .../layout/<cell>/diff/<other-project>`)を表示します。そのため、PCell を差し替えても
  実際に形が変わった部分だけが光ります。差が大きい場合は 4000 ポリゴンで打ち切ります。
- **追従した変更。** 回路図の変更に追従したレイアウトの変更(*sync layout* / *generate*)は、原因になった回路図の変更の下にぶら下がります。
  たとえば `M2  W: 1 → 2` の下に `Follows in the layout: M2  nfet_w1 → nfet_w2` が出ます。このつながりは操作ログから導くもので
  (前回レイアウトが追従した後の、そのデバイスに対する回路図の編集。API では操作の `causes`)、古い changeset にも当てはまります。
  手で描いた配線のように、回路図の編集で説明できないレイアウトの変更は最上位に残ります。
- **Confirmed / Proposal。** 切り替えると、開いているビューを実際の設計と作業コピーのどちらで表示するかが変わります。位置と倍率は保たれます
  (エージェントが作業コピーを編集した後も同じです)。Diff と確定版は今の設計を表示します。提案を開いた後に設計が進んでいることもあります。
  *ファイルごと* は提案の起点と比べます。
- **変更したオブジェクトをクリック** すると、そのビューを開き、回路図とレイアウトでハイライトします(クロスプローブ)。追加したオブジェクトでは提案版に、
  削除したオブジェクトでは確定版に切り替わります。
- **Adopt(採用)と Discard(破棄)**(採用後は Revert)は列の一番上、Confirmed / Proposal の切り替えの上にあり、ふだんの判断にスクロールは要りません。その下の一行が、変更で悪化したチェックがあれば知らせます。チェック、その鮮度、Run needed checks は変更内容の下に続きます。Adopt または Discard の後は図面が実際の設計に戻り、列には保存した証拠が表示され続けます。
- **Request changes**(修正を依頼)を押すと、提案版を開いて Agent の入力欄にカーソルを置きます。直してほしい点を書くと、エージェントは同じ提案の続きとして作業します(下記)。
  git のブランチにある changeset で表示され、[以前の changeset](#older-changesets) には表示されません。**Adopt** は HTTP API の `apply` に当たります。

## エージェントで提案の続きを作る

レビュー中(またはプレビューを開いているとき)は、エージェントは新しい changeset を開かず、その changeset の続きとして作業します。
各ターンの前に、前回のターン以降に changeset に加わった変更と、それを誰が行ったかがエージェントに伝えられます。プレビューで図形を動かしたり値を入力したり
といった人の変更は、その理由とともに人の変更として伝えられ、エージェントはそれを残して作業するよう指示されます。新しい変更がなければ、そのように伝えます。
エージェントのチェックはまだ有効な結果を使い回すので(下記)、編集が影響するチェックだけが再実行されます。会話は実際のプロジェクトの側に保存されるので、
changeset を採用・破棄しても残ります。閉じた changeset の続きを作ることはできません。

## エージェントにできること

エージェントのモードは 1 つです。質問には答え、何かを変えたり作ったりするよう頼まれると、changeset を開いて(またはレビュー中の changeset の続きとして)
その作業コピーを編集します。セルの作成(`create_cell`: 回路図、シンボル、レイアウト)、配置できるシンボルとそのピンの検索(`list_symbols`)、
配置、パラメータ設定、配線、移動、削除、レイアウトの同期、図形の描画、DRC / LVS とシミュレーションの実行ができます。changeset の採用はできず、
プロジェクトやライブラリの作成、PDK の変更、依存関係の追加、依存関係のコードの信頼、GDS / OASIS の取り込み、読み取り専用ライブラリの編集も
できません。これらを頼まれると、できないことと、人がどこで行うかを伝えます。

**changeset での信頼。** changeset の作業コピーでのシミュレーション、LVS、RTL の実行も、プロジェクトでのものと同じく
[信頼の規則](libraries.ja.md#trusting-a-dependencys-code)で確かめます: `.control` ブロックや PDK の外のファイルパスを持つ依存関係の
セルは、人がその依存関係を信頼するまで拒否されます。作業コピーはプロジェクトの今の信頼だけを数えるので、プロジェクトで
信頼すれば(`lib trust`、またはプロジェクトのパネルの **信頼...**)、また信頼を取り消せば、開いているすべての changeset にすぐ届きます。信頼はプロジェクト
でだけ与えられ、changeset のプレビューでは拒否されます。エージェントはそのような拒否を伝えてあなたに尋ね、自分では何も信頼
できません。

新しいセルは操作として記録され(`create_cell`。回路図やシンボルのファイルは効果 `v`、レイアウトのセルは `c`)、レビューでは追加として表示されます
(`+ schematic ota`、`+ cell ota`)。changeset を採用すると実際のプロジェクトに作られ(その間に同じ名前のファイルができていれば、2 つを
オブジェクト単位でマージし、両方が違うように定めているものは衝突になります)、changeset を取り消してもそのまま残ります。シンボルのピンは
回路図のポートから作られるので、シンボルは回路図にポートができてから作ります。

<a id="timeline-and-restoring-a-checkpoint"></a>
## タイムラインとチェックポイントの復元

**Timeline**(開いている changeset で *By object* の隣)は、提案の中で行われたことを順番に並べます。エージェントへの依頼ごと(依頼の文面付き)、
または作業した人ごとにまとまり、Undo、Redo、以前の復元も含みます。効果がなくなった手順は取り消し線で表示します。

手順の間にある **Restore to here** を押すと、作業コピーをその時点の状態に戻します(一番上なら、開いたときの状態)。今効いている操作を Undo するのではなく、
ログからその状態を組み立て直すので、その時点より前に追加し、その後に Undo したものも戻ります。その時点より後に作ったセルは、変更されておらず、
残る設計から使われていなければ削除します。提案が触るすべてのライブラリに対して全か無かで行い(どこかで失敗すれば、作業コピーのファイルとログを元に戻し、
何も記録しません)、`restore` の手順として記録します。レビュー、Undo、採用は復元後の状態に従い、もっと後の時点にもう一度復元することもできます。
アプリ内や外部のエージェントが書き込んでいる間は拒否します。エージェントの次のターンには、提案が復元されたことと、何が取り消されたかが伝えられます。

`GET /api/p/<project>/changesets/<id>/timeline`、`POST .../restore`(`{"to": <gseq>}`)。

## チェック結果と鮮度

Changes パネルは、DRC または LVS に対応する変更されたセルごとに、元の設計と提案を比べます。結果には、成否と鮮度の両方が含まれます:
**current**(最新)、**outdated**(古い)、**freshness unknown**(不明)、**not run**(未実行)。古い結果は以前の成否を保ちますが、
最新の合格としては表示せず、悪化や改善の判定にも使いません。パネルは開いている間更新されるので、別のクライアントがプレビューで編集すると、
結果が古いと表示されることがあります。
チェッカーごとに行があります: PDK の KLayout デッキの DRC と、sky130 では Magic の DRC(*DRC (Magic)*)、LVS、そしてその LVS から取る ERC です。
ERC の指摘(他のネットのソース / ドレインに接するボディタップ)は、違反ではなく警告としてその下に並びます([検証](verification.md#the-checks-of-a-changeset))。

**Run needed checks** は、使える最新のジョブがないチェックだけを実行します: 未実行のチェック、入力が古いか不明なもの、失敗・中止・中断したジョブ。
入力が最新の完了ジョブは、DRC 違反や LVS の不一致を報告していても使い回します。設計を直してから、もう一度チェックしてください。
同じ入力で実行中のジョブも使い回します。鮮度の判定には、ほかの検証ジョブと同じく、設計、PDK、ルールデッキ、ツールの入力ハッシュを使います。
[ジョブの来歴](../reference/data.md#job-provenance)を参照してください。

作業コピーまたは元の設計でジョブが待機中・実行中の間は、採用と破棄はできません。ツールが書き込み中の結果を消したり、中途半端に保存したりしないためです。
サーバーを再起動してもシミュレーションは続きます(次のサーバーが引き継ぎます。[サーバーの再起動](../reference/cli.ja.md#restarting-the-server))。
引き継がれたシミュレーションも、ほかの実行中のジョブと同じく終わるまで採用と破棄を止め、終わった後はほかの実行と同じように証拠に保存されます。
前のサーバーで終わらなかったそれ以外のチェック(DRC、LVS、抽出)と、どのサーバーも終わらせられないシミュレーションは **interrupted**(中断)と
表示され、**Run needed checks** でやり直せます。

<a id="adopting-the-merge"></a>
## 採用: マージ

**Adopt**(採用、`POST .../apply`)は、作業コピーをコミットし(これが先端、tip です)、証拠を保存してから(下記)、ブランチが変えた内容を設計に
マージします。

1. **ブランチが変えたファイル**(起点と先端の間で違うもの)を、起点の内容、今の設計の内容、提案の内容の 3 つでマージします。ビューごとのマージ
   (回路図、シンボル、レイアウト、netlist、設計の意図。それ以外のファイルは行単位)を使います。設計側で変わっていないファイルは提案の内容になり、
   設計側でも変わったファイルはオブジェクト単位でまとめます。違うオブジェクトへの変更は両方とも入ります。マージが触るライブラリに、設計側で
   保存していない編集のあるレイアウトが開いていれば、先に保存して(記録します)、マージに加えます。
2. **利用側と一緒に変えたシンボル**(シンボルの編集と、それを使う回路図の配線の付け替え)では、さらに、それらのビューが設計側で起点のときのままで
   あること、その後に配置された回路図で、配線がシンボルに追従しなければならない使い方をしているものがないことが必要です。どちらもファイルの
   マージでは分かりません。シンボルを変えた後に提案自身が新しく加えた回路図(新しいテストベンチなど)は、すでに新しいピンに合わせて配線されているので
   数えません。
3. **全か無か。** 衝突が 1 つでもあれば何も書き込みません。レビューにはファイルごとに衝突を UI の言語で表示し、それぞれ今の設計の値、提案の値、
   提案を開いたときの値を示します(HTTP では、コード `merge_conflict` の 409 です。[HTTP API](../reference/api.md#changesets) を参照)。それでも
   採用するには、それらのオブジェクトを両側で一致させてから、もう一度採用します: 設計側で変える(提案を開いたときの値に戻すと、提案の値が入ります)か、
   提案側で変えます(プレビューで手で直すか、**Request changes**)。採用しない場合は破棄します。提案はブランチに残ります。マージの最中に Undine で
   行った編集(設計の意図や RTL の編集も)は、マージを待ってから行われ、失われません。その間にほかのもの(ファイルを書く別のプログラム、
   `git pull`)がファイルを変えた場合は、衝突として何も書き込まず、そのプログラムが書いたものは残します。レビューは、採用している間に
   ファイルが変わったことと、もう一度採用すればその編集とマージされることを表示します。読み込めないファイル(YAML が壊れた設計の意図や
   netlist)も衝突になり、レビューは読み込めない理由を表示します。ファイルを直してから、もう一度採用してください。
4. **ログ。** 設計の操作ログには、changeset の記録(changeset の印付き)と、changeset を示す `merge` の記録が入ります。Undo はそこで止まります。
   採用した changeset は Undo ではなく **Revert**(取り消し)で戻します。
5. **コミット。** 採用する前にプロジェクトにほかの未コミットの変更がなければ(最後のコミットとの違いがマージで書いたものだけ。changeset の記録は
   数えません)、あなたのブランチにマージコミットを作ります。親は HEAD と提案の先端、メッセージは `Apply <id>: <changeset title>` で、理由、採用した人、
   チェックの結果が入ります。レビューとトーストにそのコミットが表示され、[履歴パネル](history.md)にも出ます。そうでなければ、マージは作業ツリーに
   未コミットのまま残り、レビューにその理由(答えの `why`)が表示されます: プロジェクトにほかの未コミットの変更があった(`changes`。準備ができたら
   git でコミットしてください)、リポジトリにまだコミットがない(`no_commit`。履歴パネルで最初のコミットを作成してください。このマージも含まれ、
   以降の採用はコミットされます)、コミットに失敗した(`failed`。git でコミットしてください)。
   `.gitignore` が無視していて git が追跡していないファイルはコミットに入りません(`history/` を無視していれば操作ログ。changeset の記録は
   それでも設計のログに入ります)。
6. worktree を削除し、ブランチを残します(上記)。マージが書いたファイルを表示しているタブはそれを読み直し、ほかのタブはそのままです。
   保存していないテキスト(RTL や設計の意図の YAML)を持つタブは、そのテキストを残して上にバーを出します。必要な部分を控えてから
   **テキストを破棄して再読み込み** を押すと、マージしたファイルを表示します(古いテキストをマージしたファイルの上に保存することはできません)。
   入力を Undo で元のテキストまで戻すと、タブは自分でマージしたファイルを読み直し、バーは消えます。

**Revert**(取り消し、`POST .../revert`)は、同じマージを逆向きに、採用した先端から起点へ行います。changeset が変えたオブジェクトは前の値に戻り、
同じオブジェクトへの後からの編集は衝突になります(何も書き込まず、レビューに今の値、採用前の値、採用時の値を表示します)。changeset が追加した
ファイル(セル、ビュー、設計の意図)は、作ったものがその後ほかで使われているかもしれないので、そのまま残します。結果にその一覧(`kept`)が入ります。
changeset が作ったライブラリは、ファイルが残っている間は `project.json` に残すので、そこに残したセルも、その後に加えたものも、プロジェクトの
一部のままです。
ログには取り消しを示す `merge` の記録が入ります。コミットするか(`Revert <id>: <changeset title>`、HEAD の上)、未コミットのまま残すかは採用と同じで、
開いているタブも採用のときと同じように扱います。コミットが残っているので、作業コピーは要りません。

**Discard**(破棄)は、証拠を保存し、worktree を削除し、ブランチを残します。

**処理中の表示。** 採用・破棄・取り消しはサーバーで行われ、時間がかかることがあります(数 GB の実行結果の証拠の保存や、大きなマージ)。
その間、Changes の一覧とレビューはその changeset に進み具合を表示し(`採用中: 証拠を保存中 3.1 / 25 GB`、続いて `マージ中`、`後片付け中`)、
上部バーの **Changes** ボタンは `採用中` と表示して、その changeset を未処理の提案の数に含めません。changeset は一度に一つずつ閉じます。
その間に別の changeset で **Adopt** を押すと、最初の処理の完了を待つことが表示され、順番が来るまでそのレビューには
`「…」(採用中)の完了を待っています` と表示されます。採用中の同じ changeset をもう一度採用しようとすると拒否されます(409 `busy`)。

<a id="if-undine-stops-in-the-middle"></a>
## Undine が途中で止まったとき

採用と取り消しは、まず `<project>/changesets/<id>/merging.json` に、これから書くファイルと、それぞれの書く前と書いた後のダイジェスト、
そのコミットの件名を書きます。書いている途中で Undine が止まると、次に `undine serve` を起動したとき、回路図を読んだり画面に答えたりする
前にそれを片付けます(何をしたかを表示します)。その changeset を次に読んだときも同じです。

- **終える**: マージをすべて書き終えていたとき。changeset は採用済みまたは取り消し済みになり、コミットが付くか(このマージのために Undine が
  作ったコミットだけを数え、その間にあなたが作ったコミットと取り違えることはありません)、マージが未コミットのまま残ります。
- **元に戻す**: そうでないとき。その後にあなたが行ったことは残します: マージがすでに書いたファイルは前の内容に戻し、操作ログはその後に
  加わった記録を残し、マージが追加したファイルは消し、マージがまだ手を付けていなかったファイルはそのままにします。マージが書いた後に
  変更されたファイルはそのままにし、名前を示します。changeset はそのまま(開いたまま。取り消しでは採用済みのまま)で、レビューに何が
  起きたかの注記を表示します。もう一度採用(取り消し)してください。足りない分をマージします。成功すると注記は消えます。

どちらの場合も、操作ログに changeset の記録が入るのは一度だけです。それが終わるまでは、採用、破棄、取り消しを拒否します。

起動後に Undine が初めてプロジェクトの changeset を読むときには、止まったときにリポジトリに残ったものも片付けます: 記録では採用済みや
破棄済みなのに作業コピーやブランチが残っている changeset はここで閉じ、記録のない changeset(開いている途中で Undine が止まった)のブランチと
作業コピーは片付けます。作業コピーをそのブランチにコミットし、worktree を削除し、ブランチを `refs/undine/changesets/<project>/<id>` として
残します。ブランチを削除することはありません。閉じる処理が意図して残した作業コピー(下記)には触れません。

<a id="evidence-after-apply-or-discard"></a>
## 採用・破棄の後の証拠

採用または破棄すると作業コピーは削除されますが、提案の変更、チェック結果、入力ハッシュ、ジョブの出力ファイルは
`<project>/changesets/<id>/evidence/` に残ります。作業コピーと元の設計の両方のジョブを保存し、再チェックで置き換わった以前の実行や、
起動に失敗したジョブが書いたファイルも含みます。アーカイブには、操作の引数、プロジェクトの設定、依存関係のロックも入り、起点のコミットと
レビューした先端のコミットを記録します。設計のファイルと操作ログ全体は、ブランチの参照に残るそれらのコミットにあります。
changeset の `evidence` フィールドに、アーカイブのパス、保存した時刻、ジョブの数、サイズが記録されます。

実行結果はコピーしません。証拠の中の各ファイルは実行結果のファイル自体へのハードリンクなので、数 GB のモンテカルロの波形を保存しても
その分の書き込みは発生せず、作業コピーを削除した後は証拠が唯一の保存場所になります(証拠のフォルダが作業コピーと別のファイルシステムにある場合や、
リンクが拒否された場合はコピーします)。各ファイルはハッシュのために一度だけ読み、実行が終了時にハッシュを記録していてその後ファイルが
変わっていなければ、まったく読みません。Undine は終了した実行のファイルをその場で書き換えないため(ジョブのステータスは新しいファイルに書いて
置き換えます)、後の操作がリンクを通して証拠を変えることはありません。ジョブのツールはそれぞれ専用のプロセスグループで動き、ジョブの
キャンセルや制限時間での停止は、そのジョブが起動したものすべて(Verilator のビルドが起動するコンパイラ、LibreLane のフローのツール。
再起動の後にサーバーが引き継いだシミュレーションでも同じです)を止めます。それらが終わるまで、changeset は採用も破棄もできません。
ジョブ自体が終わった後に残ったものも同じです(`cancel_job` で止められます)。それでも書き込まれる可能性のある実行結果は、リンクせずにコピーします。ジョブが
キャンセルされた、制限時間で止められた、または終了しなかった実行と、何らかのプロセスがその中で作業しているか、そのファイルを書き込み用に
開いている実行(Linux)です。コピーはその時点の実行結果で、閉じた後の書き込みは削除される作業コピーのファイルに行き、証拠には届きません。
証拠の保存中に Undine が止まった場合、途中まで保存したもの(`changesets/<id>/.evidence-*`)は、Undine が次に起動してそのプロジェクトの
changeset を読むときに削除します。

**サイズと波形の削除。** 閉じた changeset のレビューには、証拠のサイズとそのうち波形が占める量が表示され、Changes の一覧には閉じた
changeset ごとのサイズと合計が表示されます。レビューの **波形を削除** は、サイズを示す確認の後、その実行の生の波形(`out.raw` などの
`*.raw`、`*.vcd`、`*.fst`)を削除します。元に戻すことはできません。それ以外はすべて残ります。各実行の `status.json`(入力、出力のハッシュ、
判定)、ログ、ネットリスト、結果、測定値、そして保存時の全ファイルのハッシュを持つマニフェストです。マニフェストには、何をいつ誰が削除したかも
記録されます。その後レビューには波形を削除したことが表示され、証拠を検査するとそのファイルは「見つからない」ではなく「削除済み」と報告されます。
削除できるのは人だけです。エージェントのツールにはこの操作がなく、HTTP の呼び出しもエージェントのアクターからは拒否します。閉じる処理が
作業コピーを残した場合(下の、後から来た編集)、その実行結果は証拠と同じファイルなので、確認とその後のメッセージで、サイズのうちどれだけが
その作業コピーを削除したときに初めて解放されるかを示します。

閉じた changeset でも、変更とチェックは表示されます。その結果と鮮度は **採用または破棄した時点** のもので、実際のプロジェクトの今の設計についての
記述ではありません。取り消しても、元の証拠は残ります。証拠のアーカイブが導入される前に閉じた changeset では、すでに消えたファイルは復元できません。

証拠を保存した後に編集や新しいジョブが届いた場合、changeset は保存した時点の内容で閉じます。採用ではレビューした先端をマージし、後から来た編集は
ブランチにコミットします。作業コピーは復旧用に残し、Changes パネルには警告が表示されます。その作業コピーがある間は
**Open retained preview**(保持された提案版を開く)も表示され、後から来た編集やジョブを確認できます。それらは保存した証拠にも、
採用した変更にも含まれません。

<a id="older-changesets"></a>
## 以前の changeset

changeset が git のブランチになる前に開いた changeset は、ライブラリのコピーでした(記録にブランチがありません)。採用・破棄したものは証拠を残し、
これまでどおり表示されますが、取り消しはできなくなりました。まだ開いているものは、確認と破棄ができますが、続きは作れません(**Request changes**
は表示しません)。採用は拒否され、新しい changeset として提案を作り直すよう案内されます。破棄するとそのコピーを削除します。ブランチはありません。

## changeset とほかの git ブランチ

changeset は、1 つの Undine の中で、Undine が開き、チェックし、レビューにかけ、マージする git のブランチです。より長く並行して進める作業
(2 人、2 つのクローン)は自分の git ブランチで行い、git が同じ規則でマージします。オブジェクト単位でまとめ、衝突はオブジェクトごとに報告し、
まとめた内容を誰も確認していないセルを DRC / LVS の対象として一覧にします。

```bash
python -m undine git-setup demo          # クローンごとに一度: 差分とマージのドライバ
git merge feature                        # 同じセルへの編集はオブジェクト単位でまとまる
python -m undine merge-check             # 残っている衝突、警告、確認すべきセル
python -m undine resolve libs/mylib/inv.sch --theirs inst:M2:placement
```

changeset のブランチは、ほかのブランチと同じように扱えます。push して共有することも、git でマージすること(`git merge undine/demo/cs-4ce078`)も
できます。そのようにマージした changeset は Undine の記録の外にあるので、その後 Undine で破棄してください。Undine はリモートのブランチを
一覧にせず、changeset を Undine の中でリベースすることもまだできません。

Undine は、マージで下のファイルが変わったことに気づきます。未保存の編集がない開いたレイアウトは読み直し、未保存の編集があるレイアウトは、
読み直すまでマージしたファイルの上に保存しません。マージの前に読み込んだテキストからの RTL や設計の意図の保存も拒否します。
ブランチ、変更、マージは[履歴パネル](history.md)で見られます。
[git によるバージョン管理](../reference/data.md#version-control-with-git)と、設計の[意味的な差分とマージ](../design/merge.md)を参照してください。

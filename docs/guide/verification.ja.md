# 検証

DRC と LVS は、PDK の KLayout デッキを使ってサーバー上で実行します。レイアウトエディタの **DRC / LVS** タブで実行し、結果を確認します
(ルール、レイアウト上のマーカー、LVS の対応表)。

**上位セルのピン。** KLayout の比較は、レイアウトにピンのない回路図のピンを受け入れ、そのネットを同じデバイスを持つ別のネットに対応付けます。
そのため、ラベルの付いたストライプから切り離された電源でも「一致」になることがあります。Undine はさらに、回路図の上位セルのピンがすべて、
対応したネット上でレイアウトの上位セルのピンになっているかを確かめます。なっていないピンは判定の下に表示され(例: `pin VDPWR: no VDPWR label on
the layout net it matched ($12)`)、結果は不一致になります。

**セルの中で使わないポート。** セルの中で何にもつながらない回路図のポート(CDAC の `vdd` のように、シンボルのためにあるインターフェースの
ピン)には、レイアウトで対応するものがありません。デッキのネットリストの簡略化は、デバイスのないネットをラベルの有無にかかわらず取り除く
ので、レイアウトにはそのピンがありません。Undine は、そのポートのラベルがレイアウトの上位セルにあれば受け入れ、LVS の要約と
`get_lvs_report` の `unused_pins` に挙げます。ラベルはピンラベルの層(`met1.label` など)にあり、その金属の図形の上にある必要があります。
ラベルがなければエラーです(`pin VDD: connected to nothing inside the schematic and no VDD label in the layout's top cell`)。
その名前のラベルがレイアウトの使われている金属(デバイスのつながるネット)にあるのもエラーです(`pin VDD: connected to nothing in the
schematic but its label is on the layout net ...`)。キャパシタの電極などのネットがセルの `vdd` ポートになってしまうためです。

**MIM キャパシタ(sky130)。** MIM のシンボルはデバイスの呼び出し(`XC1 c0 c1 sky130_fd_pr__cap_mim_m3_1 W=12 L=12 m=2`)を書きますが、
sky130 のデッキの読み込みはこれを呼び出しのまま残します。一方デッキは、電極を別のモデル名のキャパシタとして抽出し、面積と周囲長で比較します。
そこで参照ネットリストでは MIM をそのキャパシタとして書きます。`cap_mim_m3_1` は `CC1 c0 c1 sky130_fd_pr__model__cap_mim A=144 P=48 m=2`
に、`cap_mim_m3_2` は `sky130_fd_pr__model__cap_mim_m4` になり、1 個あたり `A = W * L`、`P = 2 * (W + L)`(um)、`m` は `MF` から取ります。
これで LVS はキャパシタの合計の面積と周囲長、そしてネットを比較します。2 × 3 um のユニット 2 個は `W=2 L=3 MF=2` と一致し、ユニット 1 個、
周囲長の違うユニット(2.4 × 2.5 um)、別のネットにつながるキャパシタは一致しません。この規則は PDK プロファイルの `lvs_elements` で、
モデル名の置き換えとパラメータの計算ができます(`server/undine/pdks/pdkprofile.py`)。

**LVS の標準セル(sky130)。** PDK の標準セルで作ったレイアウト(取り込んだ LibreLane のマクロや、手で置いたセル)は、それらの回路図と
照合します。回路図のネットリストはセルを呼ぶだけで定義しないので、Undine は呼ばれた各セルをライブラリの SPICE ファイル
(`sky130_fd_sc_hd.spice`)から足します。トランジスタは、デッキがレイアウトと比べられる素子として書き(`special_nfet_01v8` は、デッキの
読み方に合わせて `nfet_01v8` に。W と L は um)、参照側の並列のフィンガーは、デッキがレイアウト側をまとめるのと同じようにまとめます
(`schematic_simplify`)。デッキはセルを 1 つずつ比べ、それからセル間の配線を比べます。そのままでは一致しないものが 3 つあります:

- *タイセル。* `conb_1` は、デッキが抽出しないポリ抵抗を通して HI と LO を出すので、レイアウトでは HI は VPWR、LO は VGND です。
  参照も同じにします。タイセルは参照から外し、HI / LO のネットは電源につなぎます(回路図の `hi9` は LVS では `vdd`)。2 つの
  ポートをつなぐタイセル(HI が出力ポート)は断ります。レイアウトでは 2 つのポートが 1 つのネットになり、LVS は 2 つのピンと比べられ
  ません。そのようなポートはバッファから出します。
- *物理セル。* 配置配線がレイアウトのためだけに足すセル(フィル、タップ、デキャップ、アンテナダイオード)は回路図にありません。LVS では
  デバイス(拡散とポリ)を除き、ウェル、タップ、レールは残します。行の n ウェルはタップに届いたままで、比べるものは何も足しません。
  参照からも外します。回路図が描いたもの(デキャップ、アンテナダイオード)も同じです。実行は同じセルをさらに足すので、比べません。
- *pwell のラベル。* フリップフロップは pwell(64/59)に `VNB` のラベルを 2 つ持ち、デッキがつなぐものではつながりません(抽出が止まる
  エラーになる)。標準セルの中のこのラベルは除きます。

レイアウトのファイルは変えません。LVS が読むコピーの話です。規則はプロファイルの `stdcell_lvs` です。PDK に SPICE がないセル
(`sky130_ef_sc_hd__decap_12.spice` のように専用のファイルにあるセルは、そこから読みます)や、デッキが比べないデバイスを持つセルは、
名前を挙げて断ります。

<a id="second-opinion-magic-drc-and-magic-netgen-lvs"></a>
## もう一つの判断材料: Magic の DRC と Magic + Netgen の LVS

KLayout のデッキのほかに、Verify パネルでは **Magic の DRC**(スタイル `drc(full)`)と **Magic + Netgen による LVS** も実行できます
(Magic がレイアウトを抽出し、Netgen が PDK の設定ファイルを使って回路図と比較します)。シャトルの事前チェックで使われるのと同じツールです
(ChipFoundry の `cf-precheck` は Magic で抽出して Netgen で比較し、wafer.space は KLayout の DRC の前に Magic の DRC を実行します)。
結果は同じブラウザで確認できます(ルールの一覧、レイアウト上のマーカー、必要に応じて Netgen の出力)。デモのインバータでは両者の結果が一致します
(DRC 違反なし、LVS 一致)。わざと違反を入れたレイアウトでは、KLayout が 172 件、Magic が 171 件の違反を、それぞれ別のルールで報告します。
両方を実行する意味はそこにあります。Magic は 1 つの違反をその範囲のエラータイルの集まりとして返します。Undine は接するタイルを 1 つのマーカーに
まとめるので、件数は違反の数です(長さ 24 um の突き合わせタップは `diff/tap.16` 1 件で、138 個の矩形ではありません)。

<a id="the-checks-of-a-changeset"></a>
## 変更セットの検証

変更セットのレビューの **必要な検証を実行**(エージェントは `run_checks`)は、変更セットが変えた各セルを、作業コピーとベースラインの両方で検証します。

- 変更したレイアウトの **DRC**。PDK の KLayout デッキに加え、sky130、GF180MCU、IHP SG13G2 / SG13CMOS5L では Magic の `drc(full)` も
  実行します(別の行、*DRC (Magic)*)。
  KLayout のデッキ `sky130A_mr.drc` には MV の diff / tap ルール(diff/tap.14-17)がなく、MIM の間隔も別の形で検査します。KLayout の DRC が
  違反なしだったブートストラップスイッチで、Magic は `diff/tap.16`(5 V nfet の PCell の突き合わせタップ。最小 0.7 um のところ 0.45 um)、
  `capm.11` 2 件、`met3.3c` 2 件を見つけました。IHP では、KLayout デッキの標準の実行が含めないルール(最小面積の `M1.d`、`Gat.e`、
  ラッチアップのタップ距離 `LU.a` / `LU.b`)を Magic が持っています。Magic はセル全体とその周り 10 um を検査します。セルの端にある細すぎる
  配線は、エラーの領域がセルの外にあり、そうしないと Magic が落とすためです。Magic がインストールされていなければ、その行は失敗し理由を
  示します。どの PDK で実行するかは PDK プロファイルの `magic_drc` が決めます。
- 回路図とレイアウトのあるセルの **LVS**。sky130、GF180MCU、IHP SG13G2 ではその LVS の接続情報から **ERC** も行います。
  他のネットのソース / ドレインに接するボディタップを探します。間に何もない n+ / p+ 接合がタップに接している状態で、その容量、リーク、逆バイアス電圧はどのモデルにも、LVS にも、寄生抽出にも
  現れません。PCell の `bulk tie`(片方のソース / ドレインに突き合わせたタップ)が信号ネットの側に来ると起こります。同じスイッチでは
  13 個中 7 個のデバイスがそうで、サンプリングスイッチの出力が vss のタップに接していました。各指摘はインスタンス、端子、そのネット、
  タップのネットを示します。ERC の行は違反ではなく警告です(黄色で表示)。GF180MCU ではこの接合はシリサイド化されるので、その LVS
  デッキが見ない短絡です。IHP の LVS デッキはシリサイド化した接合をタップにつなぐので、そのようなタップは LVS が短絡として報告し、ERC が
  接合を見つけるのは SalBlock の下だけです。PDK のタップの描き方は PDK プロファイルの `erc_tap` が示します。

各行はジョブ、終わった時刻、同じ入力で実行済みのジョブを再利用したか(`reused`)を示します。検証は入力(レイアウト、参照ネットリスト、デッキ、
ツールのバージョン)ごとに保存されるので、変わっていない設計でもう一度実行すると前の結果を使います。`run_checks(fresh: true)`
(または `POST /api/p/<project>/changesets/<id>/verify?fresh=true`)はすべてを新しく実行します。

Undine が生成した PCell のバリアントのうち、もうどこにも置かれていないもの(`nf` を変えた `sync_layout` が残した古いもの、消した
`place_pcell` の部品のもの)には行を作りません。単独では設計ではなく、Magic の `LU.2` で落ちるためです。`run_checks` はそうしたセルの数を
`skipped_unused_cells` で示し、アシスタントの `delete_unused_cells` が取り除きます。

エージェントの `run_checks` は、changeset が変えた回路図もそれぞれ検査します(`kind: schematic`: ポートに対するシンボル、電源パラメータ、
描かれていない接続)。落ちた行にはベースラインの行が付き、changeset の前から同じ指摘があれば `unchanged_from_baseline`(以前からずれている
シンボルのピン順など)、changeset が加えたものは `new_in_work` に示します。`get_lvs_report` は不一致のとき、その理由を `why` に数と名前で
示します。レイアウトと回路図のクラスごとの素子数、相手のない素子とピン、接続が 1 つしかないレイアウトのネット、あるいは KLayout が
レイアウトの回路を何も残さなかったこと(デッキのネットリスト簡略化は、接続が 2 つ未満でピンのないネットをすべて落とします。配線もラベルも
ない配置では何も残らず、抽出したネットリストはヘッダだけになります)です。

**違反の場所。** `get_drc_report(lib, cell, rule?, checker?, limit?)` は、チェッカーごとの最新の DRC について、ルールごとの説明、件数、
um 単位のマーカー(矩形、間隔や幅のルールが測った 2 本の辺、多角形)を返します。マーカーはセルの座標です。KLayout はサブセル(PCell の
バリアント)の中の違反をそのセル自身の座標と配置で報告し、Undine はそれを配置された位置に置きます(何度も配置されたセルの違反は、配置の
1 つで 1 回だけ報告されます)。`render_layout(lib, cell, markers: true)` はそれらをルールごとの色でレイアウトに重ねて描きます。描くものがなくても絵は返し、最新の実行がクリーンだったのか、まだ実行がないのかを `markers_note` が示します。

**他のエージェントの changeset を確かめる。** 検証役は `run_checks`、`get_drc_report`、`check_specs`、`extract_parasitics` と
その他の読み取りとチェックに `changeset: cs-...` を渡します。その changeset の作業コピーに対して、書き込みのロックを取らず、
検証役のものにもせずに実行し、書き手の実行と同じくその changeset に記録します
([他のエージェントの changeset を確かめる](assistant.ja.md#checking-another-agents-changeset))。

<a id="parasitic-extraction-and-post-layout-simulation"></a>
## 寄生抽出とポストレイアウトシミュレーション

DRC と LVS が通ったら、レイアウトのセルを寄生成分ごと抽出し、そのセルを回路図の代わりに抽出結果に置き換えてテストベンチをシミュレーションできます。

**抽出。** エージェントは `extract_parasitics(lib, cell, mode)` を呼びます。HTTP では `POST /api/p/<project>/pex` に
`{"lib", "cell", "options": {"mode": "c" | "rc", "cthresh_ff": 0.01, "res_threshold_ohm": 0.1, "res_nets": [...]}}` を送ります
(後の 2 つはモード `rc` のためのものです)。ジョブはセルを平坦化し(残すのは上位セルのラベルだけで、
それがピンになります)、Magic と PDK の設定ファイルで抽出して、`extracted.spice` を書きます。回路図のポートを回路図の順に持ち、
レイアウトのデバイスを含むサブサーキットで、さらに次を含みます。

- モード `c`: 各ネットの基板への容量と、ほかの各ネットとの容量(カップリング容量)。ネットごとに 1 ノード。
- モード `rc`: これに配線の抵抗を加えます。ネットごとに Magic の `extresist` が求める抵抗網を持ち、モード `c` と同じ容量を網のノードに分けます。
  ネットの容量は、Magic と同じく各ノードが受け持つ面積の割合で分けます。カップリング容量は 2 つに分け、半分ずつをそれぞれのネットに
  割り当てます。それぞれの半分を同じやり方でそのネットのノードに分け、各部分を相手のネットのいちばん近いノードにつなぎます。そのため、
  配線のどこにカップリングが付くかは、2 つのネットが重なる場所ではなく、配線の面積で決まります。ネットリストを小さく保つため、半分は
  網に沿って散らした最大 16 個のノードに分けます。

モード `rc` で抵抗網を持つネット: ポートかソース / ドレインを持つすべてのネットです。ただし、いちばん大きい抵抗(網の始まりから
ネットのどこかまで)が `res_threshold_ohm`(既定は 0.1 ohm)より小さいネットは 1 ノードのままです。それより小さい抵抗も、網が許す
ところでは隣とまとめます。Magic 自身の既定(10 ohm と遅延 1 ps)では、小さなアナログセルの信号ネットはどれも 1 ノードのままになり、
スイッチのオン抵抗に配線がまったく入りません。そのため Undine は遅延の下限を 0 にします。`res_nets: [...]` はそのネットだけに網を
作ります(既定ではネットリストが大きくなる大きなデジタルブロック向け)。名前の大文字と小文字は区別しません(`VIN` は `vin`)。ポートもソース / ドレインもないネット(ウェル、ゲートからしか
届かないネット)は 1 ノードのままです。`extresist` がそのようなネットで止まるためです。ポートでない基板も 1 ノードです(グラウンド 0)。
要約の `single_node` は、1 ノードのまま残ったネットとその理由を挙げます。`extresist` が無視できると判断したネットには、見つけた
いちばん大きい抵抗も示します。8.3.653 より前の Magic には `extresist minres` と `mindelay` がなく、threshold の意味も違うため、自身の規則でネットをまとめます。
そのときは `res_options_not_applied` が、`res_threshold_ohm` を使わなかったことを示します。

`cthresh_ff` より小さい容量は省きます(既定は 0.01 fF)。基板のノードは、ポートでなければシミュレーションではグラウンド(`0`)です。
回路図にないラベルは内部のネットの名前になります。ラベルのないネット(Magic は `a_0_0#` のような名前を付けます)も、モード `rc` で容量を
失いません。`extresist` はそのノードを `a_0_0.t0`、`a_0_0.n1` のように名前を変え、容量はそれらのノードに付きます。

**ネットの名前。** 抽出したサブサーキットは、ラベルのないネットでも回路図のネット名を保ちます。同じレイアウト(同じレイアウトのハッシュ)の LVS が
レイアウトのネットを回路図のネットに対応付けていれば、抽出はラベルのない各ネットに、そのコンタクトかビアの 1 つの中心で、その上のメタルの
ラベル層(PDK プロファイルの `net_labels`)に回路図の名前のラベルを付けてから Magic で抽出します。Magic はネットにラベルの名前を付けるので、
内部のノードを測るテストベンチ(`v(x1.g)`)は抽出結果でもそのノードを見つけます。そのような LVS がなければ、Magic はそれらのネットに
ネット上の点にちなんだ名前(`a_3109_5296#`)を付け、要約の `names` がそう伝えます(検証を実行してから、もう一度抽出してください)。
LVS が対応付けたのにラベルを付けるコンタクトのないネットは `names.unnamed` に示します。`net_labels` を持つ PDK は sky130、GF180MCU、IHP SG13G2 です。

**デバイスの名前。** Magic はデバイスに順不同で `X0`、`X1` ... と名前を付けるため、テストベンチのデバイスの量
(`@m.x1.xxm5.msky130_fd_pr__nfet_g5v0d10v5[l]`、`@m.x1.xm1.msky130_fd_pr__nfet_01v8_lvt[gm]`)はデバイスを見つけられません。同じ LVS
があれば、Magic の各デバイスは、モデルと端子のネットが自分と同じレイアウトのデバイス(ソースとドレイン、キャパシタの電極はどちら向きでも。
Magic が名前を付けなかったネットは、どこでも同じ 1 つのネットを表します)に LVS が対応付けた回路図の素子の名前を、シミュレーションの
ネットリストが書く形(`XXM5`)で受け継ぎます。Magic が複数に分けたデバイス(フィンガー、倍数)は、その素子、続いて `_2`、`_3` ... になります
(MF=2 の MIM なら `XXCB`、`XXCB_2`)。そこで読む量(`[id]`、`[gm]`)はその一片のものです。同じ素子(同じモデル、ネット、L。ダミーなど)は
Magic のデバイスを分け合い、異なる素子のどちらにも合うデバイスは Magic の名前のままです。要約の `names` は、名前を付けた数
(`devices_named`)、Magic の名前のままのもの(`devices_kept`)、分かれた素子(`devices_split`)を示します。

**MIM キャパシタ。** Magic の sky130 のテクノロジーファイルは、MIM の容量層のプレーン(`capm` の `cap1`、`cap2m` の `cap2`)を
`planeorder` ですべてのメタルより上に置いています(「MiM cap layers have been purposely put out of order」)。その既定の容量規則
(`defaultoverlap`、`defaultsideoverlap`)は、あるメタルを別のメタルから遮蔽するプレーンをこの順序から決めるので、上部電極は何も遮蔽せず、
キャパシタの上のメタルは上部電極を通り抜けて下部電極に届きます。そのため Magic は、キャパシタの中でそのメタルが下部電極に重なる容量
(sky130A の met4 over met3 は 84.03 aF/um²)と、そこでのメタルの辺のフリンジ(`defaultsideoverlap allm4 metal4 allm3 metal3`:
70.52 aF/um)を、2 つの電極のネット間に数えます。実際のシリコンでは、それは自分のネットの上部電極の上にあるメタルです。電極どうしの容量は
デバイスのモデルにあり、上部電極の辺のフリンジはその周囲長の項に入っています。

そこで MIM キャパシタを含むセルの抽出では、Magic をもう一度(ジョブの `shielded/` で)実行します。各容量層のプレーンを下部電極のすぐ上に
置き、下部電極のメタルとその上のメタルの間の既定の規則を、同じ値で容量層にも写します。下部電極が上部電極を通して受けていたものを
上部電極が受けます。自分のメタルならカップリングはなく、別のネットのメタルなら上部電極のネットとのカップリングになります。
2 回目の抽出のネット間のカップリングが結果です。基板への容量はそうではありません。Magic は辺のフリンジを横にあるものに分け合うので、
容量層の新しいフリンジの規則が上のメタルの基板へのフリンジを少し取ります(1.17 um のユニットで下部電極の 1521 aF のうち 2.8 aF)。
シリコンでは下部電極の上の上部電極はこれを変えないので、基板への容量は 1 回目の抽出のものです。要約の `mim_shielding` が
変わったものを示します。

- `removed_ff`: 除いたカップリングの合計(すべての組の変化の和。移ったものは合計が変わらないため)。そのうち面積による `overlap_ff`
  (キャパシタの中のビアで上部電極につながるメタル)と、残りの `fringe_ff`(フリンジと、そこにビアのない上部電極のネットのメタル)。
- `pairs`: MIM の 2 つの電極であるネットの組ごとに、Magic が与えた値(`magic_ff`)、残した値(`kept_ff`: キャパシタの外のカップリング。
  下部電極の縁の上を通るストラップや、横にある下部電極の met4 コンタクトなど)、その変化 `removed_ff` と面積による `overlap_ff`。
  組の変化は、そこへ移ってきたものを差し引いた値です。上部電極のネットが 1 つの CDAC では、ある下部電極のメタルが別のユニットの
  キャパシタの上にあると、上部電極のネットとのカップリング、つまり最初のユニットの電極の組になります(合計は `moved_to_plates_ff`)。
- `moved`: それ以外に変わった組。キャパシタの上を通る別のネットの配線は、上部電極とのカップリングになります(合計は変わりません)。

0.78 um のコンタクトパッドを持つ 1.17 um の sky130 ユニットでは、Magic の電極間 191 aF のうち 51 aF がパッドの面積、38 aF がキャパシタの中の
フリンジで、102 aF(キャパシタの周りの下部電極へのパッドのフリンジと、横にある下部電極の met4 コンタクト)が残ります。4 × 4 のアレイに
列ごとの met4 ストラップを付けた場合、内側のユニット 1 個あたり 357 aF が 303 aF になりました。2 回目の抽出が失敗したときは、これまでどおり
重なりの面積だけを除き(`mim_overlap_removed`)、`mim_shielding.not_applied` に理由を示します。

1 つのネットに 2 つのラベルがあると、Magic のネットリストでは 1 つのポートになります。回路図のピンがそのうち 1 つだけなら、そのピンが
ネットの名前になります。両方が回路図のピンなら、要約の `ports.shorted` にその組を示し、ポートは合っていないことになります。

モード `rc` を Undine が自分で組み立てるのは、Magic の抵抗抽出の流れが容量を誤るからです。Magic 8.3.465 はカップリング容量を残したまま、
同じ値をもう一度ネットのグラウンドへの容量に加えます。1 mm の met1 配線の隣に別の配線がある場合、カップリングは 113 fF で、グラウンドへの容量は
51 fF ではなく 164 fF になります。論文「The Era of Vibe Tapeout」では、カップリングをグラウンドにまとめたことで ADC の SNDR が 9 dB 良く見えました。
Undine は、デバイスと抵抗網を Magic の抵抗抽出から、容量を同じ抽出の容量抽出から取るので、ネットごと・ネットの組ごとの合計はモード `c` と同じです。
Magic は階層の扱いにも問題があるため、抽出の前にセルを平坦化します。階層のあるセルでは `extresist` がトランジスタをすべて 2 回書き、
Magic 自身の `flatten` は MIM キャパシタとその上に描いた via4 の接続を切ります。詳しくは `server/undine/checks/parasitics.py` の
モジュールの説明にあります。

**要約。** ジョブの結果(と `GET /api/p/<project>/jobs/<job>/parasitics?net=`)は次を返します。

- 各ネットの容量。大きい順(グラウンドへ、カップリング、合計)
- 大きいカップリング容量
- モード `rc` では各ネットの抵抗(抵抗の合計と、ピンから網をたどった最大の抵抗)
- モデルごとのデバイス数
- ポートが回路図と合っているか(足りないピン、ほかのピンとショートしているピン、余分なラベル)
- 浮いているネット(容量だけでつながるネット。ngspice が動作点を求められるよう、基板へ 1 TΩ を付けます)
- 内部のネットの名前の出どころ(`names`)と、MIM キャパシタの上部電極が遮蔽するもの(`mim_shielding`)
- レイアウトの LVS が回路図と合わないときの `warning`(診断のために抽出はします。素子が Magic の名前のままの理由は names が示します)と、
  かかった時間 `runtime_s`

エージェントの `get_parasitics` に `net` を渡すと、そのネットの行だけを返します(抽出にないネットなら、近い名前を添えたエラー)。また、抽出が古いかどうか(`outdated: true / false` と、変わったもの)と、何から作ったか(レイアウトのハッシュと時刻)も示します。

長い一覧は 12 行で切り、残りの数を示します。sky130A での実行時間: インバータで約 1 秒、2 × 1024 の MIM キャパシタアレイ(デバイス 2048 個)で、
モード `c` が 1.9 秒、モード `rc` が 3.7 秒(抵抗 8124 個)。配線していない 1.17 um ユニット 1156 個の CDAC は、MIM の 2 回目の抽出を
含めてモード `rc` で 3.6 秒です。

**抽出結果でのシミュレーション。** `run_simulation`、`check_specs`、`sweep` は `extracted: ["lib/cell", ...]`
(または `{"lib/cell": "<job>" | "c" | "rc"}`)を受け付けます。`POST /api/p/<project>/sim` も同じフィールドを受け付けます。
テストベンチは、コーナー、温度、プロパティの上書き、スペクトルの測定も含めて普段どおりにネットリストにします。違いは、
指定したセルのサブサーキットが、そのセルの最新で古くなっていない抽出結果(またはジョブを指定すればその抽出結果)になることです
(ポートはシンボルのピンの順)。そのセルとその下はすべてレイアウトから来ます。次の場合は、何を実行すべきかを添えて拒否します。

- セルに終わった抽出がない
- 抽出が古い(その後でレイアウトか回路図のポートが変わった)
- 抽出に回路図のポートが足りない(ラベルのないピン)、または 2 つのピンが 1 つのネットにある
- セルがテストベンチにない
- スイープが、抽出結果で置き換えたセルの中のプロパティを変えようとしている
- テストベンチが、抽出結果にない、抽出したセルの中のノードを参照している(抽出がそのネットを `a_3109_5296#` と名付けたときの `v(x1.g)` など。
  `.meas`、B 電源、`.save`、`.control`、`signals` のどこでも)。ngspice はそのノードを新しい浮いたノードとして作り、動作点は収束のエラーで
  失敗します。エラーはそのノードと、抽出のネット名の出どころを示します。
- テストベンチが、抽出結果にない、抽出したセルの中のデバイスの量を求めている(デバイスが Magic の名前 `X0` のままのときの
  `@m.x1.xxm5.msky130_fd_pr__nfet_g5v0d10v5[l]`)。ngspice は "no such device" と言って何も評価しないので、`.control` のスクリプトは誤った値で
  先に進みます。エラーはそれらを示します。

このシミュレーションが保存するのは、テストベンチ自身のネットと電圧源の電流、`.meas` の行が参照するベクトル、そして求められた信号
(`signals`、`output`、`input`、`spectrum`、`sample`、スペックが測る信号)だけです。抽出結果のセルの中のノードは保存しません。CDAC のモード `rc`
の抽出結果にはノードが数千あり、長い過渡解析ではそのすべてを時刻ごとに保存することになるからです。そのようなノードを見るには
`signals` に名前を書きます(例: `x1.out.n0`)。テストベンチに自分の `.save` の行があれば、その指定どおりに保存します。回路図での過渡解析も
同じものを保存します。[シミュレーションが保存するもの](#what-a-simulation-stores) を見てください。

結果とジョブ(`extracted` と、入力の `extraction` の項目)には、どのセルをどの抽出ジョブで置き換えたかが残ります。レイアウトが変わると、
そのシミュレーションも古くなります。抽出ジョブを指定したシミュレーションは、そのジョブが古くならない限り最新のままです。最新の抽出結果で
実行したシミュレーションは、同じモードのより新しい抽出が別のネットリストを出した時点で古くなります。例: 1 mm の配線を駆動するインバータの立ち下がり遅延は、回路図で 26 ps、モード `c` の抽出結果で 186 ps、
モード `rc` で 214 ps です。

<a id="what-a-simulation-stores"></a>
## シミュレーションが保存するもの

過渡解析は、回路図でもポストレイアウトでも、raw ファイルに次のものだけを保存します。

- テストベンチ自身のネットと、電圧源の電流
- `.meas` の行と `.control` ブロックが参照するベクトル(`v(x1.outp)`、または `let` の中の `x1.outp`)
- 求められた信号: `signals`、`output`、`input`、`spectrum`、`sample`、実行結果から読む測定、そして `check_specs` と `sweep`
  でスペックが測る信号

セルの中のノードは保存しません。そうしないと、ngspice はすべてのノードを時刻ごとに保存します。ミックスドシグナルのブロックでは 1 回の
実行で数百 MB になり、changeset の証跡はすべての実行を残します。例えば SAR ADC のコンパレータはベクトルが 3,191 本あり、モンテカルロの
過渡解析 1 回で 870 MB を書きました。セルの中のノードを見るには、`signals` に名前を書きます(例: `x1.xcmp.outp`)。すべてのノードを
保存するには `save_all: true` を渡すか、Simulate パネルで **すべてのノードを保存** にチェックを入れます。テストベンチに自分の `.save`
の行か `.options savecurrents` があれば、その指定どおりに保存します。動作点解析、AC 解析、DC スイープはすべてのノードを保存します。
これらのファイルは小さいからです。

実行が保存しなかった信号を結果で求めると、そのことと、次の実行で保存する方法を返します(`missing_hint`)。ジョブには、何を保存したかが
残ります(`saved: testbench`)。

<a id="stand-ins"></a>
## 代役: セルを動作モデルでシミュレーションする

トップレベルには本物のセルを置く必要があります。レイアウト、LVS、抽出はそれをもとに作るからです。一方で、トップレベルのシミュレーションには、
遅いブロックを動作モデルに置き換えないと現実的に回らないものがあります。例として、SAR コントローラがスタンダードセルで約 1700 トランジスタの
ADC を考えます。コントローラのイベント駆動モデルが別のセルにあり、ピンは同じ名前、同じ順です。ADC の 256 点 FFT のテストベンチには約 50 µs の
過渡解析が要り、それが現実的なのはモデルを使うときだけです。**代役**(stand-in)を使うと、設計を編集せずに、
コントローラの代わりにモデルを置いてこのテストベンチを実行できます。

```
run_simulation(lib="adc", cell="tb_adc_fft", substitute={"adc/sar_logic": "adc/sar_logic_ideal"}, ...)
```

テストベンチの下のどの深さにある `adc/sar_logic` のインスタンスも、すべて `adc/sar_logic_ideal` としてネットリストにします。インスタンスは
代役自身のシンボル(その format と template)でネットリストにします。シンボルのない(回路図だけの)代役は、元のセルのシンボルと代役の名前で
呼び出します。`run_simulation`、`check_specs`、`sweep`、`POST /api/p/<project>/sim` のどれも `substitute` を受け付けます。次の場合は、
何が違うかを添えて拒否します。

- どちらかのセルが存在しない
- 代役のピンが元のセルのピンと同じ順で同じでない(それぞれのシンボルのピン。シンボルがなければ回路図のポート)。メッセージはピンを名指しします。
  例: `in another order: pin 2 is vss, not out`
- 代役が、置き換える元のセルを直接またはさらに下に含んでいる(テストベンチがその上に置くセルや、ほかの代役を経由する場合も含みます)。
  ネットリストが終わりません。メッセージはその連なりを示します。例: `div_s > wrap > div`
- 代役自身もほかのセルで置き換えられている(`{a: b, b: c}`)。各セルの最終的な代役を書いてください
- 代役の名前が、テストベンチがネットリストにするほかのセル(別のライブラリのもの)と同じ。ネットリストには名前ごとに 1 つのサブサーキットしか
  ないので、2 つが 1 つとしてシミュレーションされてしまいます
- 同じセルを、抽出結果と代役の両方でシミュレーションしようとしている。メッセージは代役がどこから来たか(たとえばテストベンチの既定)を示し、
  `substitute {"lib/cell": null}` で取り消せます

**どこに残すか。** 一度だけなら `substitute` を渡します。再現できなければならない結果は、意図に残します。

- **仕様**は、コーナー、温度、条件と並べて `substitute` を持てます。ADC の SNDR の仕様なら、何も指定しない `check_specs` がモデルで測ります:
  `{measure: sndr_db, min: 60, testbench: tb_adc_fft, spectrum: {...}, substitute: {adc/sar_logic: adc/sar_logic_ideal}}`。
- **テストベンチ**は、そのすべての実行が既定で使う代役を持てます。回路図エディタの **Simulate** パネルからの実行も含みます。これはテストベンチ自身の
  意図の制約です: `{kind: constraint, text: "コントローラはモデルで: トランジスタレベルで 50 us は遅すぎる", rule: {type: substitute, cells: {adc/sar_logic: adc/sar_logic_ideal}}}`。
  実行はファイルからこの rule だけを読みます。ファイルのほかの部分に問題があっても実行は止まりません。ファイルがまったく YAML でない場合は
  `substitute_warnings` で知らせます(代役は読まれていません)。substitute の rule 自体が壊れている場合は、ファイルと項目を示して実行を拒否します。
  同じ rule をポートのあるセル(テストベンチではなく、測られるセル)の意図に書いても使われず、意図パネルが警告します。

指定は重なります。テストベンチの既定が先にあり、仕様の指定がその上、呼び出しの指定がさらにその上です。`null`(または `""`)を
対応させたセルは、そのセル自身としてネットリストにします。たとえば `check_specs(..., substitute={"adc/sar_logic": null})` は、SNDR の仕様を
一度トランジスタレベルのコントローラで測り、モデルを確かめます。

**結果に残ること。** 代役を使った実行は、結果とジョブに代役を記録します(`substitute` と、それぞれがどこから来たかの注記)。何も置き換えなかった
指定は、無視せず `substitute_warnings` で知らせます。セルがテストベンチにない、または抽出結果やほかの代役のセルの中にしかない場合です。
`check_specs` は仕様ごとの報告に、その仕様の代役を書きます。SNDR の値を読む人は、コントローラが動作モデルだったことがわかります。
代役の違う仕様が 1 つの実行を共有することはありません。1 つの点でテストベンチを複数回実行したときは、その点の `jobs` が実行ごとに、
測った仕様を添えて名前を付けます(`tb_adc_fft (s1)`)。

**来歴。** 代役はジョブの入力の一部です(テストベンチの `netlist` の項目の `substitute`)。代役を使った実行が、代役なしの実行や別の代役の実行に
再利用されることはありません。ネットリストのハッシュは、元のセルではなく代役のセルを含みます。モデルが変わればその実行は古くなり、
トランジスタレベルのコントローラだけが変わっても古くなりません。

**抽出結果と一緒に。** `extracted` と `substitute` は併用できます。抽出したセルはレイアウトから、置き換えたセルは代役として、ほかのセルは
これまでどおり回路図からネットリストにします。抽出したセルの中にあるセルは回路図からネットリストにしないので、置き換えても何も起きず、
結果がそれを知らせます。スイープで、置き換えたセルの中のプロパティは変えられません(メッセージが代役を示します)。代役の中なら変えられます。その回路図を
ネットリストにするからです。

<a id="cells-from-a-dependency"></a>
## 依存関係のセル

シミュレーションはネットリストが ngspice に指示することを実行し、[依存関係](libraries.ja.md#dependencies)のセルは誰かほかの人の
成果物です。そこで Undine は、シミュレーション、スイープ、仕様の確認を実行する直前に、依存関係のセルが加える行のうち、コマンドを
実行するもの(`.control` ブロック、`*#` の行)や、誰も見ていないファイルを読むもの(PDK の外の絶対パス、`..` を含むパス、`$` や
`~` が残るパスを持つ `.include`、`.lib`、XSPICE の `file=`)を、人が[その依存関係を信頼して](libraries.ja.md#trusting-a-dependencys-code)
いない限り拒否します。ある行が依存関係のものとみなされるのは、それが依存関係のセルの中にあるとき、またはあなたの回路図に配置した
そのシンボルの 1 つから作られたときです。再利用されるはずの結果も、再利用の前に確かめるので、同じく拒否します。

```
ip/opamp (dependency analog_ip 1.2.0, not trusted): code block s1 line 1: .control; a person can trust analog_ip@1.2.0 in this project (undine lib trust demo ip, or Trust... in Undine); an agent cannot
```

**LVS**(KLayout、Magic + Netgen)は制御コードを実行しないので、参照ネットリストの中のそれらのパスだけを、実行を始めるときに
拒否します: サインオフの状態の表示や、changeset での結果の再利用は、ネットリストを読んでも拒否しません。Xschem のネットリスタでの
netlist ビューは、プロジェクトに入っている信頼されていない依存関係の回路図やシンボルの属性に `tcleval(...)` があれば拒否します。
Xschem は、どのシンボルを読むかにかかわらず、それを Tcl として評価するからです。Undine 自身のネットリスタでは警告するだけです
(`not trusted: would be refused in a simulation: ...`)。シミュレーションにテキストで渡したネットリストは呼び出し側のもので、
確かめません。

シミュレーションと検証のパネル、テープアウトのパネルの sign-off のスイートの行は、拒否を **信頼...** とともに表示し、その依存関係の
信頼のダイアログが開きます。信頼したら、もう一度実行してください。changeset のプレビューでは、拒否は代わりにプロジェクトで依存関係を
信頼するよう示します。エージェントは拒否をテキストで受け取り、あなたに尋ねます。

<a id="outdated-results"></a>
## 古くなった結果

実行ごとに、何に対して実行したかを記録します。レイアウトのセル(そこから参照するものすべてを含む)、回路図から生成したネットリスト、PDK、
デッキ、ツールのバージョンのそれぞれのハッシュです([ジョブの来歴](../reference/data.md#job-provenance)を参照)。実行後に設計が変わると、
結果は **Outdated**(古い)と表示され、何が変わったか(「layout of mylib/inv changed」「schematic netlist of mylib/inv changed」)と
**Rerun** ボタンが出ます。シミュレーションのパネルも同じです。比較は内容で行うので、Undo で実行時の状態に戻せば結果は再び最新になり、
回路図にコメントを足しただけでは LVS の結果は古くなりません。

<a id="pdk-models-in-a-simulation"></a>
## シミュレーションでの PDK のモデル

シミュレーションは PDK のモデルライブラリ全体を読みません。ネットリストが指定するセクション(sky130 では `sky130.lib.spice tt`、ミスマッチでは
`tt_mm`)を、ネットリストから届くものだけを残したコピーとして読みます。残すのは、ネットリストとそこから読み込むファイル(スタンダードセル、
抽出結果)が使うデバイスと、それらが依存するパラメータ、オプション、乱数の引き方で、ライブラリ自身の順序と書き方のままです。結果は最後の桁まで
同じで、モデルの読み込みは何分の一かの時間で済みます。sky130 で、混んだマシンの上では、トランジスタ 1 個の動作点がライブラリ全体で 65 秒、
コピーで 0.2 秒(空いたマシンなら全体で約 20 秒)、SAR ADC のようなデバイスの組み合わせ(1.8 V、低 Vt、5 V のトランジスタ、MIM キャパシタ、
スタンダードセル)の動作点が 80 秒と 2 秒でした。一緒に読むセクション(GF180MCU では `typical`、`res_typical`、
`mimcap_typical` など)はまとめて縮小し、ほかのセクションで残した定義が必要とするものも残します。コピーは
PDK のバージョン、セクション、デバイスの組み合わせごとに一度だけ `~/.cache/undine/models`(`UNDINE_CACHE`)に作り、ライブラリのファイルが
変わると作り直します。ジョブのネットリストにはライブラリとセクションの名前が残り、ジョブの状態(`models`)とログの先頭の行が、どのコピーを
読んだかを示します。縮小の仕組みが理解できないライブラリ(IHP SG13G2 のもの)やネットリストの行があれば全体を読み、ジョブがその理由を示します。
`UNDINE_SIM_FULL_MODELS=1` を設定すると、常に全体を読みます。
